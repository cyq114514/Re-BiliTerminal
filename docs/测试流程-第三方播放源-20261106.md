## 0.14 第十六轮：返回到导航菜单 + 线路自动屏蔽 + 提速（2026-11-06）

### 返回目标

用户截图：番剧「推荐」页点标题栏返回，要回到**导航菜单那一屏**（16 个图标的网格）。
原因：`MenuActivity.killAndJump()` 跳转时会把菜单自己 finish 掉，栈里没有菜单；
上一轮把 `BangumiActivity` 改成 `setTopbarExit()`（纯 `finish()`）就会直接退出应用。
改回 `setMenuClick()`（启动 `MenuActivity`），返回箭头图标保留。子页面仍是 `setTopbarExit()`
回上一级，行为不变。

### 线路自动屏蔽（新增 `SourceChannelHealth.java`）

| 规则 | 行为 |
| --- | --- |
| 连续 2 次解析不到地址 | 屏蔽 12 小时 |
| 播放器 `onError` 报一次 | 屏蔽 12 小时（用户已亲眼看到播不了） |
| 解析成功 | 立即解封 + 记「上次成功」时间 |
| 过期 / 选集页点「恢复 N 条」 | 自动或手动解除，不会永久丢线路 |

记录按 `channel.id`（含 sourceId + 作品键）落 SharedPreferences，**重启后仍生效**。
`ThirdPartyPlayback` 起播时把线路 ID 通过 Intent extra `third_channel_key` 交给播放页，
`PlayerActivity` 的 ijk `onError` 据此上报失败；不经过 `PlayerData`，Parcel 顺序不用动。
选集页过滤被屏蔽线路、状态栏显示「已屏蔽 N 条」并给「恢复」chip；`onResume` 用缓存重新过滤，
所以从播放器返回后坏线路立刻消失。

### 提速

1. **跳过坏线路**：以前每条死线路都要等一次 8~10s 超时，这是加载慢的主要来源。
2. **上次成功的线路排最前**：选集页按 `lastSuccess` 排序，起播第一条就命中。
3. **并发升级等待 4s → 2s**：坏线路已过滤，不必再为慢站点等 4s 才补第二条。
4. **m3u8 内容缓存 5 分钟**：同一集重看省掉一次播放列表网络往返，改写仍每次重做以保证 token 绑定当前会话。

### 断言

`SourceChannelHealth` 纯 Java 断言 `RESULT pass=9 fail=0`：1 次解析失败不误杀、
连续 2 次屏蔽、播放失败 1 次屏蔽、成功解封、屏蔽计数、已落盘、模拟冷启动后仍生效、一键恢复。

## 0.11 第十三轮：修复「大量线路播不了」（2026-11-06）

### 现象与定位

播放页显示「这条线路播不了」、进度 `00:00/00:00`。这句文案只在
`PlayerActivity:1734` 的 `ijkPlayer.setOnErrorListener` 里设置 → 说明**解析阶段认为成功**
并交了一个 `mediaUrl` 给播放器；若解析全失败会弹「没有线路能播」对话框，根本不进播放器。

真机 logcat 当次不可用：`Logu.LOGD_ENABLED=false`（V/D/I 全关），`third>` / `third-diag>`
全是 D 级；缓冲只覆盖 83 秒；设备未开文件日志。因此从代码层复现。

默认 `matchVideoUrl` 正则只要求「URL 里出现 m3u8/mp4 字样」，实测：

| URL | 修复前判为直链 | 实际 |
| --- | --- | --- |
| `player.php?v=123.m3u8` | 是 | 播放页 |
| `vodplay/1-1.html?url=abc.m3u8` | 是 | 剧集页 |
| `player.js?need=m3u8` | 是 | 脚本引用 |
| `cdn/.../123.m3u8?token=…` | 是 | 真直链 |

`HtmlVideoScanner.collect()` 先抓 `src/href` 属性，脚本与播放器链接常排在真流前面；
旧 `scan()` **第一条命中即 return** → 稳定把网页地址交给 ijk，ijk 收到 HTML 就报错。

### 修复

| 文件 | 改动 |
| --- | --- |
| 新增 `MediaUrls.java` | `isDirectMedia()`：去掉 query/fragment 后 path 必须以 `.m3u8/.mp4/.mkv/.flv` 结尾；`looksLikePlaybackPage()`、`rank()`、`summarize()`（日志脱敏，绝不输出 query 里的 token） |
| `AnimekoMediaRule.matchVideo()` | 正则命中后再过 `isDirectMedia`，网页地址一律返回 null |
| `HtmlVideoScanner.scan()` | 不再第一条即返回：收齐全部真直链按 m3u8>mp4>mkv>flv 挑最好的；被拦下的页面地址改投 `nestedUrls` 跟进 |
| `MediaResolver` / `ThirdPartyPlayback` / `PlayerActivity` | 解析成功、起播、ijk 错误全部落 **W/E 级**日志（正式包可见），含 `via`、URL 摘要、请求头键名、错误码 |

### 断言

纯 Java 18 条全部通过：3 类网页 URL 修复前确实会被误判、修复后全部拦掉；
真 m3u8/mp4/大写扩展名/flv 不误杀；`.ts` 分片不当主播放列表；
网页 URL 正确进嵌套候选；m3u8 优先级高于 mp4；日志摘要不含 token。

## 0.9 第十轮：弹弹play 凭据实测（2026-11-06）

AppId/Secret 已写入 `local.properties`（gitignored）并注入 `BuildConfig`。
从**手机网络出口**用 curl 按官方签名算法实测：

| 请求 | 响应 | 响应头 |
| --- | --- | --- |
| 不带鉴权头 | 403 | `X-Error-Message: Missing Authentication Headers` |
| 正确 AppId + Timestamp + Signature | 403 | `X-Error-Message: Invalid AppId` |

需要用户在弹弹play 开放平台核对：应用是否已启用/审核通过、复制的是否为开放平台 AppId（而不是别的字段）。

不再对每一集重复请求弹幕（日志 `third-danmaku 凭据被服务端拒绝…`）。
换凭据后重新打包即可自动恢复，播放与其它功能不受影响。

## 0.3 第四轮：播放解析崩溃 + 搜索慢（2026-11-06）

### 崩溃：`IndexOutOfBoundsException: No group 1`

堆栈落在 `HtmlVideoScanner.collect` ← `scan` ← `MediaResolver.scanPage`，也就是**点某一集、解析播放页时崩**。

根因：`HtmlVideoScanner` 里的 `ABSOLUTE` 正则 `(?i)https?://[^\s"'<>\\]{6,2048}` **没有捕获组**，
而 `collect()` 统一取 `matcher.group(1)` —— 只要 `scan` 走到「裸绝对地址」这一轮就必崩。
（`ATTR` / `SCRIPT` 有组，所以只在部分页面触发，表现为「有时能搜、一点播放就闪退」。）

修复：正则补捕获组 `(https?://…)` + `collect()` 改为 `groupCount()>=1 ? group(1) : group()`。
纯 Java 断言通过：三种来源共抓出 3 个候选，无异常。

### 慢：四处开销，逐个削

| 项 | 原来 | 现在 |
| --- | --- | --- |
| 并发 | 3 线程跑 63 个源 | **6 线程** |
| 单源耗时上限 | 只有 readTimeout 12s（慢吞吞吐字节可拖到 12s+） | 搜索阶段加 **8s 整调用超时**（`Call.timeout`） |
| 重复搜索 | 每次都把 60 个外站重打 | **5 分钟内存缓存**（源+关键词，LRU 120 条；B 站混排与「源」页共用） |
| 健康度落盘 | 每 3s 整表重写 ~170KB SP，且解析+序列化都在工作线程 | **节流到 15s**，一次搜索最多写 1~2 次 |

预期：63 源首次搜索从「一分钟级」降到 10~25s；5 分钟内重复搜同一关键词几乎秒出。
启停/排序/删除源与导入订阅都会清空搜索缓存。

## 0.2 第三轮：搜索 0 结果的根因与修复（2026-11-06）

**日志证据**（用户真机，24377 进程）：

```
third-diag 嘀嗒影视 a分支 命中=0 文档=23821 选择器=.myui-vodlist__media h4 > a
third-diag 嘀嗒影视 丢弃条目：链接非法        ← 连打 12 次
third-diag 落攻动漫 indexed分支 名称=0 链接=0 文档=97124
third-diag 落攻动漫 丢弃条目：链接非法        ← 连打 14 次
```

**根因**：`Templates.replaceValue()` 只判了 `template == null`，没判空串。
订阅里 **63/63 条源的 linkTemplate 都是空串**，而 `"".replace("{value}", href)` 的结果是空串，
于是每一条搜索结果都被 `UrlGuard` 判成「链接非法」丢掉 —— 表现就是「每个源都 HTTP 200，但一条结果都没有」。
这是上一轮我引入的缺陷（日志里 0 个「搜索 成功」，与 63/63 空模板完全吻合）。

**修复**：空/空白模板原样返回 href（与上游 `applyLinkTemplate` 的 `isNullOrBlank() → rawHref` 一致）；
模板不含 `{value}` 时按固定地址处理。已用纯 Java 断言验证：

```
PASS 空模板→原样 -> [/voddetail/123.html]
PASS 空白模板→原样 -> [/a.html]
PASS null→原样 -> [/a.html]
PASS 占位符替换 -> [https://x.com/v//a.html]
PASS 无占位符→固定地址 -> [https://x.com/fixed]
ALL PASS
```

> 注意：`/a.html` 前面出现 `//` 是因为测试用例本身把 `{value}` 放在路径末尾、value 又以 `/` 开头，
> 真实配置里 `linkTemplate` 全为空，走的是第一条分支。
