## 3. 已知限制与未验证项

1. **全部改动未装机点过**（用户说明由他手动测试）。最该看的四处：
   - 下载列表：顶栏「批量」是否被标题/时钟挤掉；勾选高亮是否清楚；删除确认框是否可读。
   - **所有 `RefreshListActivity` 子页**（推荐/热门/收藏等）顶栏：我把 `pageName` 的右锚点改到了新增的 `btn_batch` 上，按钮 GONE 时靠 RelativeLayout 回退，**理论上位置不变，但没实看**。
   - 私信页：辅助按钮灰底后文字是否仍清楚（白字在 `#4D262626` 上）；40dp 高度在手表上是否还能点。
2. **批量删除的边界没跑过**：选中包含「正在下载」的项时会先 `stopService` 再删，与原单条逻辑一致，但**连续删几十项的耗时与失败分支未测**。
3. **文件系统删错的风险**：沿用了 `type.contains("video")` 才删目录的校验（防脏数据回退到相册目录），批量路径下同样生效，但没实际验证过脏数据场景。
4. **`sel_filter_chip` 的选中态仍不跟随自定义主题**（上一轮遗留，未动）。

## 4. 番剧缓存可行性（评估，不写代码）

### 4.1 结论

**能做，且比预想容易**——项目已经有 PGC 取流和分段下载两套基础设施，缺的只是"把番剧接到下载队列"这一段。

### 4.2 现有可复用的件

| 件 | 现状 | 位置 |
|---|---|---|
| 番剧取流 | **已实现**：`pgc/player/web/v2/playurl`（PiliPlus 同款），失败回退 v1；参数带 `ep_id`/`season_type`/`season_id` | `api/PlayerApi.java:421 getBangumi()` |
| 返回形态 | **`durl` 分段 mp4**（`fnval=1`），音视频已混合，**不需要合并** | `PlayerApi.java:471-477` |
| 分段下载 | 已支持多段 `urls_video` 顺序下载 | `service/DownloadService.java:178-220` |
| 弹幕 | 已有 `url_danmaku` 通道 | `DownloadService.java:179` |
| 下载列表 + 批量删除 | 本轮刚补完 | 见 §1.1 |

### 4.3 需要新增的三件事

1. **数据库**：`DownloadSection` 加 `epid`（番剧按集存进度/身份，靠 `aid+cid` 定位不到），`DownloadSqlHelper` 做版本迁移。
2. **下载分支**：`DownloadService` 加 `video_pgc` 类型，调 `PlayerApi.getBangumi()` 取 durl，走现有分段下载与落盘。
3. **入口 UI**：番剧选集页加「缓存」按钮 + 清晰度选择（可复用 `QualityChooserActivity`），写入下载记录。

估计 **200~350 行，跨 5~7 个文件**。

### 4.4 风险（需要先拍板）

| 风险 | 说明 |
|---|---|
| **合规/条款** | B 站对 PGC（番剧/影视）内容明确限制下载传播，与 UGC 缓存的风险等级不同。**是否要做，由你决定，我不替你拍板。** |
| VIP/付费剧集 | 无权限账号取流会返回业务错误（如 -10403），UI 必须给出明确提示而不是"下载失败"四个字 |
| 播放地址时效 | durl 通常 2 小时过期，排队过久的任务会失败（现有 UGC 也有同样问题） |
| 清晰度上限 | 现在 `getBangumi()` 用 `fnval=1`（durl），拿不到 4K/高码率；要更高清得给 PGC 也开 `fnval=4048` 的 DASH 分支 |
| 风控 | 批量连续下载多集容易触发限流 |

**如果你确认要做，我建议拆两步走**：先做单集缓存（durl 1080P，不带选集批量），跑通后再加批量。这样能先验证权限/时效/落盘三件事。
