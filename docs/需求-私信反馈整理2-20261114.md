## R1（P2）UP 主头像小红点：可消除 + 状态持久

**原文**：
> 那个消除阿婆主头上的红点还是没有实现
> 如果我消除了红点之后，切个页面，再换回动态页，红点还是会出现⊙▽⊙

**定性（已定位到机制层）**：这是 2026-11-07 反馈过的「刷新视为已读」的延续。当时的修复（DynamicActivity.java:209、:234、:308）只做了一半——手动下拉刷新时把**内存里** `RecentUpAdapter` 列表的 `has_update` 置 false：

- 已读状态**没有持久化**。切到别的页面再回动态页，`loadRecentUpList(false)` 重新拉接口，服务端 `has_update` 原样带回 → 红点复活。与反馈描述逐字吻合。
- 「还是没有实现」指的应当是「持久消除」这个完整预期，而非消除动作本身不存在（消除=下拉刷新，用户已经摸到了）。

**方案方向**：本地持久化 per-UP 已读标记（SharedPreferences 存已读 mid 集合或 mid→时间戳，加载最近 UP 列表后与本地已读做差集）；服务端字段语义不动。可顺带支持点按红点手动消除。

**待澄清**：期望的消除交互——A. 保持「刷新即已读」但要求持久；B. 点红点手动消除；C. 点进该 UP 动态即算已读。可多选。

## R2（P3）私信聊天气泡与按钮跟随主题

**原文**：
> 私信的聊天气泡和按钮，我觉得可以跟随主题

**定性（已定位）**：气泡颜色是写死的——PrivateMsgAdapter.java:113 自己发送的气泡卡片 `R.color.pink`、:117 接收气泡 `#78242424`，与主题色系统（见 docs/decisions-theme-color.md、UI 一致性收口那批）完全脱钩；发送按钮同理在 activity_private_msg.xml。官方客户端气泡粉色跟随主题。

**方案方向**：气泡/按钮改走主题色 attr（与全局主题色跟随机制同一口径），注意异步 bind 期也要 apply（主题色跟随的历史坑）。影响面仅私信会话页。

**待澄清**：无，可直接立项。建议顺带过一遍 NoticeHolder/回复卡片是否同样写死。

## R4（P1）弹幕：不滚动、突然出现 + 卡顿回归

**原文**：
> 还有一个还是弹幕显示问题，现在这弹幕不是滚动过来，而是突然出现，弹幕又和原版一样，出现卡顿的问题了

**定性（代码定位，未实机定位）**：1.3.6 为根治「弹幕整屏消失又出现」上了**位置驱动投放**（PlayerActivity.java:388 起）：弹幕不再整包灌进引擎，而是挂在 **250ms 进度 tick** 上逐条投放（feedDanmaku），另有实验室开关可回退旧链路（PlayerActivity.java:2868）。

两个症状可以用同一机制解释：**主线程/进度 tick 被卡 → 弹幕补投批量化 → 一批弹幕同时入场（视觉上「突然出现」）+ 滚动帧率掉（「卡顿」）**。卡顿源与本日性能审计的 P1（两个前台服务通知轮询、暂停也刷）可能同源或叠加。「又和原版一样」说明用户感知为回归。

**下一步（立项后）**：① 问用户实验室「位置驱动」开关状态（关=旧链路已知问题，开=位置驱动新问题，定性完全不同）；② 问复现设备/必现性；③ 卡顿时段抓 logcat/systrace，确认 tick 延迟与卡顿源；④ 对照性能审计 P1 修复排期。

## 追加：反馈者复测回复与「同屏弹幕上限」（2026-11-14 深夜）

**反馈者回复**：「突然出现」已消失（错峰生效），但**弹幕滚动仍一卡一卡**；反馈者自推测低性能设备运存不足/SOC 性能低，且无法提供设备参数。

**定性**：「一卡一卡」= 渲染资源问题，与「突然出现」（投放时序）是两个独立症状。代码层三实锤：① 仓库 `DanmakuView extends View`——弹幕每帧画在**主线程** onDraw；② DFM 缓存池按运存等比缩（1MB × memoryClass/3），低运存设备缓存抖动；③ 同屏条数无上限（DFM 内置 `setMaximumVisibleSizeInScreen` 从未调用）。

**实施（用户批准，仅做 A）**：
1. `PlayerActivity` 配置链接入 `setMaximumVisibleSizeInScreen()`，读 `player_danmaku_max_visible`，**默认 30**，支持 -1=引擎自动 / 0=不限制，解析失败回落 30；
2. `SettingTerminalPlayerActivity` 弹幕组新增「同屏弹幕上限」（input_int）；
3. **DFM 调整（仓库内 vendor 补丁）**：`DanmakuFilters.QuantityDanmakuFilter` 防全拦豁免窗口 `MAX_DANMAKU_DURATION/20`(≈300ms) 收紧为 `/4`(≈1.5s)——位置驱动 250ms tick 高频投喂下，密集段弹幕间隔 300~500ms 原豁免几乎每次命中，实测上限 3 仍在屏 6 条；收紧后最坏每 1.5s 强制放行一条，屏不会空。

**E2E 验证（真机）**：设置条目上线、默认 30 → 设 3 → 播 BV17dxS6uEFu → 屏上滚动弹幕 3~4 条（对比收紧豁免前 6 条）→ 恢复 30。验证途中误改「弹幕速度倍率」为 30，已恢复 1.0 并回读确认；同屏上限/缩放/不透明度均回读无误。

## 追加：第三批反馈（2026-11-14 深夜，同反馈人）

**原文**：①「那统一私信的 UI 和顶部标题栏的渐黑能全局实现吗🥺」②「对的对的，还有私信输入框的跑马灯，跑马灯！」

**研究结论**：渐黑 `background_titlebar_fade` 全项目仅私信页+下载页在用（57 个顶栏布局未覆盖）；顶栏跑马灯 1.3.3 已全局，但私信会话页 pageName 固定「私信」二字永不溢出，形同虚设；私信 UI 的 token 统一（辅助按钮/输入框/气泡）在之前批次已完成，无需单独立项。

**实施（用户批准，澄清后确认②=输入框 hint 跑马灯）**：
1. **顶栏渐隐黑全局化**：`BaseActivity.setRound()` 统一挂载（每次 onStart 按开关重设，切开关返回页面即生效）；新增开关 `titlebar_fade`（界面设置「顶栏渐隐黑」，默认开）；沉浸页排除：图片查看/直播/听歌三 Activity override `titlebarFadeEnabled()`=false（播放页直接继承 Activity 天然不挂）。
2. **输入框 hint 跑马灯**：Android marquee 不作用于 hint → 覆盖层方案（`MarqueeTextView` 叠在输入框上，未输入且未聚焦时显示长文案滚动，聚焦/有文本隐藏，触摸穿透到下层 EditText）；文案 `hint_private_message_marquee`=社会主义核心价值观全句；首验发现覆盖层半透明底透出下层原 hint 造成重影 → 覆盖层显示期间下层 hint 置空、隐藏时恢复。

**验证（真机）**：渐黑——推荐页/菜单页顶栏生效、开关关闭返回页面立即恢复透明（fade1/fade_menu/fade_off2.png）；hint 跑马灯——空闲态滚动无重影、聚焦输入态覆盖层正确隐藏（"CE" 测试字符）、清空后覆盖层回归滚动继续（ghost1/2、ghost_focus、ghost_clear.png），全程零崩溃。**未提交**，与此前各批一起待发版。
