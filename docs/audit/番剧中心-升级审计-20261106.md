## 2. Bangumi API 接入方案（已实测）

### 2.1 实测响应（2026-11-06，UA `ReBiliTerminal/1.3.0 (audit)`）

| 接口 | 结果 |
| --- | --- |
| `GET /calendar` | 200，86517 B，7 天共 114 条，**每条都有 `air_weekday`**；`weekday.id` 1..7 = 周一..周日 |
| `POST /v0/search/subjects?limit=2&offset=0` + `{"keyword":"","sort":"rank","filter":{"type":[2],"air_date":[">=2026-10-01","<2027-01-01"]}}` | 200，`total=169`（2026Q4 动画条目），`data[]` 含 `id/name/name_cn/date/platform/images{small,grid,medium,common,large}/summary/rating{rank,total,score}/tags/eps/total_episodes/collection/nsfw` |
| 同上 `limit=100` | 200，但 **returned=20，limit 被服务端钳制为 20**（季度 169 条需 9 页） |
| `GET /v0/subjects/400602` | 200，含 `rating{rank:43,score:8.5}`、`infobox` 中「放送星期=星期五」「放送开始」「别名[]」「话数」 |

结论：**季度识别用 `air_date` 区间过滤 + `type:[2]`；星期归属用 `/calendar` 的 `air_weekday`；别名/放送星期兜底用详情 `infobox`**。字段全部来自实测响应，无臆造。

### 2.2 接入设计

| 项 | 方案 |
| --- | --- |
| 网络 | **新建独立 `OkHttpClient`**（不经过 `NetWorkUtil`）：无 Cookie、独立 UA（`ReBiliTerminal/x.y.z (Android)`）、`followRedirects(true)` 但只允许 https、connect 8s/read 12s；`setOkHttpSsl` 复用老系统 TLS 适配 |
| 季度计算 | 运行时按 `Calendar.MONTH` 推导（1-3/4-6/7-9/10-12），不写死；支持上/下季度偏移 |
| 分页 | `limit` 固定 20（服务端上限），`offset` 递增；首页 20 条即出屏，滚动续拉 |
| 缓存 | 独立 SP 文件 `bgm_cache`：key=`season_{year}Q{q}`，value=JSON + `fetchedAt`；TTL 6h（列表）/24h（详情）；**接口失败时保留旧数据只提示"离线/上次更新于…"**，绝不清空 |
| 限流 | 进程内单飞（同一 key 并发请求合并）+ 串行队列，请求间隔 ≥300ms；返回 429/5xx 指数退避 1 次 |
| 取消 | 页面级 `generation` 计数（复用 `BangumiActivity` 既有范式 `idxGeneration`），响应回主线程先比对代际 |
| 图片 | `images.grid`（100px）做列表缩略图、`common`（400px）做详情；**必须绕过 `GlideUtil.url()`**（否则拼出 `...jpg@0e_25q_512w.webp` 404），走 `Glide.with().load(rawUrl)` |
| 归一化 | `/calendar` 与 v0 搜索结果按 `id` 合并：`air_weekday` 只来自 calendar/infobox，缺失则为「未定档」，**不参与任何星期筛选** |

## 3. 新番推荐页设计

### 3.1 位置（不改现有 4 页签结构）

`BangumiActivity` 现有页签已满（推荐/追番/索引/新番），手表宽度下第 5 个页签会挤。方案对比：

| 方案 | 做法 | 代价 | 结论 |
| --- | --- | --- | --- |
| A（推荐） | 新增页签「新番表」并置于首位，原 B站「新番」页签并入其下二级切换（B站时间线 / Bangumi 季度） | 改动集中在一个 Activity + 一个布局 | **推荐** |
| B | 把现有「新番」页签内容整体替换为 Bangumi（B站时间线降级为二级） | 语义变化，老用户找不到 B站时间线 | 备选 |
| C | 新建独立 `BgmActivity` 从菜单进入 | 与"推荐页应是番剧分区发现入口"冲突（需求 3.7 明确不允许割裂） | 不采用 |

### 3.2 页面结构（方案 A）

```text
[推荐] [新番表] [追番] [索引]        ← 页签行（沿用胶囊样式 chipBackground）
  └ 新番表
      [2026 Q4 ▾] [上一季] [下一季]   ← 季度条（单行，可左右滑）
      [全部][一][二][三][四][五][六][日] ← 星期筛选行（横向滚动，紧凑 30dp）
      列表：封面(3:4) + 标题 + 原名 + 开播日/星期 + 评分（有则显示）
```

- 季度条与星期条复用 `BangumiActivity.createFilterChip()/wrapFilterRow()`（`BangumiActivity.java:430-454`），主题色随 `ThemeManager.getPrimary()`。
- 排序：默认「按开播日期近→远」，第二项「Bangumi 排名」（`rating.rank>0` 才参与，rank=0 排末位），第三项「按名称」。默认不按评分，符合"优先发现效率"。
- 未定档：`air_weekday` 缺失的条目只在「全部」出现，并显示"未定档"，不落入任何星期。

### 3.3 详情页（复用 + 新增两块）

复用现有详情视觉与结构（`BangumiInfoFragment` 的布局骨架），新建 `BgmSubjectActivity`：

```text
封面 / 标题 / 原名 / 简介(折叠) / 开播日期 / 放送星期 / 季度
Bangumi 评分(score + rank + 评分人数) / 标签 / 原始条目链接(bgm.tv)
── 资源匹配 ──────────────────────────────
[搜索 B站番剧]  → 候选列表（标题+封面+开播年），用户点选确认
[第三方来源]   → 暂无（阶段 C/D 接入后才出现）
[收藏] [已看] [追番中] [暂停追番]
```

- 不自动认定匹配：候选必须人工点选；同名不同季/剧场版/OVA 通过「年份 + platform + 集数」三列并排展示帮助判断。
- 无可用来源时详情页照常展示，播放区显示「暂时没有可用播放源」，不阻塞浏览。

## 4. 元数据与来源映射

### 4.1 数据边界（三个独立命名空间）

```text
BgmSubject(bgmId)  ──┬── BiliMapping(mediaId/seasonId)   ← 仅当用户确认/B站搜索命中
                     ├── AnimekoMapping(sourceId, subjectUrl)
                     └── KazumiMapping(ruleName, subjectUrl)
```

| 规则 | 说明 |
| --- | --- |
| `bgmId` 只做元数据主键，**永不**当第三方 ID 用 | 需求 3.4 硬约束 |
| 第三方 ID 一律带来源前缀（`animeko:{sourceName}:{url}`、`kazumi:{ruleName}:{url}`） | 避免跨站 ID 冲突 |
| 手动确认优先于自动匹配 | 存 `confidence=manual|auto`，读取时 manual 覆盖 auto |
| 匹配不成立允许"空映射" | 详情页可浏览、播放区提示无源 |

### 4.2 持久化（复用 SP + JSON，不引入 Room）

| 存储键 | 内容 | 量级 |
| --- | --- | --- |
| `bgm_cache` | 季度列表/详情 JSON + fetchedAt | 数十 KB |
| `bgm_local_follow` | `[{bgmId,status,followAt,lastWatchedAt,lastEpisode}]` | 数十~数百条 |
| `bgm_mapping` | `[{bgmId, source, sourceKey, title, confidence, updatedAt}]` | 数十条 |

理由：项目无业务数据库、手表存储紧张（`UserLogStore.java:28` 有同类注释），JSON+SP 足够且零依赖；超过 200 条时按 `lastWatchedAt` 淘汰。

## 5. 两种规则引擎方案

### 5.1 Animeko `web-selector`（可纯原生）

实测 `dist/online.json`：63 源，**全部** `factoryId=web-selector`、`version=2`。

| 字段 | 出现次数 | 用途 |
| --- | --- | --- |
| `searchUrl`（含 `{keyword}`） | 63 | 搜索 URL 模板 |
| `selectorSubjectFormatA.selectLists` | 59 | 搜索结果条目选择器（CSS） |
| `selectorSubjectFormatIndexed.{selectNames,selectLinks}` | 58 | 名称/链接两列按下标配对 |
| `selectorSubjectFormatJsonPathIndexed` | 54 | JSON 结果（`$[*]['url','link']`） |
| `selectorChannelFormatFlattened` | 63 | 线路/剧集（`selectChannelNames`/`selectEpisodeLists`/`matchEpisodeSortFromName` 正则具名组） |
| `selectorChannelFormatNoChannel` | 55 | 无线路分组的剧集列表 |
| `matchVideo.{matchVideoUrl,matchNestedUrl,cookies,addHeadersToVideo}` | 63 | **播放地址靠正则匹配播放页 HTML**，非选择器 |
| `subjectFormatId` | a=41 / indexed=21 / json-path-indexed=1 | 三种搜索解析分支 |
| `channelFormatId` | index-grouped=59 / no-channel=4 | 两种剧集解析分支 |
| `requestInterval` | 3000ms 为主 | 必须遵守的请求间隔 |

实现：jsoup 选择器 + 正则（`matchEpisodeSortFromName` 的 `(?<ep>...)` 具名组 → 转 Java 命名组）+ `matchVideoUrl` 正则抓 m3u8/mp4。**不需要 WebView**。

### 5.2 Kazumi 规则格式（实测 18 条）

| 事实 | 数据 |
| --- | --- |
| `api` 版本分布 | 4×3、5×4、6×1、8×3、9×7（**README 只定义到 5，6/8/9 无公开语义**） |
| `useWebview` | **18/18 = true** |
| 字段并集 | `usePost`(12)、`searchMode`(10)、`chapterMode`(10)、`referer`(10)、`searchApiConfig`(8)、`chapterApiConfig`(3)、`antiCrawlerConfig`(6)、`useLegacyParser`(13) |
| 解析模式 | `searchMode/chapterMode` ∈ {`xpath`, `api`}；`api` 模式用 **JSONPath**（`$.data.records[*]`、`$.title`） |
| 播放地址 | **规则内不存在任何视频地址字段** |

### 5.3 关键结论：Kazumi 侧"XPath 提取视频地址"不成立

Kazumi 官方客户端取视频地址的方式是 **WebView 拦截网络请求（`shouldInterceptRequest` / iframe src）**，规则只描述"搜索 → 详情 → 剧集列表"，**不描述播放地址**。因此：

| 需求项 | 能否纯原生 | 说明 |
| --- | --- | --- |
| 规则加载/版本检查 | ✅ | `index.json` + `{name}.json` |
| XPath 搜索/剧集解析 | ⚠️ 部分 | Android 内置 `javax.xml.xpath`（Harmony 精简实现）对 `//div[2]/...` 位置谓词的支持**需真机验证**；备选自写子集求值器 |
| `api` 模式（JSONPath） | ✅ | 需自写极简 JSONPath 求值（`$.a.b[*].c` 子集） |
| 播放地址提取 | ❌ 纯原生 | 只能 ①WebView 嗅探 m3u8 ②MacCMS `player_aaaa` 正则兜底（覆盖有限） |

**不能为了宣称兼容而假设全部规则可执行**——这一点在验收口径里必须先对齐（见 §9 决策项 2）。

## 6. 多源协调与自动故障切换

### 6.1 播放前

```text
候选来源 = B站(有映射时) + 已启用规则源
按 priority(手动>自动) → 健康度(近 N 次成功率) → 解析耗时 排序
逐个解析；失败原因分桶（网络/规则失效/无该集/需要 WebView），不阻塞其它源
首个成功 → 交给现有播放器
```

并发：受控并发上限 3（`CenterThreadPool` + 自建 `ExecutorService`，不复用协程作用域以免污染），单源超时 12s，任一源失败只记录不抛。

### 6.2 播放中（关键改动最小化）

| 改动 | 位置 | 说明 |
| --- | --- | --- |
| 播放器接收自定义请求头 | `PlayerData` 末尾追加 `String[] httpHeaders`（**只能追加**，`PlayerData.java:81,133` 注释已强调顺序约束）+ `PlayerActivity` 分支 | 无自定义头时行为完全不变 |
| 错误上报钩子 | `PlayerActivity.onError` 末尾（`PlayerActivity.java:1708` 前）追加：`if (autoSwitchEnabled && switchable) → 回调 Session` | 不改原有重试语义 |
| 切源判定 | 连续 2 次 `onError` 且 `position` 未前进 或 `what/extra` 属于不可恢复 | 缓冲（`MEDIA_INFO_BUFFERING_*`）与用户暂停**不触发** |
| 防死循环 | 单集切源上限 3 次 / 单源同一集上限 1 次，触发后停自动切换并提示 | 会话内计数，退出清零 |
| 进度恢复 | 切源时携带 `position`，新源 prepare 后 `seekTo` | 复用现有 `progress` extra |

| --- | --- | --- | --- |
| 1 | 第三方源大量是 **http 明文** / 详情链接是 http | A. 放开全局明文（安全回退） B. 只支持 https 源（约 60/63 Animeko；Kazumi 部分可用） C. 仅对"用户手动导入的源域名"逐域放行（需动态配置，实现成本高） | **B 起步**，逐域白名单留到有真实需求再做 |

| 3 | 页签方案 | A. 新增「新番表」置首，B站时间线降为二级 B. 直接替换现有「新番」 | **A** |

## 12. 已知限制 / 未验证项

## 13. 后续方案调整（2026-11-06 当日确认）

用户看过参考截图后明确了产品口径，与本文档 §3 的初版设想不同，实施以本节为准：

| 项 | 初版设想 | 最终口径 |
| --- | --- | --- |
| 页面形态 | 季度表 + 星期筛选 + 三种排序 | **只做对标 Kazumi「热门番组」的单页网格**（封面 + 标题），不做季度/星期/排序 |
| 页签 | 新增「新番表」置首，B 站时间线降为二级 | **直接替换原「新番」页签**（页签总数不变），B 站时间线不再出现在番剧页 |
| 数据 | `POST /v0/search/subjects`（air_date 过滤） | 主用 `api.kazumi.fyi/kazumi/v1/popular/subjects`，失败回退 v0 搜索 |
| 明文 HTTP | 待决策 | **只支持 https 源**，不放开全局明文 |
| Kazumi 播放地址 | 待决策（WebView / 正则） | **先不引入 WebView**（阶段 D 再议） |
| 详情页 | 复用 B 站详情 + 资源匹配 | 新建 Bangumi 详情页，只展示元数据 + 本地追番；资源匹配留到阶段 C/D |
