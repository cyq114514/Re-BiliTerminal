# 弹幕偶发消失 —— 全面排查报告与修复方案

> 排查日期：2026-11-05  
> 范围：`PlayerActivity` 弹幕装载/渲染链路 + `DanmakuFlameMaster` 引擎 + `DanmakuApi` + 弹幕缓存  
> 方式：只读静态分析（主代理逐条复核子代理取证）。**未改动任何项目代码**，未复现真机日志。
> 结论分级：**A=会导致该 P 永久没有弹幕；B=一过性清屏（闪一下又回来）；C=弹幕变少**

---

## 一、结论先行

1. 代码里**唯一能让整屏弹幕瞬间消失的引擎动作是 `seekTo()`**：DFM 的 `SEEK_POS` → `DrawTask.seek()` → `reset()`，把屏幕上所有弹幕实例整批丢掉（`DrawTask.java:226-250`）。所以"闪一下"必然是某次 seek；而"永久没有"是**数据层/装载层**出了问题。
2. 已确认 **6 个会导致"永久没有弹幕"的缺陷**（A0~A6，全部有代码证据），其中 A0、A1 是典型的"偶发"——取决于网络时序与点击速度。
3. 已确认 **4 条会额外触发清屏的路径**（B1~B4），最坏情况用户能看到「1.2 秒内闪两次」。
4. **现有日志无法定位**：`seekDanmakuTo` 全函数零打点；`release/prepare/pause/resume` 零打点；弹幕条数只有 D/V 级（默认不落盘）。所以必须先补埋点，否则改完也无法证明修好了。

## 三、A 类：会导致"这个 P 永久没有弹幕"

### A0（最像"偶发"）迟到的弹幕响应会抢装到新页面上

- 证据：`streamDanmakuOnUi` 回主线程后**不校验 cid / 代际**：
  ```java
  // PlayerActivity.java:2522-2525
  private void streamDanmakuOnUi(final List<DmSegMobileReply> segments) {
      runOnUiThread(() -> {
          try {
              streamDanmaku(null, segments);
  ```
  而切 P 时先 `release()` 并置空，再重新 `findViewById` 拿回同一个 view：
  ```java
  // :4653-4656
  if (mDanmakuView != null) { mDanmakuView.release(); mDanmakuView = null; }
  // :4698
  mDanmakuView = findViewById(R.id.sv_danmaku);
  ```
- 机制：切 P 前发出的新版弹幕请求若在切 P 之后才返回 → 主线程回调时 `mDanmakuView != null`（已是新页面的 view）→ 用**旧 P 的数据** prepare。DFM 只在 `drawTask == null` 时装载数据（`DrawHandler.java:498-542`），新 P 自己的弹幕随后到达时**被静默忽略**。
- 用户看到：新 P 的弹幕是上一 P 的、数量明显不对，或者干脆很少/空白；重进该 P 又正常。
- 修法：给弹幕链路加**按 cid 的代际守卫**（请求发起时捕获 `cid`，回主线程后 `if (cid != requestCid) return;`），比复用 `switchToken` 更精确，且不受切清晰度影响。

### A1（必现）切 P 后紧接着切清晰度 → 新 P 的弹幕装载被丢弃

- 证据：
  ```java
  // :4708-4710  切P的弹幕加载，60ms 后执行，用 switchToken 守卫
  layout_control.postDelayed(() -> CenterThreadPool.run(() -> {
      if (destroyed || myToken != switchToken) return;
  ```
  ```java
  // :4792  切清晰度第一件事就是把 token 加一
  final int myToken = ++switchToken;
  ```
  而 `switchQuality` 自身**完全不重载弹幕**（`:4785-4847` 无 `downdanmu`）。
- 机制：切 P 已 `release()` 掉弹幕引擎并在 `:4698` 重新拿到 view；此时切清晰度把 token 提升 → 弹幕加载被 return → 没有任何代码再 `prepare` 这个 view。
- 用户看到：这个 P 从头到尾一条弹幕都没有，退出重进才恢复。
- 修法：把"弹幕装载"从 `switchToken` 里拆出来，改由 A0 的 cid 代际守卫控制；切清晰度不再影响弹幕装载。

### A2 空/坏缓存被当成命中，30 分钟内反复复现

- 证据：命中判断只看**段数**，不看条数：
  ```java
  // :2476-2480
  List<DmSegMobileReply> cached = readDanmakuCache(cacheFile);
  if (cached != null && !cached.isEmpty()) {
      streamDanmakuOnUi(cached);
  ```
  `readDanmakuCache` 逐段 `parseDmSegMobileReply(raw)`，不校验 `elems` 是否为空（`:2567-2585`）。
- 机制：写过一次"可解析但 0 条"的缓存（如全空响应体、字段被跳过的数据），之后 30 分钟内每次进入都命中它 → 引擎 0 条 → 整片无弹幕，且已经没有任何网络请求，日志里也没有 W/E。
- 修法：命中时统计 `elems` 总数；为 0 视为未命中，删除缓存并走网络；写缓存时跳过空段。

### A3 旧版回退链路可以产出"null 数据集"，全程无异常无提示

- 证据：旧版把响应**原样**写盘（HTML/404 页面也写），解析失败返回 null：
  ```java
  // :2435-2437
  byte[] decompressBytes = decompress(Objects.requireNonNull(response.body()).bytes());
  bufferedSink.write(decompressBytes);
  ```
  ```java
  // BiliDanmukuParser.java:63-71  catch 之后 return null;
  ```
  ```java
  // DrawTask.java:282-284  接受 null，不抛异常
  danmakuList = parser.setConfig(mContext)...getDanmakus();
  if (danmakuList != null && !danmakuList.isEmpty()) { ... }
  ```
- 用户看到：新版失败自动回退旧版（有一次性 toast），回退后整片无弹幕且再无任何提示（提示位 `danmakuFallbackTipShown` 全程不复位）。
- 修法：写盘/解析前校验内容以 `<?xml`/`<i>` 开头（B 站 XML 弹幕固定格式）；不合法直接判失败，走"获取失败"提示而不是静默空装载。

### A4 引擎"二次 prepare 不生效"

- 证据：`DanmakuView.prepare()` 复用已有 handler（`DanmakuView.java:210-222`），`DrawHandler.prepare()` 在 `drawTask != null` 时只执行回调、**不重新装载弹幕**（`DrawHandler.java:497-543`）。
- 影响：任何"同 view 再 streamDanmaku"的路径都静默无效。当前具体有两处：播放错误重试（`:2921-2950`）只重建播放器、不重载弹幕；将来任何增量补拉弹幕也会踩这个坑。
- 修法：`streamDanmaku` 入口若 `mDanmakuView.isPrepared()`，先 `release()` + 重新 `findViewById` 再 prepare；重试路径补一次弹幕装载。

### A5 分段"空即停" + 时长估算固定 3600 秒

- 证据：
  ```java

  } else {
      Logu.d("新版弹幕API", "分段 " + (i + 1) + " 为空，停止获取");

  ```

### A6 `hasDanmaku` 只在 onCreate 定一次（加固项）

- 证据：`:532` 唯一赋值点（除本地视频失败分支）；切 P 后 `danmaku_url` 在 `:4663` 被覆盖但 `hasDanmaku` 不重算。
- 影响：本地/异常入口下 `danmaku_url` 为空时，后续 `start/pause/seek` 全部空转（`seekDanmakuTo` 第一行 `if (!hasDanmaku) return;`），且 `downdanmu` 的空地址分支**没有任何日志**（`:2415`）。当前在线视频路径 `PlayerApi` 一定会写 danmakuUrl，故概率低，但属于必须加固的不一致。

## 四、B 类：一过性清屏（"消失一下又回来"）

| 编号 | 触发 | 证据 | 用户可见 |
|---|---|---|---|
| B1 | 落点校正窗口被自己续期 | `seekDanmakuTo` 每次都 `danmakuLandingCheckUntil = now + 8000`（`:4135`），而纠偏宽限只有 1200ms（`:4226`）、上限 2 次（`:4231`） | 一次用户 seek 后，最坏在 1.2s / 2.4s 各再清一次屏 |
| B2 | 卡顿 seek 也会续期窗口 | 卡顿分支调用同一个 `seekDanmakuTo`（`:4215`） | 卡顿 → seek 清屏 → 8s 内再叠 1~2 次落点清屏 |
| B3 | `prepared()` 无条件 seek | `:2723-2728` 只要 `anchor > 0` 就 seek | 弹幕比视频晚到时，用户先看到没弹幕，随后"弹幕出来→立刻被清→重新出现" |
| B4 | 互动题暂停只停播放器不停弹幕 | `:5013-5017` 只有 `ijkPlayer.pause()`，没有 `mDanmakuView.pause()`，也不置 `userPaused` | 思考十几秒再继续 → DFM 时钟已跑远 → 极端偏差兜底（`:4278-4280`）3 秒后 seek 清屏一次 |

附带两处稳定性隐患：
- `cancelAllTimers()` 用 `mainHandler.removeCallbacksAndMessages(null)`（`:3536-3537`），会撤销尚未执行的 `isSeeking=false`，标志可能永久卡 true → 整场不再纠偏（漂移不修，属于"错位"不是"消失"）。
- `mDanmakuView` / `hasDanmaku` / `isSeeking` 都是**普通 boolean/字段**，在 Timer 线程读、主线程写（`:194-195`），存在可见性与竞态（`seekDanmakuTo` 判空后再次解引用）。

## 五、C 类：弹幕变少（不是"消失"，但容易被误判）

1. **类型被丢**：`BiliProtobufDanmakuParser` 丢 `mode 7/8`（`:118-120`），`DanmakuFactory.createDanmaku` 只支持 `1/4/5/6/7`（`DanmakuFactory.java:153-171`）→ **mode 2/3（老式滚动）与 9（BAS）全部被丢弃**，两条路径（新版 protobuf、旧版 XML）同病。
2. **防重叠过滤**：`player_danmaku_allowoverlap` 默认 `true` 传给 DFM 是"会撞就丢"语义，加上 `maxLines=15`（`:2692-2698`），高密度段落会被引擎二次丢弃。
3. 单条解析异常静默丢（`BiliProtobufDanmakuParser.java:160-163` 只 `printStackTrace`，不进 `app-log.txt`）。

## 十、按用户复现信息修正结论（2026-11-05 追加）

用户实测口径：

1. 消失后**不会自己回来**；
2. 消失前**只是放着播放**，没有拖动/双击/切P；
3. **开关一次弹幕按钮就恢复**。

### 10.1 由此排除的假设

| 被排除 | 理由 |
|---|---|
| A2 空缓存命中、A3 旧版解析出 null、A5 分段全空 | 这些是**数据层为空**，`seekTo/show` 不可能让弹幕回来——数据在 `danmakuList` 里根本没有。开关弹幕能恢复 ⇒ 数据是好的。 |
| B1/B2/B3 纠偏 seek 清屏 | 那是一次性清屏，下一帧就重建，不可能"不回来"。 |
| A0 迟到响应抢装 | 表现为弹幕内容/数量不对，不是空白，且开关按钮也不会修复数据。 |

### 10.2 收敛后的三种可能（都在"引擎状态机"层）

| 代号 | 状态 | 机制 | 开关按钮为何能恢复 |
|---|---|---|---|
| **E1 停摆** | `quitFlag=true`（PAUSE 之后没有 RESUME） | DFM 更新线程退出，画面停在最后一帧；若那一帧刚好没有弹幕，就是整屏空白 | 开关 → `show()` 画一帧 + `seekDanmakuTo()` → `SEEK_POS` → RESUME 重启更新线程 |
| **E2 隐藏** | `DrawTask.mIsHidden=true` | `drawDanmakus` 直接 `return`（`DrawTask.java:315-317`），**任何 seek 都画不出东西**，只有 `requestClear()`（show 路径）才会清掉 | 开关 → `show()` → `SHOW_DANMAKUS(null)` → `drawTask.requestClear()` → `mIsHidden=false`（`DrawTask.java:358-361`） |
| **E3 时钟停** | timer 不再推进但线程活着 | 渲染窗口 `[t-4s, t+4s]` 卡在无弹幕区间 | 同 E1，seek 会重建 `mTimeBase` |

### 10.3 能造成 E1/E2 的具体代码路径（待日志验证）

1. **缓冲暂停后没有 END**：`BUFFERING_START` 里 `pause()` 且只在 `isPlaying` 为真时置 `danmakuPausedByBuffering`（`:1709-1712`）；`playerPause()` / `playerResume()` 都会把这个标记清零（`:3177`、`:3195`）。任何让标记在 END 之前被清掉的路径，都会留下"引擎已暂停、标记已丢" → E1。
2. **听视频模式**：进入时 `pause()`（`:4362`）且把 view 设为 `GONE`（`:4425`）；DFM 的 `resume()` 在 view 不可见时只重试 4 次（约 650ms）就永久放弃；退出时只恢复 `VISIBLE`（`:4441-4443`），**没有再 resume/show** → E1。
3. **按钮被隐藏的老人机设置**：`player_ui_showDanmakuBtn=false` 时走 `:1823-1827` 分支，只同步状态位、不执行 `show()`；若 DFM 因任何原因处于隐藏/停摆，就再没有恢复入口。
4. **E2 的入口只有 `hide()`**（`:1805`，唯一调用点）。当前只有按钮点击会触发，需日志确认是否出现过非用户点击的 `hide`。

### 10.4 建议动作（两阶段）

**阶段 A（先做，可直接缓解 + 取证）**

1. 埋点（W 级，默认可见）：`pause/resume/hide/show/start/seek(来源)/prepared(引擎条数)/release` 全部打一行，附 `isPlaying/userPaused/isSeeking/isDanmakuVisible/pausedByBuffering`。
2. 5 秒心跳：`video_now`、`mDanmakuView.getCurrentTime()`、`isPrepared()`、上述状态位。**一条日志就能区分 E1（时钟不走）/E2（时钟在走但屏幕空）**。
3. 自愈看门狗（与心跳同一处）：当 `isPlaying && isDanmakuVisible && hasDanmaku && mDanmakuView.isPrepared()` 且**弹幕时钟连续 3 秒没有前进**而 `video_now` 在前进 → 自动执行 `show() + seekDanmakuTo(video_now)`，60 秒冷却、每视频最多 5 次。这一条能把"必须手动开关弹幕"变成自动恢复，并且日志会记录触发了哪一类。

**阶段 B（拿到 1 次日志后，按根因做最小修复）**

- 若是 E1 且日志显示 `BUFFERING_START` 后无 `BUFFERING_END`：改为"以弹幕时钟是否停住"为准的恢复条件，不再依赖配对标记。
- 若是 E1 且出现在听视频退出：退出时补 `resume()/show() + seek`。
- 若是 E2：把唯一 `hide()` 调用点加上调用来源日志，定位是谁触发的；同时给 `hide` 加"只在用户点击时执行"的防护。
- 时钟停（E3）：在 seek 前先 `setVisibility`/`prepare` 校验，必要时 release + 重载（复用 A4 的重建逻辑）。
