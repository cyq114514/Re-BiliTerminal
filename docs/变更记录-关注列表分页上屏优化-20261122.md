# 变更记录：关注列表分页上屏优化（2026-11-22）

## 0. 背景

手表 `app-log-6.txt` 的掉帧日志显示：FollowUsersActivity 5 秒内 38 段卡顿（最长 617ms/14 慢帧），
占全部卡顿时长的 69%，且每段都紧跟 `x/relation/followings` 分页请求之后。
`RefreshListActivity:53` 已 `setItemAnimator(null)`，插入动画不是原因。

## 1. 改动（方案 A，三项中的两项）

| 项 | 改动 | 说明 |
|---|---|---|
| 1 | `UserListAdapter` 头像改走 `GlideUtil.requestRound` | 与 `ElectricUserAdapter` 同一条路径：宿主判活 + `url()` 拼接 + circleCrop + transition + RGB_565；原实现每项新建一份 RequestOptions，且用 Application context 不随页面销毁取消 |
| 2 | `userDesc.setSingleLine()` 去抖 | `setSingleLine` 每次都 requestLayout；原来每次 bind 都切一次，现在只在 `hasAvatar` 变化时切。状态按布局实际 `maxLines` 初始化，兼容复用本 Holder 的 `cell_up_list` |

**未做**：`ThemeApplier.apply(holder.itemView)` 原计划从 `onBindViewHolder` 移到 `onCreateViewHolder`。
检查发现 `UpListAdapter extends UserListAdapter` 只重写 `onCreateViewHolder`、复用父类 bind，
移走会让 `cell_up_list` 在非默认主题下漏掉主题应用；且默认主题下 `apply()` 首行就 return，本来零成本。
按最小改动原则剔除。

## 2. 验证

- 编译：`:app:compileDebugJavaWithJavac` 通过，lint 0 条。
- 真机（PJZ110）覆盖安装后进入关注列表：圆形头像、昵称、签名、列表渲染正常（截图见
  `~/Desktop/bili-jankmonitor-verify-20261122/follow-list-check.png`）。
- **效果未达预期**：手机上分页 `pn=2/3/4` 之后仍有 `66ms/1 帧`、`111ms/3 帧` 的卡顿段，
  与改动前同量级。说明这两项不是分页卡顿的主因，主因更可能是
  「20 条一次性插入的布局 + 头像解码峰值」。
