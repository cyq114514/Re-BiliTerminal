## 一、播放器

### R1（P0）双击手势互相触发：缩放 / 快进 / 暂停 / 恢复原大小抢同一次双击

**原文（三条合并，指向同一个问题）**：
> （2026-11-21 用户口述）那开启视频缩放功能后双击，本来我开启了优先恢复原来大小，但是双击后有时他会乱动，这能优化吗
> （S_sans_B，评论）双击单指缩放时会同时触发其它双击手势（我忍它很久了）
> （S_sans_B，评论）你在打开双击快进快退之后播放视频，然后在靠右边单指缩放就懂了（缩放和快进会同时触发，中间的话就是缩放的同时暂停）

**定性（已定位到机制层）**：一次双击目前最多被 **三个** 消费者处理，且阈值各不相同：

1. **Quick scale（双击后拖动缩放）**——这是新版 Android `ScaleGestureDetector` 自带的行为，
   工程里的副本在 `ScaleGestureDetector.java:110-113` 对 `targetSdk > 18` **无条件**
   `setQuickScaleEnabled(true)`；`:262-274` 里双击一发生就进入 `ANCHORED_SCALE_MODE_DOUBLE_TAP`，
   之后同一次触摸的纵向拖动被解释成缩放。也就是说：**只要开了「视频缩放」，双击本身就变成了
   「双击启动缩放」**，第二下手指稍微抖一下，缩放就从 1.0 被拉走。
2. **双击快进/快退/暂停**——`PlayerActivity.java:892-942` 的独立 `GestureDetector`：
   中间 40%×40% 区域复位或暂停（`:905`、`:915-920`），左右区域 seek（`:924-937`）。
3. **老的双击=连点两次**——`PlayerActivity.java:1080-1089` 的 `OnClickListener` 走 `clickUI()`，
   `:1119-1137` 再用「300ms 内两次点击」判一遍复位/暂停；`:1085` 另有 400ms 的屏蔽窗口。

后果分三种，正好对上三条反馈：
- **「双击后有时乱动」**：第 2 步把 scale 复位成 1.0、位置复位到 `video_origX/Y`（`:906-914`），
  紧接着第 1 步的 anchored 缩放还在同一条事件流里，手指离屏前的小幅移动把画面又缩放出去；
  两个动作的时间差取决于点击间隔和手指抖动，所以是「有时」。
- **「双击单指缩放同时触发其它双击手势」**：第 1 步与第 2、3 步对同一次双击都返回 true。
- **「右边缩放同时快进、中间缩放同时暂停」**：双击落点只要不在中间 40% 区域（`isDoubleTapCenter`，
  `:1349-1359`），第 2 步就走 seek/暂停，与第 1 步的缩放叠加。
- 另有放大器：单指移动**没有 touch slop**，`:979-993` 里任何 `deltaX/deltaY != 0` 都直接
  `videoMoveBy()`（`:3620`），双击第二下的微抖会把画面挪一点；直到位移超过 5px 才置
  `gesture_moved`（`:3644`），但位移已经生效了。

**方案方向**：
- **双击只留一个决策点**。二选一：A. 关掉 quick scale（`setQuickScaleEnabled(false)`），双击只归
  player 管；B. 保留 quick scale，则双击不再承担复位/暂停/快进。不能两套并存。
- 复位做成「吞掉本次手势」：复位时置一个到 `ACTION_UP`（或下一次 `ACTION_DOWN` 之前）的屏蔽标记，
  同时打断正在进行的 anchored scale 流，避免复位后又被拖走。
- 删掉 `clickUI()` 里的第二套双击判定，统一由 `GestureDetector` 负责（含双击快进未开启时的回退路径）。
- 单指移动加 `ViewConfiguration.getScaledTouchSlop()`：不达阈值不移动画面。
- 建议补一条回归用例（可写进现有 `app/src/androidTest`）：放大 2.0 → 双击中间 → 1 秒内
  `scaleX/Y == 1.0` 且 `getX/Y == video_origX/Y`；双击落点左右 1/4 处只 seek、缩放不变。

**待澄清**：「优先恢复原来大小」的期望语义是「**任何**双击都先复位」还是「只有中间双击才复位」？
现在代码只认中间 40% 区域，落在两侧仍然是 seek——这本身也是「有时乱动」的一部分。

## 二、缓存 / 下载

### R2（P1）缓存音频后离线没有歌词：歌词要随缓存一起落盘

**原文（2026-11-21 用户澄清）**：
> 听歌模式缓存音频之后无法像联网时候一样加载歌词，需要缓存的时候把歌词也缓存下来，方便无网的时候使用。

**定性（已定位，两个断点叠加）**：
1. **本地条目根本没有 cid**：缓存页把文件扫成 `VideoCard` 时只填 `localPath`（`LocalListActivity.buildAudioItems`），
   `AudioPlayerActivity.ensureLyrics` 第一行 `item.cid <= 0` 就直接 return——整条歌词链路没启动，
   不只是“联网失败”。
2. **两条歌词来源都要联网**：B 站 CC 字幕（要 cid）和网易云兜底；24h 缓存按 cid 存、有 TTL，
   本地条目没有 cid，命中不了，断网后也无源可取。
   另外原实现 `durationMs > 0` 才提交网易云任务，本地条目拿不到时长，兜底直接不发生。

**方案（本轮已实施）**：
- **下载时落盘**：仅音频下载完成后，在后台取一次歌词（B 站字幕优先、网易云兜底），写到条目目录
  `<缓存文件夹>/lyrics.json`（多P 各自的分P目录）。时长取自取流结果（`PlayerData.durationMs`）；
  时长未知也允许网易云按标题匹配（`bestMatch` 对未知时长给中性分）。失败静默，不阻塞下载队列。
- **播放时离线优先**：`LyricProvider.readLocal/load/readCache` 先读同目录 `lyrics.json`（无 TTL），
  再走 24h 网络缓存与在线来源；`ensureLyrics` 不再要求 `cid > 0`，本地条目用 media 路径做单曲身份，
  命中本地文件时直接出歌词、不闪「加载中」。
- **老缓存兜底**：本地没有歌词但能联网时，播放/预取会取一次并回写 `lyrics.json`，
  下次离线就有；下载时已写入的文件不会被后续网络结果覆盖。
- **单测钉住契约**（`LyricProviderLocalTest`，5 条）：JSON 往返、已有文件不覆盖、空歌词不落盘、
  本地/在线身份 key 区分、无文件返回 null。

**已知限制**：
- 下载时完全无网、或 B 站/网易云都没搜到，就不会写文件（联网播放一次会补上）。
- 本次改动前已经缓存好的音频没有歌词文件，需要联网播放一次（或重新下载）才补齐。

**验证**：`:app:testDebugUnitTest` 含新增 5 条 PASS；离线实机（飞行模式 + 缓存音频听歌）**NOT RUN**，需真机。

## 三、私信 / 消息

### R9（P1）私信页 hint 跑马灯没盖满输入框 + 三个控件不等高（4.4/6.0）

**原文**：
> 在安卓4.4安卓6.0设备上测试均发现这个私信页他跑马灯没有完全覆盖住输入框
> 右边会留下一点点空隙，并且这三个按钮不等高

**定性（已定位）**：`activity_private_msg.xml` 的 hint 覆盖层 `MarqueeTextView`（`:167-187`）
同时设了：
- `alignEnd/alignRight="@id/msg_input_et"`，又设了 `layout_marginEnd="4dp"` 和
  `toStartOf="@id/more_btn"`；而 EditText 自己也带 `marginEnd="4dp"`（`:150`）。
  `alignEnd` 对齐的是对方的**边界**、不会继承对方的 margin，覆盖层又自带 4dp → 右侧空隙叠加成 8dp。
- 高度：输入框 `minHeight 38dp`（`:155`），`more_btn`/`send_btn` 都是 44dp（`:192`、`:206`）→ 不等高。

**方案方向**：覆盖层只保留一套定位（`alignStart/Top/Bottom` + `toEndOf`，去掉自带的 `marginEnd`），
或直接把 hint 交给 `TextInputLayout` 级别的统一容器；三个控件统一 40dp 或统一
`alignTop/alignBottom` 撑满输入行。

**验收**：4.4/6.0 各截一张图，右侧无缝隙、三控件等高（正好可复用云端多屏 UI 冒烟）。

**原文（三条合并）**：

**方案方向**：跳转时按 aid 补拉一次置顶评论并插到列表头；或直接复用详情页评论区的初始化路径

### R8（P2）Android 4.4 部分 UI 不跟随主题色

**原文**：
> 首先在安卓4.4上还是有部分UI还是不会根据主题自动更换颜色

**定性**：主题色是「`ThemeApplier.apply(root)` 白名单 + 精确值守卫」的 R1 方案
（见 `docs/decisions-theme-color.md` 结论 7）。默认主题下整体直接 return，零开销，
但代价写得明明白白：**Adapter 行内布局、对话框、Fragment 需要在其创建/绑定处显式调用**。
漏调用的位置在默认主题下完全无感，只有换主题才暴露 → 用户看到「部分不跟随」。

**方案方向**：补 apply 调用点（Adapter `onBindViewHolder`、Dialog `show`、Fragment `onCreateView`）；
整理一份「主题色覆盖自检表」方便以后加控件时对照；低版本不涉及 Material overlay 差异，无需按 sdk 分支。

**待澄清**：具体是哪几处控件（用户只说「部分 UI」）。拿到一张换主题后的截图就能定位。

### R12（P1）sdk21 收藏界面 UI 遮挡

**原文**：

### R13（P2）sdk21 投币/收藏后的图标显示异常

## 五、导航

### R10（P1）短视频按返回退出后，右滑在菜单页与短视频页之间无限循环

**原文**：
> 发现在短视频界面用返回键触发退出后，右滑会无限循环菜单页和短视频页

**定性（三处语义各自成立，串起来成了乒乓）**：
1. 短视频返回键 → `handleBack()` → `exitToMenu()`（`ShortVideoPlayerActivity.java:163-192`），
   用 `menuClick` 把 `MenuActivity` **盖在短视频页上**、不 finish（注释明确写了「不能 finish」的原因：
   裸 finish 会回桌面）。
2. `MenuActivity` 继承 `BaseActivity`，右滑返回 = 关闭菜单 → 露出下面的短视频页。
3. 短视频第 0 页的右滑被 Activity 自己解释成「回菜单」（`:196-242`，阈值 20% 屏宽）→ 又盖一层菜单。

于是「右滑」在两个页面之间轮流制造新的可返回层，永远退不出去。

**方案方向**：定义唯一返回链，任一层不允许右滑再压出新层。本轮选 **B/A 组合**：
`exitToMenu()` 拉起菜单后**立即 finish 短视频页**，恢复本 App 其它页面的扁平模型——
菜单是首页，退出短视频就离开这一页，菜单关闭即离开 App。

**已接受的代价**：这推翻了 1.3.3「关菜单回到短视频」的行为（当时的反馈是“关菜单退到桌面”）。
两条反馈在栈语义上互斥：只要短视频还留在菜单下面，两个页面就互为“上一级”，无论返回键还是右滑都会循环。
本轮以“不循环”为准。若更想保留「关菜单回短视频」，另一条路是给菜单加一次性出口标记：
菜单关闭时同时 finish 短视频（同样以退到桌面收尾），但能保留“返回键拉出菜单后，菜单再返回回到短视频”的中间态；
需要产品确认后再换。

**验收**：短视频 → 返回（出现菜单）→ 右滑（到首页，不再回到短视频）→ 再右滑不再出现循环；
短视频第 0 页右滑仍能回菜单（若保留该语义）。

## 六、新功能

### R6（P2）音乐播放器「锁屏模式」

**原文**：
> 音乐播放器加一个锁屏模式，软件内屏幕黑屏，中央显示时间和电量并保持屏幕常亮，滑动解锁锁屏模式
> （今天自习课偷偷听歌时发现的，我的手表熄屏自动断网，必须保持常亮才能联网，之前一直听缓存）

**定性**：现有 `AudioPlayerActivity` 是常规播放界面，没有常亮/黑屏形态。用户环境事实很关键：
**手表熄屏会断网**，所以「听在线歌」必须靠应用内常亮维持，这跟手机上的省电直觉相反。

**方案方向**：
- 全屏纯黑覆盖层 + 居中时间/电量（跟系统时钟对齐，`ACTION_TIME_TICK` 或 30s 刷新）；
- `FLAG_KEEP_SCREEN_ON`（退出/解锁时清掉，别把用户屏幕常亮带到别的页面）；
- 滑动解锁：沿用项目「右滑 = 返回」的既有语义，或上滑；解锁后回到播放页同时取消常亮；
- AMOLED 防烧屏：时间位置轻微漂移（可选，待确认是否要）；
- 锁屏模式下仍要能切歌/暂停（物理键或双击区域），否则手表上没法操作。

**验收**：手表实机锁屏模式 10 分钟不断网、不熄屏；滑动解锁回播放页；退出后屏幕常亮关闭。
