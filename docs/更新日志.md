# 1.3.1：第三方番剧播放源体系（2026-11-06）

> **已发版**：`versionCode 20261107` / `versionName 1.3.1`。以下改动已通过用户 2026-11-06 真机手动验收，并同步进应用内「设置 → 关于 → 历史更新日志」（`UpdateLog.java`）与 GitHub Release 说明。
>
> 相关文档：方案与审计 `docs/audit/第三方播放源-移植方案-20261106.md`、番剧中心审计 `docs/audit/番剧中心-升级审计-20261106.md`、逐轮测试与排障记录 `docs/测试流程-第三方播放源-20261106.md`、界面规范 `DESIGN.md`。

## 一、做了什么（用户视角）

- 番剧分区新增独立第三方播放能力：从 Bangumi 番剧卡片出发，搜可用站点 → 选线路 → 选集 → 用现有播放器播；B 站原有播放链路、进度、弹幕完全不受影响。
- **开箱即用**：内置一份常用源快照（63 条 `web-selector`），首次启动自动导入，装好即可搜番，不必先找订阅地址；源管理页新增「恢复默认源」。
- 可导入 Animeko Selector 订阅、启停数据源、查看状态、解除临时跳过；默认只搜前 24 个健康源，可一键「搜索全部源」。
- 常规搜索里补 B 站没有的番剧（Bangumi 卡片），点进卡片再嗅探第三方资源，不把站点原始结果混进 B 站列表。
- 第三方番剧支持弹弹play 弹幕（审核通过后的 AppId/Secret 实测可用），播放失败自动屏蔽坏线路并可一键恢复。
- 番剧分区所有页面点标题栏返回（顶级主页返回导航菜单）；推荐/动态刷新按钮改为始终半透明灰卡片，加载中不再高亮。

## 二、审计结论与方案取舍（为什么不是照抄）

| 结论 | 依据 |
| --- | --- |
| RE 公共仓库**没有**第三方播放源实现，番剧换源在被 gitignore 的 `private/` 私有仓库 | `readme.md` 明确「公开构建不含这部分实现」；`OptionalFeatures.kt` 全是 `Class.forName` 反射转发 |
| 从 RE 借鉴的是**交互约定**（点播接管、解析进度文案、失败提示指向手动选源），不是代码 | 逐方法追踪 `OptionalFeatures.kt` / `PlayerActivity.kt` |
| Animeko Selector 取流依赖 **WebView 拦截网络请求**，纯 HTTP 正则不等于上游行为 | `WebVideoMatcher.kt`、`SelectorMediaSourceEngine.kt`、`WebViewVideoExtractor.android.kt` |
| **不存在统一的 Animeko 在线解析 API**；线上只有静态订阅清单 | 实测 `dist/online.json`：63 条全部 `factoryId=web-selector` / `version=2`，60 条 https、3 条 http |
| 纯 HTTP 走到播放页常拿不到直链（MacCMS `player_aaaa` 有 `encrypt=1` 自定义加密） | 抽样站点实测：搜索/详情/播放页均 200，但 m3u8/mp4 命中 0 |

**实际支持的数据源类型**：Animeko `web-selector` 订阅格式的**纯 HTTP 解析子集**（规则里的搜索页/详情页/线路/剧集/匹配视频的 selector 配置）。
**只是预留、未实现**：RSS 数据源、JSON API 数据源、Animeko 在线资源服务接口、完整两层嵌套与 WebView 拦截等价能力（`WebViewSniffer` 有开关但默认关，手表 WebView 可用性未验证）。
**只支持 https 源**（不动全局明文策略）；3/63 条 http 源不可用。

## 三、架构与调用链

```
番剧分区「源」入口 / Bangumi 详情页「播放来源」/ 常规搜索 Bangumi 卡片
  → SourceMatchActivity（Bangumi 标题 → 并发搜站点 → 相关性过滤）
  → SourceDetailActivity（线路 + 剧集，过滤坏线路、按上次成功排序）
  → 点一集 → ThirdPartyPlayback（1 条起步，2s 补第 2 条，首条成功即起播）
  → MediaResolver（player_aaaa → HTML 直链 → 一层嵌套页 → WebView 嗅探）
  → MediaUrls 强校验（path 必须以 .m3u8/.mp4/.mkv/.flv 结尾，挡「假直链」）
  → LocalHlsProxy（仅加密 HLS：改写 m3u8 → loopback）
  → PlayerData(TYPE_THIRD_PARTY) + 白名单请求头
  → PlayerApi.jumpToPlayer(forceBuiltInPlayer=true)
  → 现有 PlayerActivity（ijkPlayer + DFM 弹幕），进度/弹幕均不走 B 站链路
```

分层：`Anime UI → SourceManager / SourceStore / SourceSubscriptions → ThirdPartySource(AnimekoSelectorSource) → MediaResolver / HtmlVideoScanner / MacCmsPlayer / WebViewSniffer → 统一模型 → 现有播放器`。具体站点逻辑不进 UI 与播放器。

## 六、播放流程与失败处理

- 解析：`MediaResolver` 按「剧集自带直链 → `player_aaaa` → HTML 属性/脚本/绝对地址 → 一层嵌套页」顺序，命中后按 `.m3u8 > .mp4 > .mkv > .flv` 挑最好的一条；页面 URL 改投嵌套候选，绝不当直链。
- 播放地址：白名单请求头（`Referer/User-Agent/Origin/Cookie/Accept*`）经 `SourceMedia.headersForIntent()` 扁平化 → `PlayerData.extraHeaders` → Intent `headers` → `PlayerActivity` 解码；为空时仍走原 B 站头逻辑，B 站行为字节不变。
- 第三方播放**强制内置播放器**（外部播放器拿不到请求头）。
- 失败：`PlayerActivity` 的 ijk `onError` 输出 `ijk-err` E 级日志（含地址摘要，不输出 query/token），并把线路 ID 回传 `SourceChannelHealth` 自动屏蔽；选集页给「恢复 N 条」入口。
- 加密 HLS：`HlsPlaylist` 改写 `#EXT-X-KEY` 的 URI 与全部分片到 `http://127.0.0.1:<port>/f/<token>`，`LocalHlsProxy` 只绑 loopback、按 token 白名单转发并带原始头；ijk 因此从不支持的 `crypto+https://host:9999` 变成 `crypto+http://127.0.0.1`。项目里已有 `AudioCacheProxy` 同款路径，`network_security_config.xml` 早已放行 127.0.0.1 明文。

## 改进：用户主页「TA 的投稿」的搜索栏随列表一起滚动，不再焊死在顶部

- 原来：空间内搜索栏是列表上方的一条独立横条（`fragment_user_video.xml` 里 `LinearLayout` 的固定子项），列表怎么滑它都钉在最上面，还长年白占一条约 46dp 的高度。
- 现在：根布局换 `CoordinatorLayout` + `AppBarLayout`，搜索栏作为 AppBar 的子 View 标 `app:layout_scrollFlags="scroll|snap"`，列表区套一层 `app:layout_behavior="@string/appbar_scrolling_view_behavior"` 的 `FrameLayout` 装 `fragment_simple_refresh`；上滑时搜索栏按滚动量 1:1 跟着列表移出屏幕，滑动回顶部再出现。
- 为什么加 `snap`：只写 `scroll` 时手指停在半途松手，AppBar 会长期停在「半收起」，视频卡片会从半透明的搜索栏底下透出来。`snap` 让它在滑动结束时归位到「全展开/全收起」。
- 为什么不用「把搜索栏塞进 RecyclerView 当 header」：① 该列表横屏走 `CustomGridManager(3)`，header 只会占一格，得再补 `SpanSizeLookup`；② 空态是靠基类 `showEmptyView()` 把 `recyclerView` 设 `GONE` 上屏的，搜索栏进了列表就会在「没搜到相关稿件」时一起消失，用户改不了关键词。
- 与 `activity_bangumi.xml`（番剧页签/筛选栏）同一套做法，保持一致；AppBar 透明底 + `elevation=0` + `liftOnScroll=false`，不切断氛围背景，也不出现阴影横条。
- Java 侧零改动：`UserVideoFragment.initSearchBar()` 仍按 id 取 `keywordInput` / `sortButton` / `searchButton`，搜索、排序、翻页、空态逻辑全部不动。
- 验证：`assembleDebug` 与 `assembleRelease` 均通过；release 包 `apksigner` 验签 SHA-256 `8557d314…78ae9e75`（与线上同一把钥匙）；版本号未改（`versionCode 20261106` / `versionName 1.3.0`），同签名 `adb install -r` 覆盖安装成功；滑动表现经用户真机复测通过。

## 改进：收藏夹多选点选不再整表重绑

- 原来：`VideoCardAdapter.toggleSelected()` 每点一次就 `notifyDataSetChanged()`。收藏夹多选管理下勾一条，整表所有卡片都要重新 `onBindViewHolder`（封面、标题、UP、播放量全部重走，封面还会再走一次 Glide 取图）。
- 现在：先按 aid 在 `videoCardList` 里定位；命中且唯一时只 `notifyItemChanged(position)`；同一 aid 出现多次、已不在列表里、或列表为 null 时退化为原来的全量刷新，视觉结果与改动前一致。
- 为什么按 aid 反查而不用 `getAdapterPosition()`：点击回调触发时 position 可能已因插入/删除过期，按 aid 查才不会刷错行。`aid` 在收藏夹条目上唯一，退化分支只作兜底。
- 未验证：低端机/手表上的实际掉帧改善量没有测，只有编译与代码复核。

## 改进：私信页表情数组不再重复解析

- 原来：`PrivateMsgActivity` 的 `refresh()` 与 `loadMore()` 里，`getEmoteJsonArray(...)` 在 `for` 的条件表达式和循环体内各调一次，N 条新消息要解析同一个 JSON 字段 2N 次。
- 现在：循环外取一次 `JSONArray`，循环内直接 `put`。解析结果与写入顺序完全一致，表情映射行为不变。
- 边界：只把「同一入参的重复解析」提到循环外，没有动分页、`msgSeqno`、去重与 UI 刷新顺序。

## 改进：下载队列不再每条任务重开一次 SQLite

- 原来：`DownloadService` 的 8 个静态方法（`getFirst` / `getAll` / `deleteSection` / `clear` / `setState` / 两个 `startDownload` / `startDownloadBatch`）各自 `new DownloadSqlHelper(...)`，用完立刻 `database.close()`。下载 worker 是「取一条 → 查库 → 下载 → 再取一条」的循环，等于每取一条都重新 open 一次 `download.db`（读表结构、恢复 journal）；`clear()` 里同一连接还被 close 了两次。
- 现在：`getDownloadDbHelper()` 缓存一个 helper 单例（`synchronized` 懒加载；`SQLiteOpenHelper` / `SQLiteDatabase` 本身线程安全），各方法复用同一连接、不再逐次 close，关闭交给进程退出；`clear()` 的重复 close 一并消失。
- 为什么可以常驻：一个 SQLite 连接占的是页缓存（百 KB 量级），远小于反复 open/close 的打开开销；且所有调用点原本就在 `CenterThreadPool` 后台线程，不涉及主线程。
- 为什么不会踩到「复用已关闭连接」：全库检索 `new DownloadSqlHelper` 只剩本文件的这一处单例创建，没有第二个持有者会去 close 它。
- 未验证：没有在真机上做「添加下载 → 暂停 → 继续 → 删除 → 清空」的完整回归，也没有长队列的耗时对比。

## 修复：播放页「跳到指定时间」弹窗闪退（InflateException）

- 现象：播放页点「跳转」直接崩，堆栈为 `dialog_adaptive` 第 24 行 `MaterialCardView` inflate 失败。
- 根因：`AdaptiveDialog` 用 Activity 的 inflater 装载弹窗布局，而播放页主题是 `Theme.NoSwipe`（parent = `android:Theme.Black`），不满足 MaterialCardView 的"必须是 Theme.MaterialComponents 后代"校验。
- 修法：弹窗内容单独套一层 `ContextThemeWrapper(Dialog_Adaptive)`，用 `cloneInContext` 保留 Activity inflater 的 Factory2（AppCompat 控件不被降级）；按钮同样用这个 inflater。看图页等其它非 MDC 主题页面一并受益。

## 修复：背景光晕正中的小黑点

- 现象：手表上背景光晕中心有一个 4px 左右的黑点，会被上层 UI 盖住，手机端不出现。
- 根因：径向渐变的**圆心是数学奇点**，个别 GPU/Skia 实现会在那一像素算出异常色；光晕又经过 1/4 分辨率缓存位图放大，异常像素被放大成可见黑点。
- 修法：把渐变圆心移到屏幕上方之外（`CENTER_Y_RATIO = -0.04`，半径收到 `0.72 × max(w,h)` 补偿亮度），可见区域内不再有像素落在奇点上；同时缓存图改为矩形 + CLAMP 填充（视觉等价，去掉圆形边缘接缝）。

## 修复：列表滑到头时的白色横条（EdgeEffect 颜色）

- 根因：Android 12+ 的 overscroll 拉伸发光取 `android:colorEdgeEffect`，未显式设置时回落到 `android:colorForeground`，本项目是近白色 `#ebe0e2`。
- 修法：`Theme.BiliClient` 与 `Theme.NoSwipe` 显式设成 `@color/card_border_new`，与卡片描边同色。

## 修复：短视频页把调试文字画在画面上

- 现象：短视频页常驻一行「首帧已出 aid=…」，看着像故障。

## 修复：收藏夹列表刷新后崩溃（Inconsistency detected. Invalid view holder adapter position）

- 现象：`FavoriteFolderListActivity`（收藏夹列表）偶发崩溃，堆栈落在 `RotaryRecyclerView` + `CustomLinearManager` 的 layout 阶段，`FavoriteHolder{position=5}`，adapter 为 `FavoriteFolderAdapter`。
- 根因：`loadFolders()` 在 `CenterThreadPool` 后台线程里先 `folderList.clear()` 再 `addAll()`。该 `folderList` 被**旧 adapter 以同一引用持有**，而新数据要等一帧后主线程 `setAdapter` 才生效。这中间 `getItemCount()` 从 N+2 瞬间变成 2，RecyclerView 手里还留着 `position=5` 的 ViewHolder，下一次 layout 立即抛 `Inconsistency detected`。与 1.2.8 修过的本地选集崩溃是同一类“列表变更与 notify 跨线程失序”，只是这次是 `clear()` 而不是 `remove()`。
- 修法：后台线程只负责网络请求，把结果装进临时 List；`folderList` 的清空/写入、adapter 创建或 `notifyDataSetChanged()` 全部收到主线程同一条消息里（`applyFolders`），RecyclerView 看不到中间态。刷新时复用同一个 adapter，不再每次 new。
- 同族隐患一并修（`FavoriteVideoListActivity`）：分页 `loadPage` 原先在后台线程直接往 adapter 持有的 `videoList` 里追加，改为先取到临时表、主线程 `addAll` + `notifyItemRangeInserted`；长按删除的 `aid` 改为在主线程先取，后台不再按下标读列表。
- 验证：`assembleRelease` 通过。**未真机复现**：触发需要“刷新/返回时列表正在布局或滑动”，本地不具备稳定复现条件，等线上或真机再次回归确认。
- 未验证：表冠滚动 + 下拉刷新并发、批量取消收藏后立即刷新的时序未做压力测试。

## 修复：本地选集页删除分 P 后滑动崩溃（IndexOutOfBoundsException）

- 现象：线上 1.2.8 崩溃上报 `Inconsistency detected. Invalid item position 4(offset:4).state:5`（`PageChooseAdapter` + `LocalPageChooseActivity`），滑动列表时崩溃。
- 根因：长按删除时 `CenterThreadPool.run` 后台线程异步执行 `pageList.remove(position)`，主线程却立即 `notifyItemRemoved` + `notifyItemRangeChanged(0, pageList.size() - position)`——数据变更与通知跨线程失序，且通知范围起点错误（应为 `position`）、长度受竞态影响。Adapter 持有同一列表引用实时读 `size()`，RecyclerView 布局状态（5 项）与 Adapter 数据量（4 项）不一致，滑动 `layoutChunk` 时越界。`CustomLinearManager` 只 catch `onLayoutChildren`，滑动路径不经过，兜不住。

- 验证：`assembleRelease` 通过；PJZ110 真机安装测试，logcat 全程无 FATAL/ANR/应用 E 级错误、无「列表报错」、进程零重启。
- 未验证：删除路径不打日志，「删除+反复滑动」以用户手动复测为准。

## 修复：弹幕间歇性消失 + 快进后时间轴不同步（用户反馈第 1 项）

- 现象：弹幕偶尔整体停住不再滚动；快进/快退后弹幕与画面长时间不对齐。
- 根因（代码级，非单一原因，逐条已由源码证实）：
  1. 缓冲恢复只看 `isPlaying`：`BUFFERING_START` 暂停弹幕、`BUFFERING_END` 时若 `isPlaying` 已被其它回调改写就不恢复，弹幕永久停住；且 `DanmakuView.resume()` 在 handler 未 prepared 时会静默丢弃（`DanmakuView.java:385-392`）。

  4. 落点校正连纠 2 次不收敛就 `disableLandingCorrection`，一次误判会让本视频剩余时间全部不再纠偏。
- 修法：缓冲 pause/resume 改为显式配对标记（`danmakuPausedByBuffering`）；`streamDanmaku` 补 `DanmakuView` 判空与一次性失败提示；所有用户 seek 入口统一置 `isSeeking`（1200ms 宽限）；用户主动 seek 时重置落点校正额度；渲染异常不再静默。
- 验证：PJZ110 真机手动验证通过（2026-11-05）：快进/快退、缓冲恢复、暂停恢复、切P 均正常，弹幕不再间歇消失；logcat 无 FATAL/应用 E 级日志。
- 遗留：本次未改 DFM 内部时钟，只保证事件对齐与恢复配对；`getCurrentTime()` 与 `seekTo()` 是否同源仍未单独取证，但原来“恒定超前 41s”的现象在复测中未再出现。

## 新增：听歌快速加载（本地缓存代理 + 竞速探活 + 看门狗）

- 背景：ijkplayer 没有 media3 的 `CacheDataSource`，起播/拖动每次都重新建连回源。真机日志实测：切歌→出声中位 461ms，**最坏 16.2 秒**——坏 CDN 节点上 8 秒读超时 × ffmpeg `reconnect=1` 自动重连两轮才报错。
- **`AudioCacheProxy`（新增）**：在 127.0.0.1 起只服务本进程的 HTTP 代理，ijk 播代理地址；按 Range 先读磁盘缓存、缺的部分回源并边下边存。等价 NeriPlayer 的读穿缓存（`CacheDataSource`），但不换播放器内核、`minSdk` 不变。
  - 只缓存"从 0 开始的连续前缀"：音频几乎总是顺序播放，前缀覆盖"拖回已播位置"的全部场景；跳到未缓存区间退回透传，行为与直连一致。
  - **源站忽略 Range 回 200 时自行跳过前 `start` 字节按 206 返回**——原样透传 200 会让 ffmpeg 从头解码、播放器却按 seek 后的时间轴走，表现就是"声音和进度条对不上"。
  - 上限 80MB + LRU（按最后访问淘汰，正在播的 cid 不删）；连续失败 3 次熔断，本进程回退直连。
- **竞速探活**：`healthOrder` 改为全部候选（最多 4 条）并发探活、**真读 1 字节**、第一个出数据的排第一，上限 1.5 秒（原来只探 2 条、只等 350ms，弱网下探不出结论就盲试第一条）；已知坏地址按**完整 URL** 记入黑名单 10 分钟沉底——真机实测同 host 不同 URL 参数，一条卡 6 秒一条 300ms，只按 host 记没用。
- **起播看门狗 3 秒**：`prepareAsync` 后仍未 `onPrepared` 就主动换线，不再依赖 ijk 自己的 `onError`（实测最坏 15.2 秒）；同时 `reconnect=0` + 读超时收窄到 4 秒（正常 prepare 最慢 1453ms，余量 2.7 倍）。
- **开关与告知**：设置 → 内置播放器设置 → 「听歌快速加载」（默认开）；首次进入听歌模式弹窗说明"最多约 80MB"，可在弹窗里直接关掉；关闭后启动服务时清空缓存目录。

## 新增：听歌进度记忆（同一收藏夹续播）

## 修复：短视频页右划直接退出应用

- 现象：短视频页右划一下，应用直接回到桌面/表盘。
- 根因：`ShortVideoPlayerActivity` 在清单里没写 `android:theme`，继承了应用默认主题 `Theme.BiliClient` 的 `android:windowSwipeToDismiss=true`。这个属性在手表上是**窗口级**右划关闭，由系统直接 dismiss 窗口，**不经过 `onBackPressed()`**——`ShortVideoPlayerActivity.exitToMenu()` 那套"先拉起菜单再 finish"的兜底完全没机会执行；而菜单页在进入时已被 `MenuActivity.killAndJump()` finish 掉，任务栈里只剩短视频这一页，所以一 dismiss 就是回桌面。手机上若走到边缘返回手势，则是第二个坑：`exitToMenu()` 的 `catch` 吞掉异常后**仍然** `finish()`，同样把栈清空。
- 修法：① 新增 `Theme.BiliClient.Fullscreen`（`parent=Theme.BiliClient`，只把 `windowSwipeToDismiss` 关掉），给短视频页挂上，右划不再被系统吞掉；② 页面自己接管右划：`dispatchTouchEvent` 里"第 0 页 + 这一划没翻动 ViewPager + 横向 >20% 屏宽且明显大于纵向 + 600ms 内"才判定为右划，调 `handleBack()` 回菜单（右侧三页的右划仍由 ViewPager 翻回第 0 页，不抢）；③ `exitToMenu()` 拉菜单失败时不再 `finish()`，只提示重试。
- 未改动的行为：返回键逻辑不变（右侧三页 → 先回第 0 页，第 0 页 → 回菜单）；短视频页现在会吃到氛围背景层（`Theme.BiliClient.Fullscreen` 不在 NoSwipe 排除列表里），第 0 页有 `@color/bgblack` 铺底所以无观感变化。

## 修复：高能进度条一直不显示

- 现象：开关打开后进度条上没有任何波形。
- 根因：数据源字段不存在。上一版把数据源从已下线的 `pbp/data` 换成了 `x/player/wbi/v2` 的 `view_points`，但 `view_points` 是「名场面标记」，元素结构是 `{type, from, to, content, imgUrl, logoUrl}`（见 `PlayerApi.ViewPointData`），**根本没有 `score` 字段**；`optDouble("score", 0)` 取出来全是 0 → 归一化时 `maxValue<=0` → `rebuildRenderData()` 把 `renderData` 置空 → `drawHighEnergy()` 第一道判断就 return。也就是说即使接口返回了数据、开关也开着，波形一行都画不出来。
- 修法：数据源改为**本地弹幕密度**——弹幕本来就要下载解析（`streamDanmaku`），按 10s 分桶统计条数即可，语义正是"弹幕越密越热"；不需要登录、不额外发请求、断网也能画。统计点放在 `streamDanmaku()` 里 `createParser()` 之后、`prepare()` 之前（此刻弹幕集合已构建完、绘制线程还没开始遍历它；`Danmakus` 的 `iterator()` 是共享可变对象，播放中从别的线程遍历会互踩光标）。同时删掉已证伪的 `PlayerApi.getHighEnergyViewPoints`。
- 顺带修：波形原来画在 `super.onDraw()` **之前**，被 SeekBar 的 track/progress/thumb 整片压住（手表上 20dp 高的控件里 2dp 折线基本看不见）。现在拆成两半——填充当底色垫在轨道下，折线画在最上层。
- 验证：真机 logcat 已确认统计生效（`本地弹幕密度：条数=1356 桶数=30 步长=10s`，对应一条 300 秒、1356 条弹幕的视频）。

## 修复：返回上级页面后新版 UI 背景消失

- 现象：部分设备上，从「检查更新」返回「关于」页后，氛围背景（粉色径向光晕）消失，整页只剩纯黑。
- 根因：**未在真机确认到唯一触发点**，三条已核实的机制都能造成这一现象：① 背景层只在 `onCreate` 里 `installAmbient()` 装一次，全工程没有 `onRestart`、`onResume` 里也不补装——窗口装饰层一旦被系统摘掉/重建，返回后永远回不来；② `AmbientBackground` 在 `onDetachedFromWindow` 里 `recycle()` 预渲染位图，而该位图仍被硬件加速的 DisplayList 引用，回收后这一层会静默停止绘制，且重新 attach 时尺寸没变、`onSizeChanged` 不再触发，缓存不会重建（只剩"每帧现算渐变"的兜底）；③ 内容层铺不透明底把装饰层整片盖住（1.2.0 修过同类：番剧/表情页底色挡住氛围层）。

- 未验证：具体是三条机制中的哪一条（甚至是不是三者叠加）**没有定位到唯一触发点**；按"任意一条命中都能自愈"加固后，用户真机复测通过（关于 → 检查更新 → 返回，背景未再消失）。

## 性能：批次 1——切页与冷启动的固定开销

全量扫描后按"每次操作都要付、改动小、风险低"筛出的第一批，只动固定开销，不碰业务逻辑。

- **背景层安装不再每次 onStart 做 binder IPC**：`installAmbient()` 增加快路径（装饰层第 0 层已是氛围背景/自定义底图就直接复用，只做两次 `getChildAt`）。原实现每次 `onStart` 都会走 `BackgroundManager.install()`（SP 读 + `getActivityInfo` IPC + `File.isFile` 磁盘 stat）和 `ambientEnabled()`（SP 读 + `getActivityInfo` IPC）——**一次页面打开 2 次 IPC，从任何页面返回都要重付**。
- **主题判定按类缓存**：新增 `noSwipeThemeCache`（key = Activity 类名），`isNoSwipeThemedPage()` 命中即返回。缓存无需失效——唯一会改主题的「新版美学设计」开关是重启应用生效的；查询失败不写缓存，避免一次 `NameNotFoundException`（alias 启动）把某个类永久判死。
- **删掉每次 onResume 的背景诊断日志**：`logAmbientState()` 每次 `onResume` 拼 6 段字符串 + 4 次视图查询，纯诊断、默认配置下无输出，整段移除（该诊断在 1.2.7 定位"返回后背景消失"时已用完，更新日志有记录）。
- **`setRound()` 按视图判重**：圆屏适配的逻辑没变，但同一个 `pageName` 视图只处理一次。`onStart` 每次返回都会调它，原来每次都 `findViewById` + 读 SP + 重设 `LayoutParams`（后者触发 `requestLayout`）。`asyncInflate` 的页面内容晚于首次 `onStart` 才 `setContentView`，视图换了会正常重做。
- **删掉菜单切页时的 `Glide.clearMemory()`**：主线程全量释放位图 + 触发 GC，正好压在切页转场动画上，且返回时整屏图要重新解码。
- **冷启动不再做日志目录探测**：`Logu.setFileLoggingEnabled(enabled, cleanExisting)` 新增重载，冷启动传 `cleanExisting=false` 跳过"为删除历史日志而探测目录"（`ProgressDiag` 的探测是 3 次真实写盘 + 6~10 次 stat，而默认配置下文件日志是关的）。设置页切换开关仍走 `cleanExisting=true`，保持"关掉开关即清理本地日志"的约定。

**审视后没有改的两项（避免为不成立的收益引入风险）**

- `BaseActivity.onCreate` 的 10+ 次 `SharedPreferences` 读取：`SharedPreferencesUtil` 底子是内存内的 SharedPreferences，单次是哈希查找（微秒级），合并读入局部变量属于纯重构，收益不成立。真正的开销在 `setRequestedOrientation`（AMS）与 `getRealMetrics`，而前者一旦按"值未变就跳过"优化，会让新 Activity 继承 `screenOrientation="locked"` 的当前朝向，风险大于收益。
- `VideoInfoFragment` / `BangumiInfoFragment` 点播放前的 `Glide.clearMemory()`：作者原注释写的是"手表内存太小，不清的话播放完回来 Activity 会被释放"，是为避免 OOM 的刻意行为；没有真机 OOM 复现前不删。

**未验证**：冷启动与切页的改前后对照没有采到（本次只测了改后：`am start -W` 三次 1413/903/870ms，无 FATAL）。切页 IPC 的减少是结构性事实（代码路径可数），但帧率层面的收益需要 `gfxinfo` 对照才算证明。

  ```
  13:15:50.707 落点偏差 -41093ms
  13:15:51.210 弹幕同步 diff=-2ms      ← 纠偏后归零
  13:15:52.209 落点偏差 -41038ms      ← 1 秒后又回到 41 秒
  ```
- 根因：偏差**恒定在 41.0~41.1 秒**、不随时间累积，且每次 `seekDanmakuTo` 后立刻归零、1 秒内又复现同量级——说明 `DanmakuView.getCurrentTime()` 读到的时钟与 `seekTo()` 修正的不是同一个源（DFM 内部 `timer.currMillisecond` 与 `uptimeMillis - mTimeBase` 两条路径），落点校正于是变成自激：每 600ms 判一次、每次判中就去 `seek`，而 `DrawTask.seek()` 内部 `reset()` 会把屏上弹幕整片丢掉重铺。
- 修法（只动 `PlayerActivity` 的纠偏分支）：① 宽限期 600ms → 1200ms（DFM 的 seek 要等一次 RESUME 才稳定）；② 单次 seek 会话最多纠 `DANMAKU_LANDING_MAX_CORRECTIONS=2` 次；③ 纠后立刻复现"同号、量级相近"的偏差（`isSameDrift`：差 ≤25% 且至少 1s 容差）就判定"这条偏移 seek 修不掉"，本视频内停用落点校正并打日志；④ 停用后极端兜底也跳过同一条偏移，避免退化成"每 20 秒清一次屏"；⑤ 换视频/换P/换清晰度走 `streamDanmaku` 时自动恢复。
- 效果（真机复测，PJZ110 / 1× 正常播放）：`落点偏差` 从"1 分钟 50 次"降到"单视频 2 次后自动停用"；拖动进度条后只纠 1 次（-971ms）即收敛。1× 下两个时钟增量一致（每 5s 各走 5000±30ms），`diff` 稳定在 ±250ms 内摆动（DFM 计时量化，非漂移）。
- 已知残留：极端兜底在"偏差量级持续变化"时仍会 seek 一次（真机实测 -22.3s 那次清了一次屏）；之后偏差稳定在 -43s 时被 `isSameDrift` 拦住不再清屏。那个 -43s 的离群场景伴随"续播 seek 未生效 + 播放器反复重建"，属独立问题，未在本版处理。

## 修复：相关推荐整页加载不出来（`rcmd_reason` 字段两态）

- 现象：视频详情页从「评论」滑到「相关推荐」是一片空白，没有报错提示。
- 根因：B 站 `x/web-interface/archive/related` 对部分视频（新式大 aid）把 `rcmd_reason` 从对象 `{content,reason_type}` 改成了**字符串**（多数是空串 `""`），而客户端模型只按对象声明。Gson 在**第一条**就抛 `Expected BEGIN_OBJECT but was STRING ... path $.data[0].rcmd_reason`，`GsonUtil.fromJson` 吞掉异常返回 null，`getRelated` 又直接把空列表当成功返回——于是整页空白且全程无痕迹（只剩一行 `GsonUtil` 的 W 日志）。
- 证据：真机 aid=117534531525560，logcat `13:08:55.694 W/GsonUtil>fromJson ... rcmd_reason`；同 aid 直连接口实测 `code=0 条数=40`、`rcmd_reason` 类型为 `str`（前 4 条均为 `""`）。
- 修法：`RecommendApi.RcmdReason` 挂 `@JsonAdapter`，兼容**对象/字符串/null/缺失**四态（字符串直接写进 `content`，空串保持空串——`VideoCard.rcmdReason` 的语义本来就是"空串=没有推荐理由"）；同时 `getRelated` 在解析失败/非 0 code/空数据时补一行诊断日志，不再静默。
- 影响面：`Item` 是首页推荐、热门、入站必刷共用模型，同一个适配器一并生效；已验证对象形态行为不变。
- 验证：Gson 2.8.9 实测三组 JSON（字符串/对象/null 与缺失）解析结果符合预期；真机复测（打开 aid=117534531525560 的相关推荐）留待装包后确认。

**根因**：`PrivacyLockSettingsActivity` 用 `new ComponentName(this, getPackageName() + ".LauncherCalculator")` 拼别名组件名。清单里别名写的是相对名 `.LauncherCalculator`，AGP 按 **namespace** 展开成 `com.RobinNotBad.BiliClient.LauncherCalculator`；而 `getPackageName()` 返回的是 **applicationId** `com.RobinNotBad.BiliClient.re`。两者差一个 `.re`，系统里没有这个组件，真机日志：

```
W/PackageManager: package com.RobinNotBad.BiliClient.re ... call SetEnabledSetting(
    component = com.RobinNotBad.BiliClient.re.LauncherCalculator, 1, 0)
W/System.err: java.lang.IllegalArgumentException:
    Component class com.RobinNotBad.BiliClient.re.LauncherCalculator does not exist in com.RobinNotBad.BiliClient.re

    at PrivacyLockSettingsActivity.applyDisguise
```

异常被 `catch (Exception e) { MsgUtil.err(e); }` 吞掉，只弹一条提示；别名状态没变，`refreshUi()` 又把开关读回 `false`，于是「拨了没反应、开关自己弹回去」。`isDisguiseOn()` 用的是同一个错误名字，所以即使切换成功也会显示为关。

## 2026-10-31 补丁（提交晚于 v1.2.5 标签，实际随 1.2.6 首发）

> 弹幕"出现一会儿→消失→又出现"根因修复 + 高能进度条数据源更换。真机 logcat 实测定案。

### 弹幕：seek 落点偏差导致周期性整层清屏

- **根因**（真机 logcat 实锤，两次会话确定性复现）：ijkplayer 的 seek 落在目标位置前最近的关键帧上并**从关键帧起播**（本工程预编译 native 无 accurate-seek），而 `seekDanmakuTo` 把弹幕对齐到**请求位置**。实测番剧续播历史进度 28000ms 时，播放器实际从 24872ms 起播（`FFP_MSG_*_SEEK_RENDERING_START` 后持续从关键帧走），弹幕整体超前 3.4s；要等 20s 冷却的「极端偏差」纠偏才拽回，**每次纠偏 = DFM seek 清空整层弹幕**。另「检测到卡顿」分支在缓冲期间 DFM 已被正确暂停（时钟没偏）时也照 seek，白清屏（观测到启动期 431ms 的误触发）。手表上网络差/解码慢，两类纠偏高频叠加，表现为"弹幕出现一会儿→消失→又出现"。
- **修法**（只动 `PlayerActivity`）：① `seekDanmakuTo` 打开 8s 落点校正窗口（600ms 宽限期避开 seek 后旧流水线的过时位置），窗口内 tick 实测两时钟差 >800ms 立即按**实际落点**重新对齐，不等冷却；② 卡顿分支 seek 前先实测时钟差，没偏就不纠。
- **效果**：落点偏差的修正延迟从 ~20s 缩到起播后 ~1s 内；无偏差的卡顿不再清屏。

### 高能进度条：数据源 pbp 接口已失效，切换 view_points

- **根因**：`https://bvc.bilivideo.com/pbp/data` 已下线——2026-10-31 实测对 Rick Astley MV、番剧 ep（cid=22742297）、12.8 万弹幕的 av2 全部 404 HTML（带不带 Referer/buvid3 无差别），App 内表现为「开始加载数据→重试 7 秒→未获取到有效数据」。
- **修法**：`PlayerApi.getHighEnergyViewPoints` 改从 `x/player/wbi/v2` 响应的 `view_points`（`{from,to,score}`，秒）取数据，映射为 10s 步长密度数组；与同接口的续播/字幕调用同口径（带 cookie + WBI 签名），不新增端点。**待验证**：匿名请求实测 view_points 恒为空数组，登录态下是否有数据需真机复测（已留诊断日志 `view_points 点数=… 首条=…`）；若登录态下仍为空，则该功能暂无可用数据源，需另行决策（隐藏或等新数据源）。

### 视频评论"别人看不到"：B 站异步审核，发送后如实提示

- **定位**（真机 logcat + 未登录公开接口对照，同账号同视频同时间窗）：
  - Re 版发**视频一级评论（type=1）**：发送返回 code=0 / reply.state=0（服务端当时不打标记），自己端正常展示，但**未登录公开接口查不到**——进异步审核；
  - 同请求发的**动态评论（type=11）立即可见**；同一账号**浏览器发的视频评论 1 分钟内可见**；官方 App 可见；楼中楼有约 1 小时内放行的实例；
  - Cookie 完整性（buvid3/4/b_nut/ticket 全有）与接口路径（与 PiliPlus 同为 `reply/add`）均被对照实验证伪为因素；换 BiliDroid UA + App 标识头（PiliPlus 同款）实测**无法绕过**——判定发生在风控深层。
- **结论**：这是 B 站对非官方渠道视频评论的**异步审核**（先发后审，部分延迟放行），不是发送失败，客户端无法绕过。
- **修法**：发送成功 3 秒后以"他人视角"（无登录凭证、仅带 buvid3 设备标识）复查这条 rpid 是否对外可见（`ReplyApi.checkReplyVisible`，一级查 `reply/main` 时间序、楼中楼查 `reply/reply`），不可见则提示「该评论已提交，B 站审核通过后其他人可见」；复查失败按可见处理不做多余提示。该逻辑自适应 B 站风控策略变化。
- **附带**：诊断期间的 Cookie/响应日志与 UA 实验代码已全部移除，发送行为恢复原样。

## 修复（按严重度）

### 1.【安全】内置播放器/短视频把完整登录 Cookie 发给非 B 站媒体域

- **根因**：`PlayerActivity` 与 `ShortVideoFeedFragment` 在 `setDataSource` 前无条件
  `headers.put("Cookie", CookieGenerator.getCookieString(true))`；而 `upgradeMediaUrlToHttps` 只对
  B 站域升 https，playurl 下发的第三方 PCDN 候选（如 `*.edge.mountaintoys.cn:4483`）原样保留 →
  SESSDATA/bili_jct 直接出站；若该地址是 http，等同于明文过网。
- **修法**：新增 `PlayerApi.mediaHeadersFor(url)` 作为媒体请求头的唯一出口，只有
  `isTrustedMediaHost(url)` 成立时才附带 Cookie；`buildMediaCandidates` 对第三方域只保留 https，
  明文第三方候选直接剔除。播放器与短视频两处改为调用它（与下载链路 `DownloadService` 的
  "非 B 站域不带 Cookie"口径对齐）。
- **验证**：真机起播 1080P（会走 PCDN 线路）正常；见 [审计报告](audit/00-summary.md) P0-1。

### 2.【功能】DASH 解析静默失效 →「仅音频下载」从未可用

- **根因**：`PlayUrlData.dash` 交给 Gson 反射映射，而 `DashData` 的字段名是
  `videoStreams/audioStreams/dolbyAudio/flacAudio`，B 站 JSON 是 `dash.video/dash.audio/dash.dolby/dash.flac`；
  既没有 `@SerializedName` 也没有注册 TypeAdapter，手写的 `DashData.fromJson()` 全仓无调用点。
  结果 `dash` 对象非空但两个列表恒空 → `audioUrl` 恒 null → 清晰度列表里点"仅音频"必然提示
  「该视频没有可用的音频流」，`DownloadService` 的仅音频任务只能退回库里数小时前就过期的 URL。
- **修法**：`GsonUtil` 注册 `DashDataDeserializer`，复用已有的 `DashData.fromJson()`（它同时兼容
  `baseUrl/base_url` 两套命名并正确处理 dolby/flac 嵌套）；`getVideoDash()` 在"dash 非空但音视频流
  全空"时抛 `JSONException`，不再静默成功。
- **验证**：真机选「仅音频」应能下载出 `audio.m4a` 并播放；见审计报告 P0-2。

### 3.【崩溃】头像上传按原图全尺寸解码，OOM 必崩

- **根因**：`EditProfileActivity.uploadAvatar` 直接 `BitmapFactory.decodeStream` 无采样，
  一张 12MP 照片的 ARGB_8888 位图约 48MB；外层只 `catch (Exception)`，而 `OutOfMemoryError` 是 Error。
- **修法**：新增 `ImageApi.prepareAvatar()`（inJustDecodeBounds + inSampleSize 到最长边 1080 + 重压 jpeg，
  头像接口固定以 `image/jpeg` 提交），上传回调加页面判活，外层 `catch (Throwable)` 兜住 OOM。

### 4.【稳定性】下载服务：worker 异常后队列永久锁死 + 双 worker 互踩 + 失败误删半成品

- **根因**：`onStartCommand` 里的 worker 只 catch `JSONException/IOException`，`stopSelf()` 写在正常路径末尾；
  任何 RuntimeException 被线程池吞掉后 worker 静默死亡，但 `started` 仍为 true，之后所有下载入口
  只提示「下载队列已在进行中」。`start()` 是"先查后置"的非原子临界区，`onStartCommand` 每次都会起新 worker；
  `onDestroy` 无条件清理目录，会把另一个 worker 正在写的目录删掉。
- **修法**：
  - worker 整体包 `try/catch(Throwable)/finally`，`finally` 里复位 `started`、`WORKER_RUNNING` 并 `stopSelf()`；
  - `WORKER_RUNNING`（`AtomicBoolean`）保证同一时刻只有一个 worker，`start()` 加 `synchronized`；
  - `onDestroy` 只在"用户主动取消（stopService）"时才复位条目状态并删目录，异常退出保留文件供续传。

### 5.【稳定性】下载页点返回 = 假取消

- **根因**：`DownloadActivity` 的读循环没有取消标志，`onDestroy` 却已经删了文件；失败分支还在后台线程
  直接 `finish()` 并弹「下载失败」。
- **修法**：加 `volatile boolean canceled`，读循环逐块检查；`onDestroy` 先置位再清理；失败提示与
  `finish()` 统一改到主线程并判活。

### 6.【登录】-111（csrf 校验失败）被当成凭证失效，一次抖动就清空 refresh_token

- **根因**：`CookieRefreshApi` 把 `-101` 与 `-111` 都归入 `REFRESH_REJECTED`，`CookieRefresher`
  随即 `resetLogin()`（清空 mid/cookies/csrf/refresh_token）。而 -111 只是本地 `bili_jct` 与 Cookie
  不一致（切号、只落了部分 Set-Cookie、并发刷新）。
- **修法**：新增 `CookieRefreshResult.CSRF_MISMATCH`（可重试），`-111` 归入此类；只有 `-101` 才登出。
- **配套**：全仓 35 处写操作（评论/动态/收藏/弹幕/私信/稍后再看/图床等）由
  `SharedPreferencesUtil.getString("csrf","")` 快照改为 `NetWorkUtil.getLoginCsrf()` 实时值；
  `saveCookiesFromResponse` 在 Cookie 轮换后同步 csrf 快照（同锁写入）。

### 7.【稳定性】弱网下 POST 可能被 OkHttp 自动重发一次

- **根因**：全局 `OkHttpClient` 没关 `retryOnConnectionFailure`（默认 true），与项目注释里
  "POST（点赞/投币/发评论）不重试"的承诺矛盾——连接被重置时 OkHttp 会自行重发，
  服务端可能已执行成功，于是重复投币/重复评论。
- **修法**：builder 加 `.retryOnConnectionFailure(false)`；幂等 GET 的重试仍由应用层
  `executeWithDoctypeRetry` 负责。

### 8.【逻辑】失效专栏/动态页永远不会自动关闭

- **根因**：`OpusInfoActivity` 与 `DynamicInfoActivity` 写成 `if (isFinishing()) finish();`，
  条件永假（正确写法在 `VideoInfoActivity` 里是 `!isFinishing()`）。
- **修法**：改为 `if (!isFinishing() && !isDestroyed()) finish();`。

### 9.【发布】release 包缺少教程插图

- **根因**：`res/raw/keep.xml` 只保留 `@xml/*`，而 6 张 `mipmap/tutorial_*.webp` 由
  `TutorialActivity` 用 `getResources().getIdentifier()` 动态取，release 的 `shrinkResources`
  判定为不可达后裁掉（debug 正常，且不报错）。
- **修法**：`tools:keep="@xml/*,@mipmap/tutorial_*"`，并在 CI 里用 `aapt2 dump resources` 断言
  release 包中存在 6 个 `mipmap/tutorial_*`。

### 10.【播放页】暂停态跳转：提示出现了，进度条和画面却没动

- **根因**：进度条与时间文字只在 `progressTimer` 的 tick 里刷新，而这个 tick 开头就是
  `if (... || !isPlaying || isSeeking) return;`——暂停时它永久早退。于是横滑（或 ±N 秒按钮）
  虽然调用了 `ijkPlayer.seekTo()`，`video_now`/进度条/画面都停在旧位置；
  更隐蔽的是下一次横滑仍以这个陈旧的 `video_now` 为起点，越滑越偏。
- **修法**：`seekToPosition()` 在 `!isPlaying` 时同步 `video_now`、进度条（其监听器会顺带改时间文字）、
  并调用 `repaintPausedFrame()` 强解一帧；同时记下 `pendingPausedSeekMs`，`playerResume()` 在
  `start()` 前补发一次 seek（部分 ijk 版本对"暂停中 seek"只记住不落地）。进度条拖动也统一改走
  `seekToPosition()`，行为一致。

### 11.【播放页】暂停后弹幕继续滚动

- **根因**：DFM 的 `DanmakuView.seekTo()` 与 `start()` 在 `DrawHandler.handleMessage` 里都会落到
  **RESUME** 分支（SEEK_POS/START 之后紧跟 `case RESUME`：`quitFlag=false`、重建 `mTimeBase`、
  重启绘制线程）。因此在暂停状态下任何"对齐弹幕时间轴"的操作都会把弹幕重新跑起来，最典型的是：
  弹幕比取流慢、加载完成时 `prepared()` 回调里做了一次 `seekTo`；以及暂停后拖动进度条触发
  `seekDanmakuTo()`。
- **修法**：新增 `userPaused` 标记（不能用 `isPlaying`：`onPrepared` 里 `isPlaying` 要到末尾才置 true），
  在 `seekDanmakuTo()`、弹幕 `prepared()` 回调、`onPrepared` 的 `start(anchor)` 之后统一调用
  `pauseDanmakuIfUserPaused()` 把它压回去；新实例 `onPrepared` 时重置标记（新实例准备完会直接开播）。

### 12.【短视频】三处生命周期问题

- 退到后台后 500ms 进度刷新仍自续期 → `onPause` 里 `removeCallbacks(progressRunnable)`；
- 短视频页继承 `InstanceActivity.isRestorablePage()=true`，冷启动可能恢复出空壳页 → 覆盖为 false；
- 新布局用了 `paddingHorizontal/paddingVertical`（API 26 才有），minSdk 19 上等于没设置 →
  改为 `paddingStart/End/Top/Bottom`。

## 看图页闪退（1.2.3 回归，最高优先）

现象：调过「界面边距」的用户点开任意图片（封面/评论图/相册）必闪退，报错
`IllegalStateException: You need to use a Theme.AppCompat theme (or descendant) with this activity.`

链路：`BaseActivity.onCreate` → `applyContentPadding` → `findViewById(android.R.id.content)` →
`AppCompatDelegateImpl.findViewById` → `ensureSubDecor()` → `createSubDecor()` 读 `AppCompatTheme_windowActionBar` 失败 → 抛异常。

根因：1.2.3 的「界面边距」把这次 `findViewById` 放进了基类；AppCompat 的 `findViewById` 会强制安装 subDecor，
而看图页在 Manifest 里挂的是 `Theme.NoSwipe`（parent `android:Theme.Black`，**不是** AppCompat 后代）；
看图页自己那行 `setTheme(R.style.Theme_BiliClient)` 又写在 `super.onCreate()` **之后**，等它生效时基类已经崩了。

修法（两层）：

1. **根因**：`ImageViewerActivity` 的 `setTheme()` 挪到 `super.onCreate()` 之前。Manifest 主题保持不变——
   氛围背景/自定义底图的排除逻辑读的是清单里的 theme，视觉不受影响；
2. **兜底**：`applyContentPadding` 整体 try/catch，主题代理失灵时退回
   `getWindow().getDecorView().findViewById(android.R.id.content)`（非 AppCompat 页面本来就只有这一个内容容器），
   以后再有非 AppCompat 主题的新页面也不会因为一个边距设置崩掉启动。

顺带全仓扫过：非 AppCompat 主题只有 `Theme.NoSwipe`，使用它的播放器继承 `Activity`、不走这段代码，
所以受影响页面只有看图页一个。

## 切后台再回来黑屏

`SurfaceView` 退到后台时被销毁、回前台重建，而播放器按默认设置已经在 `onPause` 里 `pause()` 过了。
暂停态下 ijk 的读线程停着，没有人会往新 surface 上吐帧，画面就整块黑着（声音、进度都正常）。三个入口一起补：

1. `SurfaceHolder.Callback.surfaceChanged` 原来是空实现。只在 `surfaceCreated` 里挂载时，
   解码器可能绑上一个尺寸还是 0x0 的窗口；现在两个回调都重新挂载；
2. 挂载后调 `repaintPausedFrame()`：暂停态下 seek 到「当前位置 +1ms」，逼解码器从关键帧重解一帧，
   把暂停帧重新画到新 surface 上（+1ms 是为了绕开部分 ijk 版本「位置没变就不做」的 seek 优化）；
3. `onResume` 里发现 surface 是在后台丢的，延迟 250ms（等窗口重新布局完）再挂一次并补画；
   `TextureView` 路径（`onSurfaceTextureAvailable`）同样处理。

## ±N 秒按钮：挪位置 + 跟随控制栏

原来 ±N 秒按钮和底部那一排（菜单 / 音量 / 播放）挤在同一个横向 `LinearLayout` 里。
小屏设备（368x448 的点读笔）放不下 7 个控件，文字按钮被压成竖排、只露半个字。

- 布局：两个按钮挪进左侧纵列（与倍速 `text_speed` 同一个 `LinearLayout`），纵向排列不再抢宽度；
- 显隐：`left_control` 加进 `fadeControls()` 的控件数组，点画面显示、再点收起，与顶栏/底栏/进度条同一套 150ms 淡入淡出；
- 开关：「显示快进快退按钮」控制它是否参与（直播、听视频模式一律不显示，`updateSeekButtons()` 统一口径）。

## 无极调音支持手动输入

滑条只有 0~100 的粗调。设置页新增 `input_float` 项「无极调音（0-100）」，
写入的就是播放页在用的 `player_volume_gain`（0~100 的百分比，float），两边共用一个值，不需要迁移。

## 互动视频选项显示不全

- 新增「互动选项自动竖屏」：横屏时弹出选项的瞬间 `setRequestedOrientation(PORTRAIT)`，
  收起选项（`hideInteractionChoices`）再还原回 `SENSOR_LANDSCAPE`；
  页面本来就是竖屏、或开了「软件旋屏」（自己转 View，不跟系统方向走）时不动；
- 选项容器由裸 `LinearLayout` 改为 `ScrollView + LinearLayout`：选项总高超过半屏时定高并可滚动
  （原生 `ScrollView` 没有 maxHeight，按内容 measure 一次后手动夹取 55% 屏高）。

## 空列表图文错位

`TextView` 的 `drawableTop` 贴的是**视图上沿**，而文字按 `gravity` 居中。空态 `emptyTip` 高度是 `match_parent`，
于是图标跑到屏幕顶部（压住标题栏）、文字留在屏幕中间。5 个布局（`activity_simple_refresh` /
`activity_simple_main_list` / `activity_simple_main_refresh` / `fragment_simple_list` / `fragment_simple_refresh`）
统一改成 `wrap_content` + 整体居中（RelativeLayout 用 `layout_centerVertical`，FrameLayout 用 `layout_gravity="center"`）。

## 启动时等待请求完成（新开关）

1.2.3 起开屏只做本地决策，Cookie 续期/刷新与终端接口全部挪到首屏之后，开屏一闪而过、打字动画永远看不全。
新增开关「启动时等待请求完成」（默认关）：打开后先跑完这三项启动校验、并等打字动画播完再进首屏。

- 校验跑在临时线程上 `join(6000)`，弱网/断网最多多停 6 秒，超时就先走（校验线程继续在后台跑完）；
- 动画时长按「每字 100ms、封顶 4 秒」估算，与 `onCreate` 里的打字 Timer 同一口径；
- 等待结束后复核 `isFinishing()/isDestroyed()`，返回键随时能退出；GitHub 更新检查弹窗仍推迟到首屏之后。

## 搜索页热搜开关（用户反馈）

反馈：点搜索框、还没点到下面的历史记录，热搜卡就盖上来，想找自己的搜索记录老被挡住。

代码现状：输入框为空时 `showKeywordPanel()` 优先显示热搜卡，否则才显示历史卡；两张卡与结果区**同位叠放互斥**
（不透明底板，任何时刻只能显示一张），所以只要热搜返回了数据，历史就永远看不见。

修法：新增「搜索页显示热搜」（**默认关闭**）。关闭时连接口都不请求（省一次网络），
空输入一律显示历史卡；打开则恢复原来热搜优先的行为。

## 批次十：全站排行榜一直空（接口返回结构对不上）

- 现象：进入「全站排行榜」永远空白，下拉刷新也没用。
- 根因：`/x/web-interface/ranking/v2` 的返回是
  `{"code":0,"data":{"note":"...","list":[...]}}`——**data 是对象、列表在 `data.list` 里**。
  旧代码按 `ApiResponse<List<RankingItem>>` 交给 Gson 解析，类型对不上后 `data` 直接是 null，
  于是"接口成功但列表永远 0 条"。
- 修法：`RankingApi.getRanking()` 改成直接按 `JSONObject` 取 `data.list`（兼容 data 为数组的旧形态），
  字段按 `owner.name` / `stat.view` 取，缺失时退 `author` / 空串；带 WBI 的请求失败时自动改用无签名请求重试。
- 顺带：首次加载失败时补建适配器（否则下次下拉会在 `notifyItemRangeRemoved` 上空指针），
  排行榜页补上"加载失败 / 暂无数据"的空态提示。

## 批次九：空评论区里发出的评论不显示（带图更明显）

- 现象：评论区原本一条都没有时，自己发出的**带图**评论显示不出来（个别机型表现为一张空卡片），
  再发一条纯文字评论后两条才一起出现。视频评论区与动态评论区表现一致。
- 根因是三处叠加：
  1. `notifyReplyInserted` 在"列表只有头部"的状态下用 `notifyItemInserted` 插入首条，
     这种状态下 RecyclerView 偶发不会真正重新布局 → 新评论不可见；
  2. B站评论列表有延迟：刚发完立刻拉取常常还拿不到自己那条，一次 refresh 就会把本地插入的评论顶掉；
  3. `/x/v2/reply/add` 返回的 `reply` 里不一定带 `content.pictures`，
     本地卡片的 `pictureList` 为空 → 带图评论渲染成"没有图"的空卡片。
- 修法：
  1. 空列表插首条改为 `notifyDataSetChanged()`（只有 0→1 这一种情况，代价可忽略）；
  2. `ReplyFragment` 记住本地刚发出的根评论（最多 20 条），每次 `refresh()` 成功后把服务端还没返回的
     那几条补回列表顶部（按 rpid 去重）；列表还没就绪时也先记下来，等列表加载完补上；
  3. `WriteReplyActivity` 把本次上传成功的图片地址挂到本地这条评论的 `pictureList` 上，卡片立刻有图；
     另外补了 `resultReply == null` 的兜底（服务端 code=0 却没带 reply 时不再空指针）。
- 追加两处（用户反馈"数量读得到但加载不出来"、截图是专栏详情页）：
  4. `OpusInfoActivity.onEvent(ReplyEvent)` 里那一行 `notifyReplyInserted` 被注释掉了——专栏页发完评论
     只更新了「共 N 条评论」，列表根本不插这条，要退出重进才可能看到。已恢复转发（带空判断）。
  5. 热度排序（`mode=3`）对"只有一两条新评论"的评论区经常返回空列表，而「共 N 条评论」是另一个接口
     给的数字，于是表现为"读得到数量但加载不出来"。现在 `refresh()` 遇到"接口成功 + 列表为空 +
     count > 0 + 非时间排序"时会换 `mode=2` 再拉一次，拉到了就把排序状态一并切过去（按钮口径一致）。
- 影响面：`ReplyFragment`、`WriteReplyActivity`、`OpusInfoActivity`；`ReplyApi` 增加了调试字段。

## 新增开关：显示详细接口错误（实验室 → 调试，默认关闭）

- 打开后，接口失败不再只有一句短提示，而是弹「接口错误详情」页（可长按复制），内容包括：
  接口名与请求参数（`type`/`oid`/`mode`/`offset`）、B站返回码与 message、原始返回片段（截断 800 字符）。
- 评论区还有一个专门场景：接口成功但**一条都没拉到、而头部显示共 N 条**时，也会弹这个详情页，
  并附上"改用时间排序重拉"那一次的结果——正是"读得到数量但加载不出来"需要的证据。
- 实测证据（用户反馈的那条专栏）：`type=11 oid=413114181` 在 mode=3 与 mode=2 下 B站都返回
  `replies: []`、`is_end: true`，即**服务端就是 0 条**，不是解析丢数据；而头部计数来自 `opus.stats.reply`，
  与评论列表索引不同步（刚发的评论要等审核/索引后才进列表）。
- 因此补了两层兜底：① 换排序仍为空时，按 `type` 兜底链 `17 → 12 → 1` 各试一次（接口给的 `comment_type`
  与实际存放评论的类型不一定一致，成功后把 `type`/`replyType` 一并切过去，发评论/点赞口径同步）；
  ② 全部仍是空时给一次性人话提示（审核中/被折叠/不属于当前评论区），不再只留空白页。
- 实现：`ReplyApi.ReplyResult` 新增 `endpoint`/`detail` 字段；`MsgUtil.apiErrorDetail()` 负责按开关走
  短提示或详情页；`ReplyFragment.showLoadErrorMsg()` 与 `refresh()` 的空结果分支接入。

## 批次八：弹幕每隔几秒整体右跳的修复

- 现象：播放时弹幕每隔几秒整体向右跳一下，随后继续向左飘，循环往复。
- 根因：`updateTimer` 回调里拿播放器位置 `timer.update(pos)` 强行写 DFM 的时钟。
  DFM 的时钟是**墙钟驱动**的（`DrawHandler.syncTimer` 每帧按 `SystemClock` 推进 timer，基准是
  `mTimeBase`），而 `timer.update()` 只改"当前值"、不改 base：下一帧 `syncTimer` 发现 timer 落后，
  又按 `mCordonTime` 一帧帧把时钟推回去。于是"被拽回去（右跳）→ 又被推回来（左飘）"无限循环；
  250ms 兜底通道那条"偏差 >800ms 就 seek + 2s 冷却"又在旁边补刀，每 2 秒多给一次明显的右跳。
- 修法：① `updateTimer` 改成**只读不写**（连播放器位置都不读，避免原生锁）；
  ② 兜底通道改成只在两类事件上动时间轴：**卡顿恢复**（墙钟过了很久、播放位置却几乎没变）
  按当前播放位置重 base 一次；**极端偏差**（>2s 且持续 3 秒）才纠一次、20 秒冷却。
- 保留的对齐点：起播/prepared、用户跳转（进度条、±N 秒、D-pad、双击、隐藏后重新显示）、暂停恢复。
- 影响面：`PlayerActivity.updateTimer()` / `syncDanmakuIfDrifted()` / `resetDanmakuTick()`。

## 批次七：无极调音 + 快进快退按钮 + 反馈群号更新

## 无极调音（播放页，长按音量按钮打开）

- 需求来源：凉腕播放器（`com.aliangmaker.media`）的"无极调音"。那边的实现是两套：手势拖动走
  `AudioManager.setStreamVolume()`（最终仍被系统档位量化），以及设置里的 `volume`（0–100）走
  `ijkMediaPlayer.setVolume(v, v)`——后者才是真无极（纯软件增益）。
- 我们的做法：只做软件增益这一层。`ijkPlayer.setVolume(gain, gain)` 是采样级线性乘算
  （原生方法在 `libijkplayer.so`，已确认注册），和系统音量是乘算关系；增益上限 1.0，
  不做放大（>1.0 会削波失真）。
- UI：长按底部音量 +/− 弹出 `layout_volume`（照倍速浮层的样式做），SeekBar 0–100、1% 一档，
  拖动实时生效，松手 4 秒自动收起；单击音量按钮仍是系统音量 ±1 档，老习惯不变。
- 持久化：`player_volume_gain`（默认 100%）；播放器重建（切清晰度/换 P/听视频模式）后
  由 `onPrepared()` 重新套用。
- 验证：真机 0% / 37% / 50% / 100% 听感与数值一致；「音频输出」默认与 OpenSL 两条路径都要过一遍；
  切清晰度、听视频模式、后台播放后增益保持。

## 快进/快退按钮

- 底部按钮行新增 `±N 秒`（文字按钮，避免手表上图标看不清）；N 读「快进快退秒数」设置（默认 10），
  与双击快进共用同一项。
- 逻辑复用 `seekToPosition()`（内部已同步弹幕零点），并补了边界 clamp——原来 D-pad 那条没夹
  0/duration，多按几下会把负数交给 seekTo。
- 直播模式没有可 seek 的进度，两个按钮直接隐藏。

## 横滑调进度（播放画面手势）

- 交互：单指在画面上左右滑 → 中间实时显示"快进到 01:23 / 09:41（+45s）"，**松手才 seek**；
  满屏宽度对应 `duration/6`（夹在 30s~300s），短视频整屏就是全片。
- 接管条件（缺一不可）：单指、未放大画面、非长按 3x、非双指缩放；水平位移先过 8dp，
  且横向位移 ≥ 纵向的 1.5 倍（斜滑不误触）。放大画面后单指拖动继续走 `videoMoveBy`（拖画布），
  不能抢——否则"放大后挪画面"就没法用了。
- 为什么松手才 seek：边拖边 seek 会让 ijk 反复重建缓冲，手表上直接卡成幻灯片。
- 开关：内置播放器设置 →「横滑调进度」（默认开），老用户不适应的可以关掉。
- 与既有手势的关系：单击/双击/长按 3x/捏合缩放/双指移动全部保留；拖动期间把
  `gesture_click_disabled` 置位，松手后的那次单击不会顺手把控制栏切走。

## 批次六：界面边距 / 圆屏适配下，新版美学装饰层没铺满屏幕

- 现象：设置里调过「界面边距」，再开「圆屏适配」，页面四周会留出一圈黑边，屏幕左下那枚粉色装饰圆
  还会在内容区底边处被硬切一刀——看上去像“新版美学 UI 只覆盖了中间一块”。
- 根因：「界面边距」被加在 `DecorView` 上，而氛围背景层（`AmbientBackground`）与自定义背景底图
  都是挂在 `DecorView` 上的装饰层。ViewGroup 的子 View 一律排布在自己的 padding 之内，
  所以边距一加在 `DecorView`，装饰层就跟着被压进内容区，四周只剩窗口底色（黑）。
  圆屏模式底部还要多留 3% 的“下巴”，那一刀切得尤其明显。
- 修法：边距下沉到 `android.R.id.content`（内容照样内缩），装饰层恢复整屏铺满；
  Snackbar 也改挂内容容器，避免提示条贴屏底（圆屏设备上正好落进下巴）。
- 影响面：`BaseActivity.applyContentPadding()` / `onEvent()`；`window_width`、`window_height`
  的语义不变，圆屏下标题、时钟、刷新按钮的重排逻辑不受影响。

## 圆屏适配直接沿用直屏的背景风格（去掉圆屏专属画法）

- 现象：直屏模式整页是粉色氛围，开了「圆屏适配」却变成纯黑底 + 右上/左下两圈粉线，
  像是"没上新的 UI 皮肤"，和直屏完全是两套观感。
- 根因：`AmbientBackground` 把两种模式做成了互斥——`MODE_RADIAL`（直屏）才画径向粉色光晕，
  `MODE_ROUND`（圆屏）只画两枚装饰圆环，光晕不画。
- 修法：**直接删掉圆屏专属画法**（`MODE_ROUND` / `drawRing` / `setMode` 一并移除），
  全局只有一种背景 = 直屏那套顶部粉色径向光晕；「圆屏适配」只负责布局（标题/时钟居中、
  边距与底部下巴），不再改视觉风格。
- 影响面：`AmbientBackground`（去 mode）、`BaseActivity.installAmbient()`、`SplashActivity`；
  开屏页的氛围层同样统一走这一套。

## 批次四：崩溃上报过滤

## 只上报"重要且可行动"的崩溃

- **现象**：后台 50 条 1.2.2 记录（33 台设备）里约 90% 是噪音——播放哨兵 20 条（多数是后台/内存回收）、
  lmk 11 条、实验室主动触发的测试崩溃 4 条、没有一帧本仓库代码的系统异常若干；真正能定位到代码的只有 5 条左右。
  同机同崩溃还会反复进来（没有指纹去重）。
- **改法**：新增 util/CrashFilter，在**入队之前**统一裁决（本地留档不受影响）：
  1. 系统压力类（lmk / freezer / resource）完全不上报，也不再生成崩溃文件——真 OOM 会以
     java.lang.OutOfMemoryError 走 Java 崩溃链路；
  2. 实验室「主动触发崩溃」不上报；
  3. 播放哨兵只保留三类强信号：连续异常 ≥2 次、停在 native 高危阶段（加载ijk库/配置显示/设置数据源/已提交准备）、
     或短会话（≤120s）异常收尾；「首帧就绪 + 长时间停留」这类看了一晚上被回收的记录不再报；
  4. Java 崩溃的堆栈里没有任何本仓库代码帧（含随仓库编译的 ijk / DanmakuFlameMaster / brotlij）→
     判为系统或环境异常，丢弃；java-early 例外（它本来就发生在框架初始化阶段）；
  5. 24 小时内同指纹（类型 + 异常类 + 页面 + 栈顶业务帧 + 版本）只上传一条，重复次数追加到 message 末尾
     （不加数据库字段，避免 Supabase 表约束 4xx 拒收）。
- **队列**：待发上限 5→8；文件名带 p0_ / p1_ 前缀，补发时先 P0 后 P1；队列满时先淘汰 p1（哨兵），
  P0 不再被弱信号挤掉。
- **可观测**：崩溃页会多显示一行「本次未自动上传，原因：xxx，仅本地留档」；本地 crash-*.txt（20 份循环）
  与崩溃页「重新上报未发出的记录」保持不变。
- **回归验证**：用同一批 50 条记录回放规则，过滤后剩 8 条，且全部是真 bug / native / ANR 类线索
  （选图 ActivityNotFound ×2、前台服务超时、Glide destroyed activity、4 条强信号哨兵）。

## 批次三：开屏提速

## 开屏慢的根因：两个 B 站请求被串在进首屏之前

- **现象**：冷启动时开屏打字动画要停一会儿才进首页；弱网/手表上尤其明显，断网时更久。
- **根因**：SplashActivity 的后台线程在 startActivity 之前串行做两件事：
  1. CookieRefresher.check(true) → passport.bilibili.com/x/passport-login/web/cookie/info（每次启动强制）；
  2. CookiesApi.checkCookies() → GET https://www.bilibili.com/。

  两条都是完整 RTT（DNS + TLS + 请求），而 OkHttp 的连接/读超时是 8s/16s，断网时等于要等两个超时
  才走兜底；之后还 postDelayed(100) 才 startActivity。同时 BiliTerminal.onCreate 一上来就并发 6 个
  网络任务（3 个崩溃补发、播放哨兵、动态未读、私信未读），与开屏请求抢 DNS/TLS/带宽。
- **改法**：
  1. 启动续期改 CookieRefresher.check(false)：它本来就有 1 小时节流，而 startPeriodicCheck() 已每小时
     查一次，启动时强制再查是重复的 RTT；
  2. 有网络时**本地决策一完成就进首屏**，Cookie 续期/刷新/更新检查全部挪到首屏之后（runStartupChecks）；
  3. 去掉两条退出路径上的 postDelayed(100)；
  4. 无网络时用 ConnectivityManager.getActiveNetworkInfo() 瞬时判定，直接走"恢复链/本地库"兜底，
     不再等超时（这也是断网冷启动"卡在开屏"的来源）；
  5. BiliTerminal 里崩溃补发、播放哨兵、未读数检查统一延后 2 秒（ExitReasonCollector 只读本地，保持立即）；
  6. 保留唯一的阻塞例外：首启缺 buvid3 时仍然先补齐 Cookie 再进（一次性代价）。
- **观测**：adb logcat -s startup 会输出 MultiDex.install xxms、Application.onCreate 完成 xxms、
  进入首屏：距离开屏 onCreate xxms（online=true，bootstrap=false），可直接对比改动前后。
- **行为变化**：登录失效的提示从开屏挪到首屏弹出；在线但接口失败不再阻止进入（由首页自己提示重试）；
  离线兜底、整链恢复、首启设置页跳转均保持原样。

## 回归修复：深夜提醒 / 免责声明被首屏压在下面

- **现象**：开屏提速后，"深夜提醒"要在点一下菜单之后才弹出来（本来应该一进首页就弹）。
- **根因**：这两个弹窗在 AppInfoApi.check 里是 startActivity(DialogActivity)。旧流程里它跑在
  "首屏 startActivity 之后"（postDelayed 100），所以稳定地盖在首屏上；提速后改到首屏之前/同时发起，
  两者竞争——弹窗先入栈、首屏后入栈，弹窗就被压在下面，只有下一次页面切换才浮上来。
- **修法**：把弹窗从 AppInfoApi.check 里拆出来成 showStartupDialogs（纯本地判断），
  交给新增的 BiliTerminal.runAfterFirstPageResumed 在**首屏 Activity resumed 之后**执行
  （延迟 250ms，给"恢复链"连续入栈留余量）；网络部分 checkVersion 仍留在后台。
  挂载点放在 startMainPage / startRestoreChain 的 UI 线程块内、startActivity 之前，
  避免后台线程迟到导致这一次漏弹。

## 批次二：老设备崩溃 / 上报 TLS / 弹幕漂移

> 本轮来自三路输入：一位官方 1.2.2 用户反馈的 NoSuchMethodError 截图、后台 50 条 1.2.2 崩溃记录，
> 以及一位 Android 4.4 用户上传的 8 张崩溃控制台截图。所有根因都先在本仓库的 release DEX、
> R8 mapping 与 DanmakuFlameMaster 源码里验证过，再动手改。

## 播放页在 Android 4.4/5.0 打不开：EventBus 反射踩到 API 21 的 MediaSession

- **现象**：4.4 用户每次点播放都闪退，崩溃页显示 Unable to start activity ComponentInfo{...PlayerActivity}，
  Caused by: P1.f: Could not inspect methods of ...PlayerActivity，
  再往下是 NoClassDefFoundError: android/media/session/MediaSession。
- **根因**：MediaSession 是 API 21 才有的系统类。播放页虽然已按 SDK 判断才初始化它，但
  MediaSession.Callback 匿名类要读 PlayerActivity.mediaSession 私有字段，D8 为兼容 API<24 的
  nest 机制会生成**返回类型为 MediaSession 的合成访问器**——反编译 release DEX 可见
  -$$Nest$fgetmediaSession(PlayerActivity) -> Landroid/media/session/MediaSession;，
  R8 mapping 里也同名可查。而 BaseActivity.onStart 里 EventBus 3.2.0 要 getMethods() 反射注册
  订阅者，解析到这个返回类型时老系统直接抛 NoClassDefFoundError，Activity 起不来。
- **修法**：新增 helper/MediaSessionHelper，把 MediaSession/PlaybackState/MediaMetadata 全部收进去；
  播放页只持有该 helper，并在所有访问点前置 Build.VERSION.SDK_INT >= LOLLIPOP 短路
  （hasMediaSession()），API<21 的设备连字段都不去读。
- **验证**：重新反编译修复后的 release DEX，MediaSession 只出现在 helper/MediaSessionHelper
  （含其回调内部类）里，PlayerActivity 零引用；PlayerActivity -> MediaSession 的合成访问器数量为 0。

## 老设备崩溃报告一条都传不上来：上报专用 OkHttp 漏了 TLS 兼容

- **现象**：4.4 设备的崩溃控制台连续 补发失败 xxx.json（第 2/3/4/5 次，HTTP -1），
  日志里是 SSLHandshakeException: tlsv1 alert protocol version。
- **根因**：全站网络统一走 NetWorkUtil.setOkHttpSsl（API≤22 时启用 TLS1.1/1.2），但 CrashUploader
  自己 new 了一个裸 OkHttpClient，没套这套兼容 —— 老系统默认只谈 TLSv1.0，被服务端（Supabase）
  拒绝，于是**老设备的崩溃报告全部丢失**。后台 50 条记录里没有一条 sdk_int <= 21，正是这个原因。
- **修法**：CrashUploader.client() 复用 NetWorkUtil.setOkHttpSsl，失败时退回系统默认
  （不能因为 TLS 初始化失败反而不上报）。

## 弹幕越看越偏：弹幕引擎自己走时钟，零点还和视频对不上

- **现象**：弹幕时间轴与进度条不一致；长视频、低帧率手表、切清晰度/切听视频后尤其明显，
  有时是"一开始就差几秒"，有时是"越看越偏"。
- **根因（四层，都在 DanmakuFlameMaster 源码里可查）**：
  1. DanmakuView.start() 内部就是 start(0)，零点 = **"DFM 准备好的那一刻"**。而弹幕是异步下载的
     （长视频 11 段串行），起播时往往比取流慢 → 整场固定偏后 N 秒。
  2. 每次 prepare() 都把 DrawHandler.mTimeBase 重置成当前 uptimeMillis()；弹幕空闲时
     （mInWaitingState/nothingRendered，弹幕间隙 500ms 就会出现）syncTimer 会执行
     timer.update(startMS - mTimeBase)，等于把时间轴直接拽回 0。
  3. DFM 时间轴按墙钟 + 渲染帧率推进（每帧 d 被钳制在 [mFrameUpdateRate, mCordonTime]），
     低帧率设备上会越走越慢；而播放器位置从来没有被反馈回去。
  4. 旧纠偏 syncDanmakuIfDrifted 只认"时间轴完全停住 + 播放器领先"，慢漂移永远不触发，容差还是 2 秒。
- **修法**：
  - onPrepared 改用 start(anchor)（续播/换清晰度用 progress_history），不再 start(0)；
  - prepared() 回调**无条件**按当前播放位置 seek 一次（原来只处理 pendingDanmakuSeekMs），
    并补一次 setSpeed——此前 handler 未 prepared 时 setSpeed 会被静默丢弃，倍速播放时弹幕时钟停在 1x；
  - updateTimer 重新启用：**只读** 250ms 定时器维护的 volatile video_now（绝不碰 ijk 的
    getCurrentPosition() 原生锁），偏差 >500ms 且连续两次采样成立才 timer.update(pos)；
  - syncDanmakuIfDrifted 从"卡死判定"改成绝对偏差判定（连续 3 个 tick >800ms，冷却 2s）；
  - seekDanmakuTo 在 handler 已 prepared 时清掉 pending，避免下次 reload 用过期位置再跳一次；
  - 每 5 秒打一条 弹幕同步 player=… danmaku=… diff=… 诊断日志，真机上可直接验证。
- **未做**：参考仓库（凉腕播放器）的"弹幕随倍速"开关。DFM 的时间轴与滚动速度是耦合的
  （setSpeed 同时缩放时间轴），做成开关要么时间轴不跟、要么滚动速度不对，收益低于风险。

## 转发/发动态在 Android 4.4/5.x 崩：List.sort 是 API 24 才有的方法

- **现象**：官方 1.2.2 用户反馈弹窗：java.lang.NoSuchMethodError: No virtual method
  sort(Ljava/util/Comparator;)V in class Ljava/util/ArrayList; or its super classes。
- **根因**：DynamicApi.parseAtContent 里用了 indexesList.sort(...) —— List.sort 是 Java 8 默认方法，
  Android 上 API 24 才有；本项目 minSdk 19 且没开 core library desugaring，老设备必崩。
  反编译确认这是**全 DEX 唯一一处** sort(Comparator) 调用。
- **修法**：改 Collections.sort(...)；顺带给 parseAtContent 补 atUserUid == null 兜底。
- **路径**：视频详情页「转发」→ DynamicApi.relayVideo → buildContents → parseAtContent，
  即用户在小屏上点转发就必然触发。

## 线上 50 条崩溃记录里能定位到代码的三处

- EditProfileActivity 选图 ActivityNotFoundException（4 条，sdk27 手表没有相册）：先 resolveActivity

  后台 20 条同类「播放异常退出」不再淹没真正的新崩溃。
- **不修**：BadParcelableException（Android 11 系统 InsetsSourceControl 自身的问题）、
  DeadSystemException、reason:3 低内存回收、reason:14 freezer、实验室里主动触发的测试崩溃。

## 批次一：收藏夹 / 下载 / 缓存播放 / 首页推荐

> 本轮改动面向 2026-10 B 站接口调整，四个独立问题：收藏夹、下载失败、缓存播放崩溃、首页推荐。
> 全部改动均在真机接口层面先做过对照实验，结论写在各自的「根因」里。

## 收藏夹：整条链路迁到 x/v3/fav/*

- **现象**：收藏页只剩「创建收藏夹」和「图文收藏夹」两张卡片，视频收藏夹列表为空；页面不报错、不转圈，就是不显示。
- **根因**：视频收藏夹这条链路三处都用的是老接口，B 站已经换成 `x/v3/fav/*`，老接口对登录态不再返回数据：
  1. 列表 `space.bilibili.com/ajax/fav/getBoxList` —— 请求成功但 `data.list` 为空（这是"只剩图文收藏夹"的直接原因：图文收藏夹走的是 `api.bilibili.com` 的 `polymer/.../opus/favlist`，域名和接口都是新的，所以只有它活着）；
  2. 内容 `x/space/fav/arc?fid=` —— 已被官方前端淘汰；
  3. 收藏/取消收藏 `medialist/gateway/coll/resource/deal|batch/del` —— 线上直接返回 `-401 未授权`（容器内实测，匿名探测也是 -401，说明是接口本身下线而不是登录态问题）。
- **修法（对齐 PiliPlus `lib/http/fav.dart`）**：
  - 列表 → `x/v3/fav/folder/created/list`（分页，`pn/ps/up_mid`），字段 `id=media_id / fid / title / cover / media_count / attr`；
  - 内容 → `x/v3/fav/resource/list`（`media_id/pn/ps/order=mtime/type=0/tid=0/platform=web`），只保留 `type==2` 的普通视频稿件，`attr!=0`（失效视频）显示为「已失效」；
  - 增删 → `x/v3/fav/resource/batch-deal`（`resources=<aid>:2` + `add_media_ids|del_media_ids=<media_id>`）。
- **关键点：媒体身份从 fid 变成 media_id**。v3 只认 media_id，因此：
  - 收藏夹列表接口直接给 media_id，走正常路径；
  - 老入口/老 Intent 只有 fid 时用 `FavoriteApi.mediaIdOf(mid, fid)` 兜底换算（`media_id = fid*100 + mid 后两位`，实测 `636926+73→63692673`、`40267484+32→4026748432`，老代码里 addFavorite 也是这么拼的）；
  - `getFavoriteState` 的响应补了 `id` 字段，收藏选择页据此传 media_id。
- **显示**：v3 不再返回收藏夹容量上限（`max_count`），卡片改为只显示数量（老数据里还有上限值时沿用旧样式，不会出现 `307/0`）。
- **影响文件**：`FavoriteApi`、`FavoriteFolderAdapter`、`FavoriteVideoListActivity`、`AddFavoriteActivity`、`FolderChooseAdapter`。

## 下载：不是网络问题，是自家域名白名单把 PCDN 地址拦死了

- **现象**：新版下载器缓存视频必弹「下载失败，网络错误」。
- **根因**：`DownloadService.validateMediaUrl` 只放行 `bilivideo.com / hdslb.com / bilibili.com / 两个 akamai 镜像`，而 B 站现在对 1080P 的 mp4（`format=mp4720`）与 DASH 流下发的首地址大量是 PCDN：
  - `https://xxx.edge.mountaintoys.cn:4483/...`（第三方 PCDN 域）
  - `https://xyxxx.mcdn.bilivideo.cn:8082/...`（B 站自有 PCDN，但白名单只写了 `.bilivideo.com`）
  抽样 12 条热门视频，**10/10 命中**，主地址全部判 false → `downFile` 第一步就 `return ERR_NETWORK`。
  对照实验：老下载器 `DownloadActivity` 直接 `NetWorkUtil.get(url)`、不做域名校验，所以能下。
- **修法（PiliPlus `getCdnUrl` + `DownloadManager` 同思路）**：
  1. **候选地址列表**：取流时把 `durl[].url + backup_url[]`（DASH 是 `baseUrl + backupUrl[]`）整理成候选，**官方 CDN 优先、PCDN 垫底**。实测 `backup_url` 里 100% 带 `upos-sz-*.bilivideo.com`，且官方 CDN 拉 200KB 约 1 秒、PCDN 约 5 秒。PiliPlus 的默认 CDN 策略（`CDNService.backupUrl`）就是优先备用地址；
  2. **两档域名策略**：B 站自有域（新增放行 `.bilivideo.cn`）带完整请求头；非 B 站域但**确实来自 playurl 响应**才放行，且改用 `webHeadersWithoutCookie()`（只发 UA/Referer/Origin）—— 第三方 PCDN 是合法播放地址，但不是 B 站资产，绝不能收到登录 Cookie；其余来源仍然拒绝；
  3. **Range 断点续传**：`bytes=<已下载>-` + append 模式，206 续写、416 视为已完整、200 则从头覆盖；下载结束做长度校验（PCDN 会提前断流），对不上判本次候选失败，交给下一个候选/下次续传；
  4. **失败可诊断**：日志记录每个候选的 host 与 HTTP 码（原来失败只报一句"网络错误"，连域名都没有）。
- **仅音频同样修复**：`getVideoDash` 之前只取 `baseUrl`，而音频主地址正是 `mcdn.bilivideo.cn`，同样会被判死；现在也走候选列表。
- **影响文件**：`PlayerApi`（`DurlItem.backup_url`、`buildMediaCandidates`）、`PlayerData`（`videoUrls/audioUrls`，含 Parcelable）、`NetWorkUtil.isBilibiliHost`、`DownloadService`。

## 缓存播放：本地弹幕在后台线程操作 View，把整段加载一起中断了

- **现象**：播放已缓存视频，先在中间显示「装填弹幕中 (≧∇≦)」，随后弹出
  `CalledFromWrongThreadException: ... Expected: main Calling: DefaultDispatcher-worker-8`，视频停住，进度条一直是 `00:00/00:00`。
- **根因**：`PlayerActivity` 的本地视频分支在 `CenterThreadPool` 的协程线程（`Dispatchers.IO`，线程名 `DefaultDispatcher-worker-N`）上直接调用 `streamDanmaku()`，而它要操作 `DanmakuView`。异常被 `CenterThreadPool` 兜底成错误提示后，**同一个 lambda 里后面的 `setDisplay()` 不再执行** —— 播放器从未 `setDataSource/prepare`，所以画面停在加载态、时长恒为 0。
  同类问题此前修过两次（`downdanmuOld`、`streamDanmakuOnUi`），本地分支被漏掉。
- **修法**：本地弹幕渲染改回主线程；外面再包一层 `try/catch`（弹幕文件损坏只该"没有弹幕"，不该让整段加载失败）；`danmaku_url` 为空时不再 `new File(null)`（NPE 同样会中断起播）。
- **影响文件**：`PlayerActivity`（一处）。

## 首页推荐：默认改走 app 端，并修掉"每次下拉都在追加同一批"

- **现状核查**：开关（设置 → 偏好设置 → 首页使用app端推荐）与代码链路都在，接口实测仍是 `code=0`、一页 8 条，游标翻页有效（第 1→2 页 aid 交集 0）；但默认是关的，等于大多数人根本没走 app 端。
- **重复推荐的根因（实测）**：web 路径只传了 `web_location/feed_version/homepage_ver/uniq_id/screen`，而 `RecommendActivity` 又把 `page` 丢了（`setOnLoadMoreListener(page -> addRecommend())`）。用**完全相同的参数**连打两次，服务端返回的是同一批 30 条（交集 30、顺序一致）→ 每次"加载更多"都在把同一批再追加一遍。
- **修法**：
  1. **默认开启 app 端推荐**（默认值同时改在 `RecommendApi` 与设置页，避免"设置页显示关、实际在开"的口径不一致）；
  2. **web 端换批参数**（PiliPlus 同款）：`ps=20&fresh_idx=<page>&brush=<page>&fresh_type=4`；带这些参数后实测相邻两页交集为 0；
  3. **app 端刷新复位游标**：第 1 页（含下拉刷新）`idx=0` 且 `pull=true`，与 PiliPlus 的 `onRefresh` 一致；
  4. **app 端卡片过滤**：按 PiliPlus `_filterAppRcmd` 的判据滤掉 `ad_av/ad_web_s/ad_info/can_play!=1` 与非 `av` 卡片（直播/番剧卡点进去本来是空的）；
  5. **兜底去重**：Activity 内按 `aid/bvid` 维护 seen 集合，刷新时清空——服务端换批已能保证相邻页不重复，这层用于网络重试、切回旧页面等边界；
  6. **失败不再静默**：首页第一页拿不到内容时提示"推荐加载失败，下拉重试"，而不是白页。
- **影响文件**：`RecommendApi`、`RecommendActivity`、`SettingPrefActivity`（默认值）。

## 崩溃上报改到自建服务（1.2.1 起默认开启）

- **为什么换**：腾讯 Bugly 后台的「问题详情」长期返回 `422` / `404`（`get-issue-info` 422、`get-last-crash` 404），榜单能看到条数，点开却没有任何堆栈，等于只能报数不能定位；而且它是闭源 SDK，与本项目的 GPL-3.0 冲突。
- **现在怎么做**：`ErrorCatch` 捕获 → 写本地文件 → 写待发队列 → 启动崩溃页 → OkHttp 上报到自建服务 → 杀主进程。零闭源依赖，零新增三方库。
- **授权策略变更**：改为**默认开启**，首次安装或升级到 1.2.1 及以上时弹一次说明框，写清收集什么、不收集什么、如何关闭；设置 → 偏好设置 → 崩溃上报 可随时关闭。
  - 例外：在更早版本里明确点过「不同意」的用户，本次**不会**被强行打开，弹窗改为告知「当前为关闭状态，可自行开启」。
- **三条不变式**：
  1. 先留痕再上报：本地文本与待发队列都写在上传之前，进程提前被杀也不丢；
  2. 崩溃页永远活下来：`CatchActivity` 跑在 `:crash` 进程，主进程什么时候死都不影响它显示；
  3. 上报失败是常态：实测 WiFi 下该域名会被重置、手机流量正常，失败一律入队，下次冷启动补发（最多 5 条；本地文件保留 20 份）。
- **采集范围**：机型、系统版本、应用版本、随机安装标识、堆栈、线程名、崩溃页面。**不采集** IMEI/OAID/AndroidID、账号、Cookie。
- **本地调试日志**：`Download/ReBiliDiag/app-log.txt` 仍**默认关闭**，与本次改动无关，需要时在实验室里手动开。
- **崩溃页黑屏的真正根因**（arm64 模拟器复现实锤）：`CatchActivity` 自 1.0.2 起给「可能的崩溃原因」前 8 个字符加粗时写死了 `setSpan(0, 8)`，而未知异常走的是只有 7 个字的「未知的崩溃原因」，越界让崩溃页自己又崩一次，系统反复拉起 → 无限黑屏。改为按 `min(8, length)` 截断。
- **体积**：release 包 9,818,310 → **9,535,964 字节**（移出 Bugly 的 jar 与两个 so）。
- **能力回退**：只捕获 Java 崩溃，Native 崩溃（ijk/ffmpeg）不再上报。本项目 so 均为 stripped，native 栈本来也只有地址，故接受此回退。

## 崩溃可观测性补强（2026-10-18，versionCode / versionName 均未变）

- **上报队列不再被单条毒丸堵死**：`CrashUploader.flushPending` 原来是「首条失败就 `break`」，队首那条若被服务端永久拒绝（字段/表约束 4xx），后面所有记录永远发不出去。改为逐条计次（旁挂 `.fail` 文件），连续失败 3 次才丢弃并留痕。
- **HTTP 状态码留痕**：`upload()` 以前只返回 `isSuccessful()`，分不清断网与 4xx 拒绝；现在把 `response.code()` 写进 `CrashTrace` 与 logcat，并对外暴露 `lastHttpCode()`。
- **补齐四类死角**：
  1. 启动最早期的崩溃（`Application.onCreate` 之前，`ErrorCatch` 尚未安装）：`attachBaseContext` 里先装一层「只落盘」处理器，写 `files/crash_early/`，下次冷启动由 `flushEarly()` 转成正式上报。此前这一段崩溃**完全不留痕**。
  2. 崩溃页自身崩溃：`:crash` 进程以前不装 handler，崩溃页再崩就彻底丢失。现在装「只落盘、不重开页面」的处理器（重开会导致无限循环），记 `crash_type=crash-page`。
  3. 原生崩溃 / ANR / 被低内存杀：API 30+ 用 `ApplicationExitInfo.getHistoricalProcessExitReasons` 在下次启动补报（`crash_type=native/anr/lmk/...`）。API 30 以下无此接口，仍只能靠播放哨兵。**`REASON_SIGNALED` 与 `REASON_OTHER` 故意不报**：我们自己崩溃后就是 `killProcess`（SIGKILL）收尾，误报噪音大于价值。
  4. 用户无手动重传入口：崩溃页的「上传堆栈」按钮以前正常崩溃时被 `GONE`，现在改为常显的「重新上报未发出的记录（待发 N）」，并显示上次 HTTP 结果。
- **「点退出又崩一次」的观感**：`exit_btn` 原来 `System.exit(-1)`，非 0 退出码被系统判成异常退出并弹「应用已停止运行」。改为 `finish()` + `Process.killProcess`。
- **设置页显示与实际相反**：`SettingPrefActivity` 里崩溃上报开关的默认值写的是 `"false"`，而 `CrashReportUtil.isEnabled()` 默认 `true`，显示为「关」实际在传。改为 `"true"`，并新增「活跃设备统计」开关。
- **崩溃次数统计**：新增 `CrashStats`，把每次崩溃按时间写进诊断目录下的 `crash-stats.log`（跨进程可读、按分钟去重、兼容旧 `crash-*.txt`）。它是**本地留痕**，不做 UI——按时间统计崩溃数量在 web 控制台看（见下条）。
- **活跃设备统计**：新增 `LaunchPing`，每天最多一条 `crash_type=launch`（安装标识 + 版本 + 系统 + 机型），随机延迟 3–8 秒上报，**不入崩溃待发队列**（避免挤掉崩溃记录）。与崩溃共用 `crash_reports` 表。
- **控制台（docs/crash-console.html）**：新增按时间筛选按钮（今天 / 近 3 天 / 近 7 天 / 近 30 天 / 全部，按钮上直接显示该区间崩溃条数）；新增「今日活跃设备 / 近 30 天活跃设备」两张卡片；查询时排除 `crash_type=launch`，避免活跃打点混进崩溃列表。
- **开屏动画独立开关**：开屏动画改为 `NEW_UI_DESIGN && SPLASH_NEW_UI` 双开关，图标与光晕观感不协调时可只关开屏、保留其它页面的新版美学（设置 → 偏好设置 → 视觉 → 新版开屏动画）。
- **回声洞新动态**：`R.array.eggs` 索引 1 插入开发者投稿（索引 0 仍是「再长按几次试试」提示，所以第一次长按行为不变）。

# 1.2.2（versionCode 20261019）

## 播放页起不来（MaterialCardView × 非 MDC 主题）

- **现象**：点开视频 → 只到「解析视频地址」页，进不了播放页；崩溃页堆栈是 `InflateException: Binary XML file line #386`。
- **根因**：`activity_player.xml:378` 的「跳过片头」卡片用了 `MaterialCardView`，而 `PlayerActivity` 的主题 `Theme.NoSwipe` 的 parent 是 `android:Theme.Black`（**不是** MaterialComponents 后代）。`MaterialCardView` 构造时校验主题，直接抛 `IllegalArgumentException: The style on this component requires your app theme to be Theme.MaterialComponents`，整份布局 inflate 失败。
- **修法**：换成 `FrameLayout` + 新增 `drawable/bg_clip_skip.xml`（深色半透明 + 圆角 + 细描边），`clip_skip_card` / `clip_skip_text` 两个 id 保持不变，Java 侧零改动。
- **为什么不改主题**：把 `Theme.NoSwipe` 换成 MaterialComponents 子主题会同时影响播放器与看图页的状态栏、对话框、背景观感，风险远大于收益。

## 退出后回到旧页面（apply 写盘被 SIGKILL 吃掉）

- **现象**：主菜单点「退出」→ 重新打开，回到退出前那个页面；崩溃后重启 → 也回到旧页面。
- **根因**：`MenuActivity` 与 `ErrorCatch` 都在 `killProcess` 之前调 `ResumePageUtil.clear()`，而它走 `SharedPreferencesUtil.putString()` → `apply()`。`apply()` 的写盘在后台队列里，`Process.killProcess` 是 SIGKILL，队列来不及 flush，恢复栈原样留着。
- **修法**：新增 `SharedPreferencesUtil.putStringSync()`（`commit()` 同步落盘），`ResumePageUtil.clear()` 改用它。恢复栈的读取路径不变。

## 其余修复

- **选背景图闪退**：`SettingUIActivity` 的 `bgImagePicker.launch("image/*")` 在 GLL-AL09 这类没有系统文件选择器的设备上抛 `ActivityNotFoundException`（`GET_CONTENT + OPENABLE + image/*` 无处理者）。加 `try-catch` 并提示，不再闪退。
- **专栏 NPE**：`OpusInfoActivity` 直接读 `opus.stats.reply`，接口未返回 `stats` 时崩（线上 2 例）。`stats` 与 `upInfo` 一并判空。
- **后台被回收被误报成播放异常**：`PlayerSentinel` 新增「是否在后台」标记（`onStop` 置真、`onStart` 置假）。退到后台后被系统回收只清标记、不上报；「听视频」模式仍上报（后台播放属预期行为，被杀才算异常）。
- **LMK 噪音**：`ExitReasonCollector` 对 `REASON_LOW_MEMORY` 且 `importance >= 400`（cached 后台进程）直接跳过。实测一批 27 条里 17 条是这类，把真实问题全淹了。
- **上报不再轻易丢记录**：`MAX_RETRY` 3→20；4xx（服务端明确拒绝）改为一次即丢，网络/TLS 失败才计次；异常日志补上 `message`——此前只记类名，出现 `SSLHandshakeException` 时完全无法定位。

# 1.2.1fix（versionCode 20261018）

> 只做修复与优化，功能集合与 1.2.1 一致。

## 弹窗全面改为自适应

- **问题**：把「界面大小」（`dpi` 倍率）调大后，弹窗正文被截断、按钮被挤出屏幕。崩溃上报说明、实验室「调试日志落文件」开关、番剧整季选集三处最明显。
- **根因**：应用内缩放走的是「改 Activity 的 `Configuration.densityDpi` + DecorView padding」，只作用于 Activity；弹窗是独立窗口，可用高度仍是系统原始屏幕高。而 appcompat 的 `abc_alert_dialog_material.xml` 里标题、正文 `NestedScrollView`、按钮栏**全是 `wrap_content`、没有任何高度上限**，放大后的内容直接把窗口顶穿，系统按屏幕硬裁。
- **修法**：新增 `util/AdaptiveDialog`（自绘 `MaterialCardView`，不走系统 AlertDialog）：
  1. 窗口宽高按**系统真实屏幕像素**取上限（92% / 86%），不受应用内密度影响；
  2. 先藏起内容区量出「标题 + 按钮 + 内边距」固定开销，再量整张卡片自然总高，取小作为窗口高；
  3. 内容区高度钉成「窗口高 − 固定开销 − 内容区 `topMargin`」，超出部分在内部滚动，按钮永远留在窗口内。
- **踩到并修掉的两个坑**（都实测复现过）：
  - 计算固定开销时内容区是 `GONE`，`GONE` 子项连同 `topMargin` 一起不参与布局，导致窗口比卡片矮几 dp，**底部按钮被窗口裁掉一半**。改为显式减去 `topMargin`。
  - `MaterialButton` 用 `wrap_content` 时，`TextButton` 样式的 inset 与 padding 叠加会把内容区压到几像素，**按钮文字只剩中间一条横线**。改为代码里固定 48dp 高、去掉竖向 padding。
- **覆盖范围（7 处）**：崩溃上报说明、设置项警告开关、番剧整季选集、更新提示（三按钮）、更新源单选、自定义镜像前缀输入、删除账号确认。
- **未改动**：`TutorialActivity`（教程页）的「已阅」按钮原本就在滚动内容末尾，小屏 + 大字号时需要滚动才能看到，属既有行为，本轮未改。

## 性能优化

- **冷启动少两个主线程阻塞点**：`PlayerSentinel.checkAndReport` 原本在 `Application.onCreate` 主线程上跑（内部两次 `commit` 同步落盘），改到后台线程，并给 `begin/finish/checkAndReport` 加同一把锁，避免后台清理标记与用户点播放的 `begin` 竞争导致漏报一次。
- **诊断任务拆开**：`flushPending / flushEarly / ExitReasonCollector` 原来串在同一个后台 lambda 里，单次上传超时 8 秒、队列最多 5 条，弱网下 `ExitReasonCollector`（补报上次原生崩溃/ANR/LMK）最坏要等 40 秒才轮到，记录经常直接丢失。改为三个独立任务并行提交。
- **活跃统计不再白占线程**：`LaunchPing` 的 3~8 秒随机延迟原本靠线程内 `Thread.sleep`，改为 `Handler.postDelayed`。
- **`episode_progress` 只清一次**：原来每次冷启动都 `clear().apply()` 一次旧进度库（1.2.0-v5 遗留），加一次性标记后不再每次重写。
- **播放页打点收敛**：`PlayerSentinel.stage` 每个调用点都是一次同步落盘，`PlayerActivity.onCreate` 里从 8 次降到 4 次（合并相邻的快速步骤），保留「进入播放页 / 布局完成 / UI初始化完成 / 加载ijk库」四个能区分崩溃阶段的关键点。
- **弹窗单选改局部刷新**：`AdaptiveDialog` 的单选列表点击后原本 `notifyDataSetChanged()` 整表重绑，改为只刷新旧选中与新选中两行（番剧整季上百集时差别明显）。
- **Glide 内存缓存封顶**：`CustomGlideModule` 补上 `setMemoryCache` 与 `setBitmapPool`（memoryClass 的 1/8，4~32MB）。Glide 默认按 memoryClass 比例放大（内存缓存约 0.8×、位图池约 1.6×），在 64MB heap 的低端手表上接近半壁江山，是进列表滑几下就 GC 甚至被回收的原因之一。
- **氛围背景改为预渲染位图（修「关于」页卡死）**：`AmbientBackground` 的径向光晕半径是 `max(w,h)*0.75`，界面放大后几乎铺满整屏，每帧都要对全屏像素做一次渐变求值。实测 dpi 1.6 下进「关于」页单帧耗时 2779ms（`Davey! duration=2779ms`，`Skipped 67 frames`），连续两次弹 ANR。改为把光晕预渲染到 1/4 分辨率的位图（1080×2160 屏上约 0.6MB），每帧只做一次位图拉伸：改后同场景滑动无掉帧告警，渐变观感不变。圆屏模式（MODE_ROUND 的细线圆环）绘制量本来就小，保持原逻辑不动。

### 修复

- **登录「约一天后掉登录」**：根因是扫码登录路径自己写了一套凭证落盘逻辑，只认 `data.refresh_token` 且用 `getString` 取值——写 `refresh_token` 那一步失败时会留下「有 mid/cookies/csrf、但没有续期凭据」的**半登录态**；而启动页在刷新失败时直接清空全部凭证，一次网络抖动就等于登出。修法：扫码统一走 `LoginApi.finishLogin()`（兼容 `data.refresh_token` 与 `data.token_info.refresh_token` 两种结构、过滤 JSON null 被 `optString` 转成的字符串 `"null"`、换号时清理上一账号残留）；刷新结果由 boolean 改为 `CookieRefreshResult` 枚举，**瞬时失败一律保留凭证**，只有服务端明确否定凭证才清理；新增 `CookieRefresher` 提供「启动 + 长驻周期 + 关键请求报未登录」三个续期触发点并带节流。

- **专栏（cv）详情改走 `x/article/view` 单次 API 直取**：原先按 id 长度猜类型——`id<=1e8`（即所有 cv 号）会去抓 `www.bilibili.com/read/cv{id}` 的**整页 SSR HTML** 再手抠 JSON，还要循环跟跳多级 301、并命中 `NetWorkUtil` 对 doctype 响应的重试。而 `ArticleApi.getArticle`（等价于 PiliPlus 的 `articleView`）早已实现却无任何调用方。现在正文由新增的 `ArticleHtmlParser` 从 HTML 转成渲染链吃的段落数组，**失败原样回退网页抓取**（最坏不比改造前差）。

- **正文章节绑定的主线程开销**：每次绑定都跑 4 个正则（URL/BV/AV/CV）并重建 Spannable。改为解析阶段后台预热并缓存在段落上，绑定只做 `setText`；长按复制监听器改为静态单例。

## 技术问题与修法

### 一、番剧进度：服务端其实有**四套**语义不同的进度数据

修这条链路踩的坑，本质是"拿错了字段"或"拿对了字段但理解错了语义"。先把四个数据源摆清楚
（实测账号与剧集：season 1178 / CLANNAD，epid 21448、21449）：

| # | 接口 | 字段 | 语义 | 单位 |
| --- | --- | --- | --- | --- |
| 1 | `pgc/view/web/season/user/status` | `result.progress.last_ep_id` / `last_time` | **本季最近观看的那一集**这一条记录 | `last_time` = **秒** |
| 2 | `pgc/player/web/v2/playurl` | `result.play_view_business_info.user_status.watch_progress.current_watch_progress` | **本次请求的这一集自己**的进度 | **毫秒** |
| 2' | 同上（同响应内） | `watch_progress.last_ep_id` / `last_time` | 季级那一条（与 #1 同义） | `last_time` = **毫秒** |
| 3 | `x/player/wbi/v2` | `last_play_time` / `last_play_cid` | 对 PGC 按季维护；`last_play_cid` 实测恒为 `0` | 毫秒，但不可用 |
| 4 | `x/web-interface/history/cursor` | `progress` / `history.epid` / `history.cid` / `history.oid` | 观看记录列表；**一季只有一条 pgc 记录**（等于 #1） | 秒 |

实测证据（诊断日志摘录）：

```
02:02:09 [服务端进度] epid=21448 v2 watch_progress={current=421000,last_ep_id=21448,last_time=421000}
02:03:26 [服务端进度] epid=21449 v2 watch_progress={current=683000,last_ep_id=21448,last_time=624000}
02:03:53 [服务端进度] epid=21493 v2 watch_progress={current=937000,last_ep_id=21448,last_time=1000}
02:03:30 [季级状态]   season_id=1178 last_ep_id=21448 last_time=624s
```

- 第 2 行：请求第 16 话时 `current=683000`（683 秒，**它自己的**位置），而季级记录还停在第 15 话的 624 秒。
- 第 3 行：季级已换成第 15 话的 1 秒，第 16 话的 `current` 仍是 `937000`。
  ⇒ **服务端按集保存进度**，`current_watch_progress` 是干净的集级数据源；"只留最近一集"只对 #1 成立。
- 第 4 行：同一个 421 秒的位置，在 #1 里是 `421`（秒），在 #2 里是 `421000`（毫秒）。
  ⇒ **两个接口的同名字段单位不同**，这是后面那次事故的直接原因。

### 二、四次迭代与两次翻车

1. **串集（v3 / v4 修掉）**，共三个原因：
   - `history.oid`（avid）被当作集身份。实测同一季多集 **共用同一个 avid**：season 1564 的第 8/9 话
     `history.oid` 都是 `135433`，按 aid 命中会把"上一集刚写下的记录"当成"这一集的记录"。
     现在只认 `cid` / `epid`，`aid` 仅在两者都未知时才兜底。
   - 番剧回退了 `x/player/wbi/v2`。该接口对 PGC 按季维护，且 `last_play_cid` 恒为 0，
     `last_play_cid == cid` 的"严格配对"根本挡不住串集。**番剧一律不回退该接口**。
   - 季级 `last_time` 被单独使用。它只属于 `last_ep_id` 那一集，必须整体配对
     （`last_ep_id == 目标 epid` 才可用）。
2. **本地存档（v5 加、v6 撤）**：v5 曾用本机 `SharedPreferences` 存"每集看到哪"，
   依据是"服务端只留最近一集"这个当时并不完整的结论。v6 确认服务端其实按集保存，
   且本地记录会因换号 / 重装 / 清数据而与服务端错位，于是**整条移除**（旧数据在冷启动时清空）。
3. **单位事故（v6 引入、v7 修复）**：v6 用 v2 的 `current_watch_progress` 作续播数据源，但加了一层
   "秒/毫秒自校准"——看到同响应里 `current == last_time` 就断定"这是秒"，于是 ×1000。
   结果 `421000` 变成 `421000000`，被越界检查丢弃，**每一次续播都归零**，
   表现恰好就是"完全读不到官方客户端已记录的进度"。v7 实测确认这两个字段恒为毫秒，
   删除一切单位换算，只保留一条保护：**位置超过总时长才从头播**。
   同时删掉了多余且有害的"季级泄漏守卫"（它会把"本集进度恰好等于季级位置"的巧合误判成泄漏并重启）。
4. **审计（v8）**：对这条链路做了一次完整审计，落实 11 项发现，其中影响行为的两项：
   - 第一次看新集时不再白扫 5 页观看记录（v2 已明确该集无记录时，记录里那条 pgc 条目必然属于别集）；
   - v2 网络层失败直接快速失败，不再对 v1 重复一轮重试（`getJson` 内部已带约 5 次重试，双倍等待无意义）。

### 三、当前实现（读 / 写）

**读（续播位置），按优先级：**

1. v2 `playurl` 的 `watch_progress.current_watch_progress`（毫秒）——本集自己的位置；
2. 同一响应里 `last_ep_id == 本集 epid` 时的 `last_time`（毫秒）——集级字段为空时的兜底；
3. 季级状态接口（秒 → 毫秒），仅在 1/2 都拿不到时查（v1 回退、字段缺失）；
4. 观看记录里本集自己的条目（cid/epid 全身份命中），仅在 v2 没有该字段时扫；
5. 都没有 → 从头播。**番剧不回退 `x/player/wbi/v2`。**

请求侧要点：取流改用 `pgc/player/web/v2/playurl`（v1 的 `result` 里没有任何进度字段），
带上 `ep_id` / `season_id`；用响应里的 `episode_info.ep_id` / `cid` 做服务端侧身份校验
（响应 cid 与请求 cid 不一致就丢弃进度字段）；`epid` 缺失的入口（历史/搜索只有 cid）会用回显的
`ep_id` 补齐，否则播放器的心跳上报会整条跳过。v1 仅在"v2 正常返回但取不到 durl"时作为兜底。

**写（上报）：** 心跳 `x/click-interface/web/heartbeat`（`type=4`，带 `epid` / `sid` / `played_time`，
播完发 `played_time=-1`）。周期上报 5 秒一次，外加退出 / 切后台 / 播完各一次并去重。
上报前重建 Cookie 头、csrf 与 mid 一律从实时 Cookie 派生 —— 心跳接口对未登录请求同样返回 `code:0`，
只看返回码无法判断是否真的落库，因此诊断打开时会在播放 25 秒后回读一次服务端做端到端确认。

**详情页不再写观看记录：** 服务端对本季只维护一条记录，没播放过就写，会把"上次看到第 N 话"
指向一集没看过的内容（官方客户端的续播入口随之错位）。记录一律由播放器心跳写入。

**本地不保存任何观看进度。**

### 四、诊断怎么开（默认关闭）

`1.2.0fix` 起番剧进度诊断**默认关闭**（不写诊断文件、不发额外回读请求）。
需要排查时：**设置 → 实验室 → 调试 → 番剧进度诊断** 打开，复现一次后取文件：

- `Download/ReBiliDiag/progress-diag.txt`（有存储权限时）
- 否则 `Android/media/com.RobinNotBad.BiliClient.re/progress-diag.txt`

文件里的 `[服务端进度]` / `[续播结果]` / `[回读自检]` 三行分别对应"服务端给了什么"、
"最终采用了哪个来源"、"上报是否真的落库"。

### 五、同一版本里的其它技术问题

- **评论卡片语言**：子评论（楼中楼）与"UP 主觉得很赞"原先用 `?attr/biliCardBackground`
  （主卡片的渐变描边语言），在评论区看起来像"模糊的灰盒子"；改用与搜索页同 token 的
  `background_card_soft`（10dp 圆角 + 0.5dp `#363636` 描边）。
- **搜索页遮挡**：历史记录 / 建议面板与结果列表在布局里同位叠放且底色不透明，
  关键词非空时一旦显示就会整块盖住结果；现在关键词非空且无建议时不再弹出面板。
- **切后台丢结果**：搜索结果只存在内存里，页面重建必然为空；新增"最后一次搜索词"记忆
  （进程内重建走 `savedInstanceState`，冷启动恢复链走 `SharedPreferences` + `EXTRA_RESUME_RESTORE`
  标记），只在恢复场景重放。
- **圆屏播放页**：右侧按钮列原先被上下横条用 `layout_below/above` 夹取，高度吃紧时最后一个按钮被裁掉；
  改为 `WRAP_CONTENT` + 垂直居中并给可横向滚动的菜单行加宽度上限。弹幕按钮的可见性统一由
  `player_ui_showDanmakuBtn` 决定（此前 onPrepared / 退出听视频模式两处口径不一致）。
- **登录态口径统一**：新增 `NetWorkUtil.getLoginMid()` / `getLoginCsrf()` / `isLoggedIn()`，
  一律从实时 Cookie 派生。旧实现读本地快照，Cookie 轮换或换设备后错位，
  表现为"明明登录了却读不到记录 / 上报被静默跳过"。经验与硬币记录的本地累积（`UserLogStore`）
  同样改用该口径做账号隔离。
- **版本名比较**：`VersionNameUtil` 原先要求修复版后缀带连字符（`-fix`），
  现在 `1.2.0fix` 这类写法也能解析（`1.2.0 < 1.2.0fix < 1.2.1`），不再退化到 versionCode 兜底。

#### 1.1.0-fix1 修复了什么

**搜索建议（三连修）**

- **建议永远为空**：B站 suggest 接口的词表从 `data` 移到了 `result` 字段，旧解析取 `data.tag` 恒为空。
  现改为 `result`/`data` 双字段兼容解析，接口再挪字段也不会悄悄失效。
- **建议卡片回弹**：点击联想词后卡片重新弹出、盖住搜索结果——点击会经 `setText` 触发一次新的建议
  请求，旧代码没有在搜索执行时作废它。现搜索执行期间整条建议链路被屏蔽（含输入法延迟 commit），
  并作废在途请求、主动收起卡片。
- **建议结果被整包丢弃**：结果回调以"输入框此刻是否持有焦点"为显示条件，而部分 ROM 输入法
  （一加13 / ColorOS16 实测）在组词/候选期间会让输入框短暂失焦，导致建议永远不出现。
  现改为代际令牌校验——只显示最新一次输入的响应，同时防乱序竞态覆盖。

**搜索后输入法无法拉起（一加13 / ColorOS16）**

- 搜索执行时 `clearFocus()`、完成后 `requestFragmentFocus()` 把焦点交给结果列表；第一次点击输入框
  只恢复焦点不拉起键盘，第二次才正常；而键盘弹出引发的列表滚动回调又会触发焦点抢占，把刚弹出的
  键盘顶掉。现改为：输入框点击时主动补一次 `showSoftInput`；输入框持有焦点期间
  `requestFragmentFocus` 不再抢占焦点（手表滚轮导航不受影响）。

**低性能设备（W527 手表）转场动画丢失**

- 诊断：关于页新增动画缩放显示（无开发者选项的设备无法查看系统设置）。实测 W527 ROM 将
  `TRANSITION_ANIMATION_SCALE` 设为 0——系统级页面转场被整体禁用，该设置从应用侧无法恢复
  （需 adb / 系统权限）。
- 缓解：页面内容就绪后按"帧数"驱动渐入（帧数 + 时间双上限），把占位屏 → 内容的硬切变成过渡。
  按帧数而非时间驱动是关键：单帧绘制耗时会超过动画时长，时间型淡入在首帧画完时就已结束。

#### 1.0.2-fix1 具体修了什么

**观看进度上报（番剧续播进度写不进服务端）**

- 上报凭证不再读本地快照 `csrf` / `mid`，改为从实时 Cookie（`bili_jct` / `DedeUserID`）派生。
  原实现下 Cookie 轮换后两者会错位，导致**所有 POST 返回 `-111`，而 GET 一切正常** ——
  表现为「只有观看记录上报静默失效」，且同一份代码在不同设备/登录时机表现不同。
- 心跳接口的 `start_ts` 夹到 `>= 0`，避免设备时钟偏慢时被服务端判 `-400`。
- 上报前若 `mid` 为 0，用实时 Cookie 补一次解析，避免已登录却被判未登录。
- 番剧续播进度在 `x/player/wbi/v2` 取不到时，兜底走观看记录列表接口。
- WBI 密钥取成功后才落 `last_wbi`，缓存为空强制刷新，避免一次取密钥失败污染当天所有 WBI 请求。

**跳转后弹幕卡死 / 退出播放后整个应用卡死**

- 弹幕绘制线程不再轮询 `ijkPlayer.getCurrentPosition()`。该回调跑在弹幕同步/绘制线程上，
  而它是会取播放器原生锁的 JNI 调用 —— 既是「弹幕时间轴被旧位置拽住」的直接原因，
  也是绘制线程卡住后主线程 `release()` 内 `join()` 无限等待、**整个应用卡死**的共因。
- 退出链路（`finish` / `onPause` / `onStop` / `onDestroy`）与 MediaSession 状态更新
  不再在主线程调用 `getCurrentPosition()`。
- 弹幕未 `prepared` 时的 seek 请求会暂存、prepared 后补做；新增带观察窗与冷却的弹幕时间轴校正。
- DanmakuFlameMaster 的 `Thread.join` 加 2s 超时，避免主线程被无限阻塞。
- 所有 `TimerTask` 加异常兜底（TimerTask 抛未捕获异常会永久终止整个 Timer，
  导致进度条与进度上报一起静默失效）。
