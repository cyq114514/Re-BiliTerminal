## 批次九：空评论区里发出的评论不显示（带图更明显）

- 现象：评论区原本一条都没有时，自己发出的**带图**评论显示不出来（个别机型表现为一张空卡片），
  再发一条纯文字评论后两条才一起出现。视频评论区与动态评论区表现一致。
- 根因是三处叠加：
  1. `notifyReplyInserted` 在"列表只有头部"的状态下用 `notifyItemInserted` 插入首条，
     这种状态下 RecyclerView 偶发不会真正重新布局 → 新评论不可见；
  2. B站评论列表有延迟：刚发完立刻拉取常常还拿不到自己那条，一次 refresh 就会把本地插入的评论顶掉；
  3. `/x/v2/reply/add` 返回的 `reply` 里不一定带 `content.pictures`，
     本地卡片的 `pictureList` 为空 → 带图评论渲染成"没有图"的空卡片。
- 修法：
  1. 空列表插首条改为 `notifyDataSetChanged()`（只有 0→1 这一种情况，代价可忽略）；
  2. `ReplyFragment` 记住本地刚发出的根评论（最多 20 条），每次 `refresh()` 成功后把服务端还没返回的
     那几条补回列表顶部（按 rpid 去重）；列表还没就绪时也先记下来，等列表加载完补上；
  3. `WriteReplyActivity` 把本次上传成功的图片地址挂到本地这条评论的 `pictureList` 上，卡片立刻有图；
     另外补了 `resultReply == null` 的兜底（服务端 code=0 却没带 reply 时不再空指针）。
- 追加两处（用户反馈"数量读得到但加载不出来"、截图是专栏详情页）：
  4. `OpusInfoActivity.onEvent(ReplyEvent)` 里那一行 `notifyReplyInserted` 被注释掉了——专栏页发完评论
     只更新了「共 N 条评论」，列表根本不插这条，要退出重进才可能看到。已恢复转发（带空判断）。
  5. 热度排序（`mode=3`）对"只有一两条新评论"的评论区经常返回空列表，而「共 N 条评论」是另一个接口
     给的数字，于是表现为"读得到数量但加载不出来"。现在 `refresh()` 遇到"接口成功 + 列表为空 +
     count > 0 + 非时间排序"时会换 `mode=2` 再拉一次，拉到了就把排序状态一并切过去（按钮口径一致）。
- 影响面：`ReplyFragment`、`WriteReplyActivity`、`OpusInfoActivity`；`ReplyApi` 增加了调试字段。

## 新增开关：显示详细接口错误（实验室 → 调试，默认关闭）

- 打开后，接口失败不再只有一句短提示，而是弹「接口错误详情」页（可长按复制），内容包括：
  接口名与请求参数（`type`/`oid`/`mode`/`offset`）、B站返回码与 message、原始返回片段（截断 800 字符）。
- 评论区还有一个专门场景：接口成功但**一条都没拉到、而头部显示共 N 条**时，也会弹这个详情页，
  并附上"改用时间排序重拉"那一次的结果——正是"读得到数量但加载不出来"需要的证据。
- 实测证据（用户反馈的那条专栏）：`type=11 oid=413114181` 在 mode=3 与 mode=2 下 B站都返回
  `replies: []`、`is_end: true`，即**服务端就是 0 条**，不是解析丢数据；而头部计数来自 `opus.stats.reply`，
  与评论列表索引不同步（刚发的评论要等审核/索引后才进列表）。
- 因此补了两层兜底：① 换排序仍为空时，按 `type` 兜底链 `17 → 12 → 1` 各试一次（接口给的 `comment_type`
  与实际存放评论的类型不一定一致，成功后把 `type`/`replyType` 一并切过去，发评论/点赞口径同步）；
  ② 全部仍是空时给一次性人话提示（审核中/被折叠/不属于当前评论区），不再只留空白页。
- 实现：`ReplyApi.ReplyResult` 新增 `endpoint`/`detail` 字段；`MsgUtil.apiErrorDetail()` 负责按开关走
  短提示或详情页；`ReplyFragment.showLoadErrorMsg()` 与 `refresh()` 的空结果分支接入。

## 批次八：弹幕每隔几秒整体右跳的修复

- 现象：播放时弹幕每隔几秒整体向右跳一下，随后继续向左飘，循环往复。
- 根因：`updateTimer` 回调里拿播放器位置 `timer.update(pos)` 强行写 DFM 的时钟。
  DFM 的时钟是**墙钟驱动**的（`DrawHandler.syncTimer` 每帧按 `SystemClock` 推进 timer，基准是
  `mTimeBase`），而 `timer.update()` 只改"当前值"、不改 base：下一帧 `syncTimer` 发现 timer 落后，
  又按 `mCordonTime` 一帧帧把时钟推回去。于是"被拽回去（右跳）→ 又被推回来（左飘）"无限循环；
  250ms 兜底通道那条"偏差 >800ms 就 seek + 2s 冷却"又在旁边补刀，每 2 秒多给一次明显的右跳。
- 修法：① `updateTimer` 改成**只读不写**（连播放器位置都不读，避免原生锁）；
  ② 兜底通道改成只在两类事件上动时间轴：**卡顿恢复**（墙钟过了很久、播放位置却几乎没变）
  按当前播放位置重 base 一次；**极端偏差**（>2s 且持续 3 秒）才纠一次、20 秒冷却。
- 保留的对齐点：起播/prepared、用户跳转（进度条、±N 秒、D-pad、双击、隐藏后重新显示）、暂停恢复。
- 影响面：`PlayerActivity.updateTimer()` / `syncDanmakuIfDrifted()` / `resetDanmakuTick()`。

## 批次七：无极调音 + 快进快退按钮 + 反馈群号更新

## 无极调音（播放页，长按音量按钮打开）

- 需求来源：凉腕播放器（`com.aliangmaker.media`）的"无极调音"。那边的实现是两套：手势拖动走
  `AudioManager.setStreamVolume()`（最终仍被系统档位量化），以及设置里的 `volume`（0–100）走
  `ijkMediaPlayer.setVolume(v, v)`——后者才是真无极（纯软件增益）。
- 我们的做法：只做软件增益这一层。`ijkPlayer.setVolume(gain, gain)` 是采样级线性乘算
  （原生方法在 `libijkplayer.so`，已确认注册），和系统音量是乘算关系；增益上限 1.0，
  不做放大（>1.0 会削波失真）。
- UI：长按底部音量 +/− 弹出 `layout_volume`（照倍速浮层的样式做），SeekBar 0–100、1% 一档，
  拖动实时生效，松手 4 秒自动收起；单击音量按钮仍是系统音量 ±1 档，老习惯不变。
- 持久化：`player_volume_gain`（默认 100%）；播放器重建（切清晰度/换 P/听视频模式）后
  由 `onPrepared()` 重新套用。
- 验证：真机 0% / 37% / 50% / 100% 听感与数值一致；「音频输出」默认与 OpenSL 两条路径都要过一遍；
  切清晰度、听视频模式、后台播放后增益保持。

## 快进/快退按钮

- 底部按钮行新增 `±N 秒`（文字按钮，避免手表上图标看不清）；N 读「快进快退秒数」设置（默认 10），
  与双击快进共用同一项。
- 逻辑复用 `seekToPosition()`（内部已同步弹幕零点），并补了边界 clamp——原来 D-pad 那条没夹
  0/duration，多按几下会把负数交给 seekTo。
- 直播模式没有可 seek 的进度，两个按钮直接隐藏。

## 横滑调进度（播放画面手势）

- 交互：单指在画面上左右滑 → 中间实时显示"快进到 01:23 / 09:41（+45s）"，**松手才 seek**；
  满屏宽度对应 `duration/6`（夹在 30s~300s），短视频整屏就是全片。
- 接管条件（缺一不可）：单指、未放大画面、非长按 3x、非双指缩放；水平位移先过 8dp，
  且横向位移 ≥ 纵向的 1.5 倍（斜滑不误触）。放大画面后单指拖动继续走 `videoMoveBy`（拖画布），
  不能抢——否则"放大后挪画面"就没法用了。
- 为什么松手才 seek：边拖边 seek 会让 ijk 反复重建缓冲，手表上直接卡成幻灯片。
- 开关：内置播放器设置 →「横滑调进度」（默认开），老用户不适应的可以关掉。
- 与既有手势的关系：单击/双击/长按 3x/捏合缩放/双指移动全部保留；拖动期间把
  `gesture_click_disabled` 置位，松手后的那次单击不会顺手把控制栏切走。

## 批次六：界面边距 / 圆屏适配下，新版美学装饰层没铺满屏幕

- 现象：设置里调过「界面边距」，再开「圆屏适配」，页面四周会留出一圈黑边，屏幕左下那枚粉色装饰圆
  还会在内容区底边处被硬切一刀——看上去像“新版美学 UI 只覆盖了中间一块”。
- 根因：「界面边距」被加在 `DecorView` 上，而氛围背景层（`AmbientBackground`）与自定义背景底图
  都是挂在 `DecorView` 上的装饰层。ViewGroup 的子 View 一律排布在自己的 padding 之内，
  所以边距一加在 `DecorView`，装饰层就跟着被压进内容区，四周只剩窗口底色（黑）。
  圆屏模式底部还要多留 3% 的“下巴”，那一刀切得尤其明显。
- 修法：边距下沉到 `android.R.id.content`（内容照样内缩），装饰层恢复整屏铺满；
  Snackbar 也改挂内容容器，避免提示条贴屏底（圆屏设备上正好落进下巴）。
- 影响面：`BaseActivity.applyContentPadding()` / `onEvent()`；`window_width`、`window_height`
  的语义不变，圆屏下标题、时钟、刷新按钮的重排逻辑不受影响。

## 圆屏适配直接沿用直屏的背景风格（去掉圆屏专属画法）

- 现象：直屏模式整页是粉色氛围，开了「圆屏适配」却变成纯黑底 + 右上/左下两圈粉线，
  像是"没上新的 UI 皮肤"，和直屏完全是两套观感。
- 根因：`AmbientBackground` 把两种模式做成了互斥——`MODE_RADIAL`（直屏）才画径向粉色光晕，
  `MODE_ROUND`（圆屏）只画两枚装饰圆环，光晕不画。
- 修法：**直接删掉圆屏专属画法**（`MODE_ROUND` / `drawRing` / `setMode` 一并移除），
  全局只有一种背景 = 直屏那套顶部粉色径向光晕；「圆屏适配」只负责布局（标题/时钟居中、
  边距与底部下巴），不再改视觉风格。
- 影响面：`AmbientBackground`（去 mode）、`BaseActivity.installAmbient()`、`SplashActivity`；
  开屏页的氛围层同样统一走这一套。

## 批次五：界面动画开关 + 启动检查更新

## 「关闭界面过渡动画」开关（偏好设置 → 视觉，默认关闭）

- 打开后：Activity 转场、开屏页到首屏的转场、菜单页自带的下滑转场、以及页面渐入渐出/交叉淡入全部置零。
- 实现：BaseActivity 覆写 startActivity 的三个重载（含 registerForActivityResult 走的三参版本）与
  startActivityForResult 的两个重载、外加 finish()，统一在开关打开时 overridePendingTransition(0, 0)；
  InstanceActivity 的菜单页显式转场加开关判断；AnimationUtils 的 fadeIn/fadeOut/crossFade 直接落位。
  不逐个调用点改，避免漏掉某个入口还带动画。
- 默认关闭（动画照常），切换即时生效（每次调用都实时读偏好，不需要重启）。

## 「启动时检查更新」开关（偏好设置 → 功能，默认开启）

- 默认开启（SplashActivity 读该偏好时的兜底值就是 true）。每次冷启动在首屏 resumed 之后调用 UpdateManager.autoCheck：
  发现新版本时弹与该弹窗原样式一致的 AdaptiveDialog（立即更新 / 忽略此版本 / 以后再说），
  「立即更新」进入「检查更新」页走下载-校验-安装链路。
- 检查源顺序：update.json 直连 → 手动选择的镜像 → 没选镜像时依次试内置镜像（ghfast.top、gh-proxy.com）
  → GitHub Releases API 兜底；下载地址跟随真正取到元数据的那个源。手动选了镜像则只跟用户的选择。
- 启动回调由"单个 Runnable"改成"回调列表 + 宿主 Activity"：启动弹窗与启动检查互不覆盖；
  执行时优先取当前栈顶页，恢复链场景不会把弹窗弹到已被盖住的页上。
- 菜单页原有的自动检查保持不变（那是一次用户主动导航，不属于"启动"）。

## 批次四：崩溃上报过滤

## 只上报"重要且可行动"的崩溃

- **现象**：后台 50 条 1.2.2 记录（33 台设备）里约 90% 是噪音——播放哨兵 20 条（多数是后台/内存回收）、
  lmk 11 条、实验室主动触发的测试崩溃 4 条、没有一帧本仓库代码的系统异常若干；真正能定位到代码的只有 5 条左右。
  同机同崩溃还会反复进来（没有指纹去重）。
- **改法**：新增 util/CrashFilter，在**入队之前**统一裁决（本地留档不受影响）：
  1. 系统压力类（lmk / freezer / resource）完全不上报，也不再生成崩溃文件——真 OOM 会以
     java.lang.OutOfMemoryError 走 Java 崩溃链路；
  2. 实验室「主动触发崩溃」不上报；
  3. 播放哨兵只保留三类强信号：连续异常 ≥2 次、停在 native 高危阶段（加载ijk库/配置显示/设置数据源/已提交准备）、
     或短会话（≤120s）异常收尾；「首帧就绪 + 长时间停留」这类看了一晚上被回收的记录不再报；
  4. Java 崩溃的堆栈里没有任何本仓库代码帧（含随仓库编译的 ijk / DanmakuFlameMaster / brotlij）→
     判为系统或环境异常，丢弃；java-early 例外（它本来就发生在框架初始化阶段）；
  5. 24 小时内同指纹（类型 + 异常类 + 页面 + 栈顶业务帧 + 版本）只上传一条，重复次数追加到 message 末尾
     （不加数据库字段，避免 Supabase 表约束 4xx 拒收）。
- **队列**：待发上限 5→8；文件名带 p0_ / p1_ 前缀，补发时先 P0 后 P1；队列满时先淘汰 p1（哨兵），
  P0 不再被弱信号挤掉。
- **可观测**：崩溃页会多显示一行「本次未自动上传，原因：xxx，仅本地留档」；本地 crash-*.txt（20 份循环）
  与崩溃页「重新上报未发出的记录」保持不变。
- **回归验证**：用同一批 50 条记录回放规则，过滤后剩 8 条，且全部是真 bug / native / ANR 类线索
  （选图 ActivityNotFound ×2、前台服务超时、Glide destroyed activity、4 条强信号哨兵）。

## 批次三：开屏提速

## 开屏慢的根因：两个 B 站请求被串在进首屏之前

- **现象**：冷启动时开屏打字动画要停一会儿才进首页；弱网/手表上尤其明显，断网时更久。
- **根因**：SplashActivity 的后台线程在 startActivity 之前串行做两件事：
  1. CookieRefresher.check(true) → passport.bilibili.com/x/passport-login/web/cookie/info（每次启动强制）；
  2. CookiesApi.checkCookies() → GET https://www.bilibili.com/。

  两条都是完整 RTT（DNS + TLS + 请求），而 OkHttp 的连接/读超时是 8s/16s，断网时等于要等两个超时
  才走兜底；之后还 postDelayed(100) 才 startActivity。同时 BiliTerminal.onCreate 一上来就并发 6 个
  网络任务（3 个崩溃补发、播放哨兵、动态未读、私信未读），与开屏请求抢 DNS/TLS/带宽。
- **改法**：
  1. 启动续期改 CookieRefresher.check(false)：它本来就有 1 小时节流，而 startPeriodicCheck() 已每小时
     查一次，启动时强制再查是重复的 RTT；
  2. 有网络时**本地决策一完成就进首屏**，Cookie 续期/刷新/更新检查全部挪到首屏之后（runStartupChecks）；
  3. 去掉两条退出路径上的 postDelayed(100)；
  4. 无网络时用 ConnectivityManager.getActiveNetworkInfo() 瞬时判定，直接走"恢复链/本地库"兜底，
     不再等超时（这也是断网冷启动"卡在开屏"的来源）；
  5. BiliTerminal 里崩溃补发、播放哨兵、未读数检查统一延后 2 秒（ExitReasonCollector 只读本地，保持立即）；
  6. 保留唯一的阻塞例外：首启缺 buvid3 时仍然先补齐 Cookie 再进（一次性代价）。
- **观测**：adb logcat -s startup 会输出 MultiDex.install xxms、Application.onCreate 完成 xxms、
  进入首屏：距离开屏 onCreate xxms（online=true，bootstrap=false），可直接对比改动前后。
- **行为变化**：登录失效的提示从开屏挪到首屏弹出；在线但接口失败不再阻止进入（由首页自己提示重试）；
  离线兜底、整链恢复、首启设置页跳转均保持原样。

## 回归修复：深夜提醒 / 免责声明被首屏压在下面

- **现象**：开屏提速后，"深夜提醒"要在点一下菜单之后才弹出来（本来应该一进首页就弹）。
- **根因**：这两个弹窗在 AppInfoApi.check 里是 startActivity(DialogActivity)。旧流程里它跑在
  "首屏 startActivity 之后"（postDelayed 100），所以稳定地盖在首屏上；提速后改到首屏之前/同时发起，
  两者竞争——弹窗先入栈、首屏后入栈，弹窗就被压在下面，只有下一次页面切换才浮上来。
- **修法**：把弹窗从 AppInfoApi.check 里拆出来成 showStartupDialogs（纯本地判断），
  交给新增的 BiliTerminal.runAfterFirstPageResumed 在**首屏 Activity resumed 之后**执行
  （延迟 250ms，给"恢复链"连续入栈留余量）；网络部分 checkVersion 仍留在后台。
  挂载点放在 startMainPage / startRestoreChain 的 UI 线程块内、startActivity 之前，
  避免后台线程迟到导致这一次漏弹。

## 批次二：老设备崩溃 / 上报 TLS / 弹幕漂移

> 本轮来自三路输入：一位官方 1.2.2 用户反馈的 NoSuchMethodError 截图、后台 50 条 1.2.2 崩溃记录，
> 以及一位 Android 4.4 用户上传的 8 张崩溃控制台截图。所有根因都先在本仓库的 release DEX、
> R8 mapping 与 DanmakuFlameMaster 源码里验证过，再动手改。

## 播放页在 Android 4.4/5.0 打不开：EventBus 反射踩到 API 21 的 MediaSession

- **现象**：4.4 用户每次点播放都闪退，崩溃页显示 Unable to start activity ComponentInfo{...PlayerActivity}，
  Caused by: P1.f: Could not inspect methods of ...PlayerActivity，
  再往下是 NoClassDefFoundError: android/media/session/MediaSession。
- **根因**：MediaSession 是 API 21 才有的系统类。播放页虽然已按 SDK 判断才初始化它，但
  MediaSession.Callback 匿名类要读 PlayerActivity.mediaSession 私有字段，D8 为兼容 API<24 的
  nest 机制会生成**返回类型为 MediaSession 的合成访问器**——反编译 release DEX 可见
  -$$Nest$fgetmediaSession(PlayerActivity) -> Landroid/media/session/MediaSession;，
  R8 mapping 里也同名可查。而 BaseActivity.onStart 里 EventBus 3.2.0 要 getMethods() 反射注册
  订阅者，解析到这个返回类型时老系统直接抛 NoClassDefFoundError，Activity 起不来。
- **修法**：新增 helper/MediaSessionHelper，把 MediaSession/PlaybackState/MediaMetadata 全部收进去；
  播放页只持有该 helper，并在所有访问点前置 Build.VERSION.SDK_INT >= LOLLIPOP 短路
  （hasMediaSession()），API<21 的设备连字段都不去读。
- **验证**：重新反编译修复后的 release DEX，MediaSession 只出现在 helper/MediaSessionHelper
  （含其回调内部类）里，PlayerActivity 零引用；PlayerActivity -> MediaSession 的合成访问器数量为 0。

## 老设备崩溃报告一条都传不上来：上报专用 OkHttp 漏了 TLS 兼容

- **现象**：4.4 设备的崩溃控制台连续 补发失败 xxx.json（第 2/3/4/5 次，HTTP -1），
  日志里是 SSLHandshakeException: tlsv1 alert protocol version。
- **根因**：全站网络统一走 NetWorkUtil.setOkHttpSsl（API≤22 时启用 TLS1.1/1.2），但 CrashUploader
  自己 new 了一个裸 OkHttpClient，没套这套兼容 —— 老系统默认只谈 TLSv1.0，被服务端（Supabase）
  拒绝，于是**老设备的崩溃报告全部丢失**。后台 50 条记录里没有一条 sdk_int <= 21，正是这个原因。
- **修法**：CrashUploader.client() 复用 NetWorkUtil.setOkHttpSsl，失败时退回系统默认
  （不能因为 TLS 初始化失败反而不上报）。

## 弹幕越看越偏：弹幕引擎自己走时钟，零点还和视频对不上

- **现象**：弹幕时间轴与进度条不一致；长视频、低帧率手表、切清晰度/切听视频后尤其明显，
  有时是"一开始就差几秒"，有时是"越看越偏"。
- **根因（四层，都在 DanmakuFlameMaster 源码里可查）**：
  1. DanmakuView.start() 内部就是 start(0)，零点 = **"DFM 准备好的那一刻"**。而弹幕是异步下载的
     （长视频 11 段串行），起播时往往比取流慢 → 整场固定偏后 N 秒。
  2. 每次 prepare() 都把 DrawHandler.mTimeBase 重置成当前 uptimeMillis()；弹幕空闲时
     （mInWaitingState/nothingRendered，弹幕间隙 500ms 就会出现）syncTimer 会执行
     timer.update(startMS - mTimeBase)，等于把时间轴直接拽回 0。
  3. DFM 时间轴按墙钟 + 渲染帧率推进（每帧 d 被钳制在 [mFrameUpdateRate, mCordonTime]），
     低帧率设备上会越走越慢；而播放器位置从来没有被反馈回去。
  4. 旧纠偏 syncDanmakuIfDrifted 只认"时间轴完全停住 + 播放器领先"，慢漂移永远不触发，容差还是 2 秒。
- **修法**：
  - onPrepared 改用 start(anchor)（续播/换清晰度用 progress_history），不再 start(0)；
  - prepared() 回调**无条件**按当前播放位置 seek 一次（原来只处理 pendingDanmakuSeekMs），
    并补一次 setSpeed——此前 handler 未 prepared 时 setSpeed 会被静默丢弃，倍速播放时弹幕时钟停在 1x；
  - updateTimer 重新启用：**只读** 250ms 定时器维护的 volatile video_now（绝不碰 ijk 的
    getCurrentPosition() 原生锁），偏差 >500ms 且连续两次采样成立才 timer.update(pos)；
  - syncDanmakuIfDrifted 从"卡死判定"改成绝对偏差判定（连续 3 个 tick >800ms，冷却 2s）；
  - seekDanmakuTo 在 handler 已 prepared 时清掉 pending，避免下次 reload 用过期位置再跳一次；
  - 每 5 秒打一条 弹幕同步 player=… danmaku=… diff=… 诊断日志，真机上可直接验证。
- **未做**：参考仓库（凉腕播放器）的"弹幕随倍速"开关。DFM 的时间轴与滚动速度是耦合的
  （setSpeed 同时缩放时间轴），做成开关要么时间轴不跟、要么滚动速度不对，收益低于风险。

## 转发/发动态在 Android 4.4/5.x 崩：List.sort 是 API 24 才有的方法

- **现象**：官方 1.2.2 用户反馈弹窗：java.lang.NoSuchMethodError: No virtual method
  sort(Ljava/util/Comparator;)V in class Ljava/util/ArrayList; or its super classes。
- **根因**：DynamicApi.parseAtContent 里用了 indexesList.sort(...) —— List.sort 是 Java 8 默认方法，
  Android 上 API 24 才有；本项目 minSdk 19 且没开 core library desugaring，老设备必崩。
  反编译确认这是**全 DEX 唯一一处** sort(Comparator) 调用。
- **修法**：改 Collections.sort(...)；顺带给 parseAtContent 补 atUserUid == null 兜底。
- **路径**：视频详情页「转发」→ DynamicApi.relayVideo → buildContents → parseAtContent，
  即用户在小屏上点转发就必然触发。

## 线上 50 条崩溃记录里能定位到代码的三处

- EditProfileActivity 选图 ActivityNotFoundException（4 条，sdk27 手表没有相册）：先 resolveActivity
  探测，再降级 ACTION_GET_CONTENT，最后 try/catch 提示。
- BangumiInfoFragment Glide You cannot start a load for a destroyed activity（1 条）：异步回调回来时

  onStartCommand 满足，主线程一忙就超时；改为 onCreate 先挂占位通知，onStartCommand 再换成真实内容。
- **哨兵降噪**：同一（最后阶段 + 停留分钟档 + 连续次数）24 小时内只上传一次，本地仍每次留档；
  后台 20 条同类「播放异常退出」不再淹没真正的新崩溃。
- **不修**：BadParcelableException（Android 11 系统 InsetsSourceControl 自身的问题）、
  DeadSystemException、reason:3 低内存回收、reason:14 freezer、实验室里主动触发的测试崩溃。

## 批次一：收藏夹 / 下载 / 缓存播放 / 首页推荐

> 本轮改动面向 2026-10 B 站接口调整，四个独立问题：收藏夹、下载失败、缓存播放崩溃、首页推荐。
> 全部改动均在真机接口层面先做过对照实验，结论写在各自的「根因」里。

## 收藏夹：整条链路迁到 x/v3/fav/*

- **现象**：收藏页只剩「创建收藏夹」和「图文收藏夹」两张卡片，视频收藏夹列表为空；页面不报错、不转圈，就是不显示。
- **根因**：视频收藏夹这条链路三处都用的是老接口，B 站已经换成 `x/v3/fav/*`，老接口对登录态不再返回数据：
  1. 列表 `space.bilibili.com/ajax/fav/getBoxList` —— 请求成功但 `data.list` 为空（这是"只剩图文收藏夹"的直接原因：图文收藏夹走的是 `api.bilibili.com` 的 `polymer/.../opus/favlist`，域名和接口都是新的，所以只有它活着）；
  2. 内容 `x/space/fav/arc?fid=` —— 已被官方前端淘汰；
  3. 收藏/取消收藏 `medialist/gateway/coll/resource/deal|batch/del` —— 线上直接返回 `-401 未授权`（容器内实测，匿名探测也是 -401，说明是接口本身下线而不是登录态问题）。
- **修法（对齐 PiliPlus `lib/http/fav.dart`）**：
  - 列表 → `x/v3/fav/folder/created/list`（分页，`pn/ps/up_mid`），字段 `id=media_id / fid / title / cover / media_count / attr`；
  - 内容 → `x/v3/fav/resource/list`（`media_id/pn/ps/order=mtime/type=0/tid=0/platform=web`），只保留 `type==2` 的普通视频稿件，`attr!=0`（失效视频）显示为「已失效」；
  - 增删 → `x/v3/fav/resource/batch-deal`（`resources=<aid>:2` + `add_media_ids|del_media_ids=<media_id>`）。
- **关键点：媒体身份从 fid 变成 media_id**。v3 只认 media_id，因此：
  - 收藏夹列表接口直接给 media_id，走正常路径；
  - 老入口/老 Intent 只有 fid 时用 `FavoriteApi.mediaIdOf(mid, fid)` 兜底换算（`media_id = fid*100 + mid 后两位`，实测 `636926+73→63692673`、`40267484+32→4026748432`，老代码里 addFavorite 也是这么拼的）；
  - `getFavoriteState` 的响应补了 `id` 字段，收藏选择页据此传 media_id。
- **显示**：v3 不再返回收藏夹容量上限（`max_count`），卡片改为只显示数量（老数据里还有上限值时沿用旧样式，不会出现 `307/0`）。
- **影响文件**：`FavoriteApi`、`FavoriteFolderAdapter`、`FavoriteVideoListActivity`、`AddFavoriteActivity`、`FolderChooseAdapter`。

## 下载：不是网络问题，是自家域名白名单把 PCDN 地址拦死了

- **现象**：新版下载器缓存视频必弹「下载失败，网络错误」。
- **根因**：`DownloadService.validateMediaUrl` 只放行 `bilivideo.com / hdslb.com / bilibili.com / 两个 akamai 镜像`，而 B 站现在对 1080P 的 mp4（`format=mp4720`）与 DASH 流下发的首地址大量是 PCDN：
  - `https://xxx.edge.mountaintoys.cn:4483/...`（第三方 PCDN 域）
  - `https://xyxxx.mcdn.bilivideo.cn:8082/...`（B 站自有 PCDN，但白名单只写了 `.bilivideo.com`）
  抽样 12 条热门视频，**10/10 命中**，主地址全部判 false → `downFile` 第一步就 `return ERR_NETWORK`。
  对照实验：老下载器 `DownloadActivity` 直接 `NetWorkUtil.get(url)`、不做域名校验，所以能下。
- **修法（PiliPlus `getCdnUrl` + `DownloadManager` 同思路）**：
  1. **候选地址列表**：取流时把 `durl[].url + backup_url[]`（DASH 是 `baseUrl + backupUrl[]`）整理成候选，**官方 CDN 优先、PCDN 垫底**。实测 `backup_url` 里 100% 带 `upos-sz-*.bilivideo.com`，且官方 CDN 拉 200KB 约 1 秒、PCDN 约 5 秒。PiliPlus 的默认 CDN 策略（`CDNService.backupUrl`）就是优先备用地址；
  2. **两档域名策略**：B 站自有域（新增放行 `.bilivideo.cn`）带完整请求头；非 B 站域但**确实来自 playurl 响应**才放行，且改用 `webHeadersWithoutCookie()`（只发 UA/Referer/Origin）—— 第三方 PCDN 是合法播放地址，但不是 B 站资产，绝不能收到登录 Cookie；其余来源仍然拒绝；
  3. **Range 断点续传**：`bytes=<已下载>-` + append 模式，206 续写、416 视为已完整、200 则从头覆盖；下载结束做长度校验（PCDN 会提前断流），对不上判本次候选失败，交给下一个候选/下次续传；
  4. **失败可诊断**：日志记录每个候选的 host 与 HTTP 码（原来失败只报一句"网络错误"，连域名都没有）。
- **仅音频同样修复**：`getVideoDash` 之前只取 `baseUrl`，而音频主地址正是 `mcdn.bilivideo.cn`，同样会被判死；现在也走候选列表。
- **影响文件**：`PlayerApi`（`DurlItem.backup_url`、`buildMediaCandidates`）、`PlayerData`（`videoUrls/audioUrls`，含 Parcelable）、`NetWorkUtil.isBilibiliHost`、`DownloadService`。

## 缓存播放：本地弹幕在后台线程操作 View，把整段加载一起中断了

- **现象**：播放已缓存视频，先在中间显示「装填弹幕中 (≧∇≦)」，随后弹出
  `CalledFromWrongThreadException: ... Expected: main Calling: DefaultDispatcher-worker-8`，视频停住，进度条一直是 `00:00/00:00`。
- **根因**：`PlayerActivity` 的本地视频分支在 `CenterThreadPool` 的协程线程（`Dispatchers.IO`，线程名 `DefaultDispatcher-worker-N`）上直接调用 `streamDanmaku()`，而它要操作 `DanmakuView`。异常被 `CenterThreadPool` 兜底成错误提示后，**同一个 lambda 里后面的 `setDisplay()` 不再执行** —— 播放器从未 `setDataSource/prepare`，所以画面停在加载态、时长恒为 0。
  同类问题此前修过两次（`downdanmuOld`、`streamDanmakuOnUi`），本地分支被漏掉。
- **修法**：本地弹幕渲染改回主线程；外面再包一层 `try/catch`（弹幕文件损坏只该"没有弹幕"，不该让整段加载失败）；`danmaku_url` 为空时不再 `new File(null)`（NPE 同样会中断起播）。
- **影响文件**：`PlayerActivity`（一处）。

## 首页推荐：默认改走 app 端，并修掉"每次下拉都在追加同一批"

- **现状核查**：开关（设置 → 偏好设置 → 首页使用app端推荐）与代码链路都在，接口实测仍是 `code=0`、一页 8 条，游标翻页有效（第 1→2 页 aid 交集 0）；但默认是关的，等于大多数人根本没走 app 端。
- **重复推荐的根因（实测）**：web 路径只传了 `web_location/feed_version/homepage_ver/uniq_id/screen`，而 `RecommendActivity` 又把 `page` 丢了（`setOnLoadMoreListener(page -> addRecommend())`）。用**完全相同的参数**连打两次，服务端返回的是同一批 30 条（交集 30、顺序一致）→ 每次"加载更多"都在把同一批再追加一遍。
- **修法**：
  1. **默认开启 app 端推荐**（默认值同时改在 `RecommendApi` 与设置页，避免"设置页显示关、实际在开"的口径不一致）；
  2. **web 端换批参数**（PiliPlus 同款）：`ps=20&fresh_idx=<page>&brush=<page>&fresh_type=4`；带这些参数后实测相邻两页交集为 0；
  3. **app 端刷新复位游标**：第 1 页（含下拉刷新）`idx=0` 且 `pull=true`，与 PiliPlus 的 `onRefresh` 一致；
  4. **app 端卡片过滤**：按 PiliPlus `_filterAppRcmd` 的判据滤掉 `ad_av/ad_web_s/ad_info/can_play!=1` 与非 `av` 卡片（直播/番剧卡点进去本来是空的）；
  5. **兜底去重**：Activity 内按 `aid/bvid` 维护 seen 集合，刷新时清空——服务端换批已能保证相邻页不重复，这层用于网络重试、切回旧页面等边界；
  6. **失败不再静默**：首页第一页拿不到内容时提示"推荐加载失败，下拉重试"，而不是白页。
- **影响文件**：`RecommendApi`、`RecommendActivity`、`SettingPrefActivity`（默认值）。

## 崩溃上报改到自建服务（1.2.1 起默认开启）

- **为什么换**：腾讯 Bugly 后台的「问题详情」长期返回 `422` / `404`（`get-issue-info` 422、`get-last-crash` 404），榜单能看到条数，点开却没有任何堆栈，等于只能报数不能定位；而且它是闭源 SDK，与本项目的 GPL-3.0 冲突。
- **现在怎么做**：`ErrorCatch` 捕获 → 写本地文件 → 写待发队列 → 启动崩溃页 → OkHttp 上报到自建服务 → 杀主进程。零闭源依赖，零新增三方库。
- **授权策略变更**：改为**默认开启**，首次安装或升级到 1.2.1 及以上时弹一次说明框，写清收集什么、不收集什么、如何关闭；设置 → 偏好设置 → 崩溃上报 可随时关闭。
  - 例外：在更早版本里明确点过「不同意」的用户，本次**不会**被强行打开，弹窗改为告知「当前为关闭状态，可自行开启」。
- **三条不变式**：
  1. 先留痕再上报：本地文本与待发队列都写在上传之前，进程提前被杀也不丢；
  2. 崩溃页永远活下来：`CatchActivity` 跑在 `:crash` 进程，主进程什么时候死都不影响它显示；
  3. 上报失败是常态：实测 WiFi 下该域名会被重置、手机流量正常，失败一律入队，下次冷启动补发（最多 5 条；本地文件保留 20 份）。
- **采集范围**：机型、系统版本、应用版本、随机安装标识、堆栈、线程名、崩溃页面。**不采集** IMEI/OAID/AndroidID、账号、Cookie。
- **本地调试日志**：`Download/ReBiliDiag/app-log.txt` 仍**默认关闭**，与本次改动无关，需要时在实验室里手动开。
- **崩溃页黑屏的真正根因**（arm64 模拟器复现实锤）：`CatchActivity` 自 1.0.2 起给「可能的崩溃原因」前 8 个字符加粗时写死了 `setSpan(0, 8)`，而未知异常走的是只有 7 个字的「未知的崩溃原因」，越界让崩溃页自己又崩一次，系统反复拉起 → 无限黑屏。改为按 `min(8, length)` 截断。
- **体积**：release 包 9,818,310 → **9,535,964 字节**（移出 Bugly 的 jar 与两个 so）。
- **能力回退**：只捕获 Java 崩溃，Native 崩溃（ijk/ffmpeg）不再上报。本项目 so 均为 stripped，native 栈本来也只有地址，故接受此回退。

## 崩溃可观测性补强（2026-10-18，versionCode / versionName 均未变）

- **上报队列不再被单条毒丸堵死**：`CrashUploader.flushPending` 原来是「首条失败就 `break`」，队首那条若被服务端永久拒绝（字段/表约束 4xx），后面所有记录永远发不出去。改为逐条计次（旁挂 `.fail` 文件），连续失败 3 次才丢弃并留痕。
- **HTTP 状态码留痕**：`upload()` 以前只返回 `isSuccessful()`，分不清断网与 4xx 拒绝；现在把 `response.code()` 写进 `CrashTrace` 与 logcat，并对外暴露 `lastHttpCode()`。
- **补齐四类死角**：
  1. 启动最早期的崩溃（`Application.onCreate` 之前，`ErrorCatch` 尚未安装）：`attachBaseContext` 里先装一层「只落盘」处理器，写 `files/crash_early/`，下次冷启动由 `flushEarly()` 转成正式上报。此前这一段崩溃**完全不留痕**。
  2. 崩溃页自身崩溃：`:crash` 进程以前不装 handler，崩溃页再崩就彻底丢失。现在装「只落盘、不重开页面」的处理器（重开会导致无限循环），记 `crash_type=crash-page`。
  3. 原生崩溃 / ANR / 被低内存杀：API 30+ 用 `ApplicationExitInfo.getHistoricalProcessExitReasons` 在下次启动补报（`crash_type=native/anr/lmk/...`）。API 30 以下无此接口，仍只能靠播放哨兵。**`REASON_SIGNALED` 与 `REASON_OTHER` 故意不报**：我们自己崩溃后就是 `killProcess`（SIGKILL）收尾，误报噪音大于价值。
  4. 用户无手动重传入口：崩溃页的「上传堆栈」按钮以前正常崩溃时被 `GONE`，现在改为常显的「重新上报未发出的记录（待发 N）」，并显示上次 HTTP 结果。
- **「点退出又崩一次」的观感**：`exit_btn` 原来 `System.exit(-1)`，非 0 退出码被系统判成异常退出并弹「应用已停止运行」。改为 `finish()` + `Process.killProcess`。
- **设置页显示与实际相反**：`SettingPrefActivity` 里崩溃上报开关的默认值写的是 `"false"`，而 `CrashReportUtil.isEnabled()` 默认 `true`，显示为「关」实际在传。改为 `"true"`，并新增「活跃设备统计」开关。
- **崩溃次数统计**：新增 `CrashStats`，把每次崩溃按时间写进诊断目录下的 `crash-stats.log`（跨进程可读、按分钟去重、兼容旧 `crash-*.txt`）。它是**本地留痕**，不做 UI——按时间统计崩溃数量在 web 控制台看（见下条）。
- **活跃设备统计**：新增 `LaunchPing`，每天最多一条 `crash_type=launch`（安装标识 + 版本 + 系统 + 机型），随机延迟 3–8 秒上报，**不入崩溃待发队列**（避免挤掉崩溃记录）。与崩溃共用 `crash_reports` 表。
- **控制台（docs/crash-console.html）**：新增按时间筛选按钮（今天 / 近 3 天 / 近 7 天 / 近 30 天 / 全部，按钮上直接显示该区间崩溃条数）；新增「今日活跃设备 / 近 30 天活跃设备」两张卡片；查询时排除 `crash_type=launch`，避免活跃打点混进崩溃列表。
- **开屏动画独立开关**：开屏动画改为 `NEW_UI_DESIGN && SPLASH_NEW_UI` 双开关，图标与光晕观感不协调时可只关开屏、保留其它页面的新版美学（设置 → 偏好设置 → 视觉 → 新版开屏动画）。
- **回声洞新动态**：`R.array.eggs` 索引 1 插入开发者投稿（索引 0 仍是「再长按几次试试」提示，所以第一次长按行为不变）。

## 退出后回到旧页面（apply 写盘被 SIGKILL 吃掉）

- **现象**：主菜单点「退出」→ 重新打开，回到退出前那个页面；崩溃后重启 → 也回到旧页面。
- **根因**：`MenuActivity` 与 `ErrorCatch` 都在 `killProcess` 之前调 `ResumePageUtil.clear()`，而它走 `SharedPreferencesUtil.putString()` → `apply()`。`apply()` 的写盘在后台队列里，`Process.killProcess` 是 SIGKILL，队列来不及 flush，恢复栈原样留着。
- **修法**：新增 `SharedPreferencesUtil.putStringSync()`（`commit()` 同步落盘），`ResumePageUtil.clear()` 改用它。恢复栈的读取路径不变。

# 1.2.1fix（versionCode 20261018）

## 弹窗全面改为自适应

- **问题**：把「界面大小」（`dpi` 倍率）调大后，弹窗正文被截断、按钮被挤出屏幕。崩溃上报说明、实验室「调试日志落文件」开关、番剧整季选集三处最明显。
- **根因**：应用内缩放走的是「改 Activity 的 `Configuration.densityDpi` + DecorView padding」，只作用于 Activity；弹窗是独立窗口，可用高度仍是系统原始屏幕高。而 appcompat 的 `abc_alert_dialog_material.xml` 里标题、正文 `NestedScrollView`、按钮栏**全是 `wrap_content`、没有任何高度上限**，放大后的内容直接把窗口顶穿，系统按屏幕硬裁。
- **修法**：新增 `util/AdaptiveDialog`（自绘 `MaterialCardView`，不走系统 AlertDialog）：
  1. 窗口宽高按**系统真实屏幕像素**取上限（92% / 86%），不受应用内密度影响；
  2. 先藏起内容区量出「标题 + 按钮 + 内边距」固定开销，再量整张卡片自然总高，取小作为窗口高；
  3. 内容区高度钉成「窗口高 − 固定开销 − 内容区 `topMargin`」，超出部分在内部滚动，按钮永远留在窗口内。
- **踩到并修掉的两个坑**（都实测复现过）：
  - 计算固定开销时内容区是 `GONE`，`GONE` 子项连同 `topMargin` 一起不参与布局，导致窗口比卡片矮几 dp，**底部按钮被窗口裁掉一半**。改为显式减去 `topMargin`。
  - `MaterialButton` 用 `wrap_content` 时，`TextButton` 样式的 inset 与 padding 叠加会把内容区压到几像素，**按钮文字只剩中间一条横线**。改为代码里固定 48dp 高、去掉竖向 padding。
- **覆盖范围（7 处）**：崩溃上报说明、设置项警告开关、番剧整季选集、更新提示（三按钮）、更新源单选、自定义镜像前缀输入、删除账号确认。
- **未改动**：`TutorialActivity`（教程页）的「已阅」按钮原本就在滚动内容末尾，小屏 + 大字号时需要滚动才能看到，属既有行为，本轮未改。

## 性能优化

- **冷启动少两个主线程阻塞点**：`PlayerSentinel.checkAndReport` 原本在 `Application.onCreate` 主线程上跑（内部两次 `commit` 同步落盘），改到后台线程，并给 `begin/finish/checkAndReport` 加同一把锁，避免后台清理标记与用户点播放的 `begin` 竞争导致漏报一次。
- **诊断任务拆开**：`flushPending / flushEarly / ExitReasonCollector` 原来串在同一个后台 lambda 里，单次上传超时 8 秒、队列最多 5 条，弱网下 `ExitReasonCollector`（补报上次原生崩溃/ANR/LMK）最坏要等 40 秒才轮到，记录经常直接丢失。改为三个独立任务并行提交。
- **活跃统计不再白占线程**：`LaunchPing` 的 3~8 秒随机延迟原本靠线程内 `Thread.sleep`，改为 `Handler.postDelayed`。
- **`episode_progress` 只清一次**：原来每次冷启动都 `clear().apply()` 一次旧进度库（1.2.0-v5 遗留），加一次性标记后不再每次重写。
- **播放页打点收敛**：`PlayerSentinel.stage` 每个调用点都是一次同步落盘，`PlayerActivity.onCreate` 里从 8 次降到 4 次（合并相邻的快速步骤），保留「进入播放页 / 布局完成 / UI初始化完成 / 加载ijk库」四个能区分崩溃阶段的关键点。
- **弹窗单选改局部刷新**：`AdaptiveDialog` 的单选列表点击后原本 `notifyDataSetChanged()` 整表重绑，改为只刷新旧选中与新选中两行（番剧整季上百集时差别明显）。
- **Glide 内存缓存封顶**：`CustomGlideModule` 补上 `setMemoryCache` 与 `setBitmapPool`（memoryClass 的 1/8，4~32MB）。Glide 默认按 memoryClass 比例放大（内存缓存约 0.8×、位图池约 1.6×），在 64MB heap 的低端手表上接近半壁江山，是进列表滑几下就 GC 甚至被回收的原因之一。
- **氛围背景改为预渲染位图（修「关于」页卡死）**：`AmbientBackground` 的径向光晕半径是 `max(w,h)*0.75`，界面放大后几乎铺满整屏，每帧都要对全屏像素做一次渐变求值。实测 dpi 1.6 下进「关于」页单帧耗时 2779ms（`Davey! duration=2779ms`，`Skipped 67 frames`），连续两次弹 ANR。改为把光晕预渲染到 1/4 分辨率的位图（1080×2160 屏上约 0.6MB），每帧只做一次位图拉伸：改后同场景滑动无掉帧告警，渐变观感不变。圆屏模式（MODE_ROUND 的细线圆环）绘制量本来就小，保持原逻辑不动。

## 同版本迭代（2026-10-17，versionCode / versionName 均未变）

### 修复

- **登录「约一天后掉登录」**：根因是扫码登录路径自己写了一套凭证落盘逻辑，只认 `data.refresh_token` 且用 `getString` 取值——写 `refresh_token` 那一步失败时会留下「有 mid/cookies/csrf、但没有续期凭据」的**半登录态**；而启动页在刷新失败时直接清空全部凭证，一次网络抖动就等于登出。修法：扫码统一走 `LoginApi.finishLogin()`（兼容 `data.refresh_token` 与 `data.token_info.refresh_token` 两种结构、过滤 JSON null 被 `optString` 转成的字符串 `"null"`、换号时清理上一账号残留）；刷新结果由 boolean 改为 `CookieRefreshResult` 枚举，**瞬时失败一律保留凭证**，只有服务端明确否定凭证才清理；新增 `CookieRefresher` 提供「启动 + 长驻周期 + 关键请求报未登录」三个续期触发点并带节流。
- **番剧进度**：把「v2 返回了 `watch_progress` 对象」误当成「本集已有记录」，从而跳过了唯一按 `epid`/`cid` 分集的**观看记录**源。判据收紧为「本集即最近一集且 `current<=0`」才跳过扫描。另修：`season_type` 改用真实值、`bvid` 的 `null` 在 Parcel 往返/接口解析/源头三处兜住、上报守卫不再被 `aid==0` 一票否决、退出补报不再覆盖「看完」标记、番剧位置过小（≤5s）不上报以免覆盖已有记录。
  - 说明：**「整季共享 aid」的番剧（如攻壳 SAC）仍无法分集保存**，这是服务端把进度收敛为「本季最近一集」的行为，且观看记录对同一 `oid` 也只留最近一条——客户端无法绕过，已确认放弃。
- **「总是跳过」反复跳导致一直加载**：原来的冷却时间挡不住 seek 失败后的位置回退。改为闩锁——**必须观察到位置越过片段结束（+3 秒余量）才重新武装**；并新增「距片段结束不足 15 秒不跳」（避免只位移几秒的无意义 seek 把刚起播的缓冲打断）；结束位置超出片长的脏片段不自动跳。
- **弹幕一直弹「新版接口获取失败」**：与接口无关——`streamDanmaku` 会操作 `DanmakuView`，却在网络/磁盘的后台线程上被调用，抛出的线程异常被上层 `catch` 当成「获取失败」→ 弹提示 + 白回退一次 XML 下载。改为回主线程渲染（三条调用路径全覆盖）。同时修正弹幕接口：两条 protobuf 端点前缀不同（`wbi` 段不能省），无签名端点作主通道、WBI 作回退；空分段是「后面没有弹幕了」的正常结束标志，不再当错误。
- **设置项串值（code review 发现的 P0）**：`choose` 的选项按钮只在多选项路径清理，而两选项与多选项共用同一个 RecyclerView holder——holder 复用时残留按钮带着旧闭包，点一下会 `putInt(旧key, 旧idx)` **静默改写另一个设置项**。清理提升到 `bind()` 入口并对所有选项数生效。

### 新功能（移植自 PiliPlus）

- **番剧片头/片尾跳过**：五档（总是跳过 / 跳过一次 / 手动跳过 / 仅显示 / 禁用），**默认「手动跳过」**。数据源是官方随取流下发的 `clip_info_list`，零新增请求；判定挂在既有 250ms 进度 tick 上，不新增定时器。
- **首页使用 app 端推荐**：`app.bilibili.com/x/v2/feed/index` 实测游客态即 `code=0`，**不需要 AppSign、不需要 access_key**，因此没有引入第二套鉴权体系。
- **空降弹幕**：点含时间点的弹幕直接跳转。弹幕层被控制层遮盖收不到触摸，改用 `DanmakuTouchHelper.onTouchEvent`（public 且恒返回 `false`，不消费事件）从控制层触摸链路旁路驱动；含时间点的弹幕有醒目标识（琥珀金 + `[跳]` 前缀 + 字号 1.15×）。

- **首页一键刷新按钮**：滚回顶部 + 复用下拉刷新回调，只在注册过刷新回调的页面显示（避免点了没反应的死按钮）。
- **开屏页跟随新版美学**：冷启动首帧底图补上与页面内 `AmbientBackground` **同参数**的粉色光晕（消除「黑一下再变粉」的割裂）；新版美学下使用新布局（氛围光晕 + 图标 + 粉色短线 + 打字机欢迎语）。

### 性能

- **专栏（cv）详情改走 `x/article/view` 单次 API 直取**：原先按 id 长度猜类型——`id<=1e8`（即所有 cv 号）会去抓 `www.bilibili.com/read/cv{id}` 的**整页 SSR HTML** 再手抠 JSON，还要循环跟跳多级 301、并命中 `NetWorkUtil` 对 doctype 响应的重试。而 `ArticleApi.getArticle`（等价于 PiliPlus 的 `articleView`）早已实现却无任何调用方。现在正文由新增的 `ArticleHtmlParser` 从 HTML 转成渲染链吃的段落数组，**失败原样回退网页抓取**（最坏不比改造前差）。

- **正文章节绑定的主线程开销**：每次绑定都跑 4 个正则（URL/BV/AV/CV）并重建 Spannable。改为解析阶段后台预热并缓存在段落上，绑定只做 `setText`；长按复制监听器改为静态单例。

## 技术问题与修法

### 一、番剧进度：服务端其实有**四套**语义不同的进度数据

修这条链路踩的坑，本质是"拿错了字段"或"拿对了字段但理解错了语义"。先把四个数据源摆清楚
（实测账号与剧集：season 1178 / CLANNAD，epid 21448、21449）：

| # | 接口 | 字段 | 语义 | 单位 |
| --- | --- | --- | --- | --- |
| 1 | `pgc/view/web/season/user/status` | `result.progress.last_ep_id` / `last_time` | **本季最近观看的那一集**这一条记录 | `last_time` = **秒** |
| 2 | `pgc/player/web/v2/playurl` | `result.play_view_business_info.user_status.watch_progress.current_watch_progress` | **本次请求的这一集自己**的进度 | **毫秒** |
| 2' | 同上（同响应内） | `watch_progress.last_ep_id` / `last_time` | 季级那一条（与 #1 同义） | `last_time` = **毫秒** |
| 3 | `x/player/wbi/v2` | `last_play_time` / `last_play_cid` | 对 PGC 按季维护；`last_play_cid` 实测恒为 `0` | 毫秒，但不可用 |
| 4 | `x/web-interface/history/cursor` | `progress` / `history.epid` / `history.cid` / `history.oid` | 观看记录列表；**一季只有一条 pgc 记录**（等于 #1） | 秒 |

实测证据（诊断日志摘录）：

```
02:02:09 [服务端进度] epid=21448 v2 watch_progress={current=421000,last_ep_id=21448,last_time=421000}
02:03:26 [服务端进度] epid=21449 v2 watch_progress={current=683000,last_ep_id=21448,last_time=624000}
02:03:53 [服务端进度] epid=21493 v2 watch_progress={current=937000,last_ep_id=21448,last_time=1000}
02:03:30 [季级状态]   season_id=1178 last_ep_id=21448 last_time=624s
```

- 第 2 行：请求第 16 话时 `current=683000`（683 秒，**它自己的**位置），而季级记录还停在第 15 话的 624 秒。
- 第 3 行：季级已换成第 15 话的 1 秒，第 16 话的 `current` 仍是 `937000`。
  ⇒ **服务端按集保存进度**，`current_watch_progress` 是干净的集级数据源；"只留最近一集"只对 #1 成立。
- 第 4 行：同一个 421 秒的位置，在 #1 里是 `421`（秒），在 #2 里是 `421000`（毫秒）。
  ⇒ **两个接口的同名字段单位不同**，这是后面那次事故的直接原因。

### 二、四次迭代与两次翻车

1. **串集（v3 / v4 修掉）**，共三个原因：
   - `history.oid`（avid）被当作集身份。实测同一季多集 **共用同一个 avid**：season 1564 的第 8/9 话
     `history.oid` 都是 `135433`，按 aid 命中会把"上一集刚写下的记录"当成"这一集的记录"。
     现在只认 `cid` / `epid`，`aid` 仅在两者都未知时才兜底。
   - 番剧回退了 `x/player/wbi/v2`。该接口对 PGC 按季维护，且 `last_play_cid` 恒为 0，
     `last_play_cid == cid` 的"严格配对"根本挡不住串集。**番剧一律不回退该接口**。
   - 季级 `last_time` 被单独使用。它只属于 `last_ep_id` 那一集，必须整体配对
     （`last_ep_id == 目标 epid` 才可用）。
2. **本地存档（v5 加、v6 撤）**：v5 曾用本机 `SharedPreferences` 存"每集看到哪"，
   依据是"服务端只留最近一集"这个当时并不完整的结论。v6 确认服务端其实按集保存，
   且本地记录会因换号 / 重装 / 清数据而与服务端错位，于是**整条移除**（旧数据在冷启动时清空）。
3. **单位事故（v6 引入、v7 修复）**：v6 用 v2 的 `current_watch_progress` 作续播数据源，但加了一层
   "秒/毫秒自校准"——看到同响应里 `current == last_time` 就断定"这是秒"，于是 ×1000。
   结果 `421000` 变成 `421000000`，被越界检查丢弃，**每一次续播都归零**，
   表现恰好就是"完全读不到官方客户端已记录的进度"。v7 实测确认这两个字段恒为毫秒，
   删除一切单位换算，只保留一条保护：**位置超过总时长才从头播**。
   同时删掉了多余且有害的"季级泄漏守卫"（它会把"本集进度恰好等于季级位置"的巧合误判成泄漏并重启）。
4. **审计（v8）**：对这条链路做了一次完整审计，落实 11 项发现，其中影响行为的两项：
   - 第一次看新集时不再白扫 5 页观看记录（v2 已明确该集无记录时，记录里那条 pgc 条目必然属于别集）；
   - v2 网络层失败直接快速失败，不再对 v1 重复一轮重试（`getJson` 内部已带约 5 次重试，双倍等待无意义）。

### 三、当前实现（读 / 写）

**读（续播位置），按优先级：**

1. v2 `playurl` 的 `watch_progress.current_watch_progress`（毫秒）——本集自己的位置；
2. 同一响应里 `last_ep_id == 本集 epid` 时的 `last_time`（毫秒）——集级字段为空时的兜底；
3. 季级状态接口（秒 → 毫秒），仅在 1/2 都拿不到时查（v1 回退、字段缺失）；
4. 观看记录里本集自己的条目（cid/epid 全身份命中），仅在 v2 没有该字段时扫；
5. 都没有 → 从头播。**番剧不回退 `x/player/wbi/v2`。**

请求侧要点：取流改用 `pgc/player/web/v2/playurl`（v1 的 `result` 里没有任何进度字段），
带上 `ep_id` / `season_id`；用响应里的 `episode_info.ep_id` / `cid` 做服务端侧身份校验
（响应 cid 与请求 cid 不一致就丢弃进度字段）；`epid` 缺失的入口（历史/搜索只有 cid）会用回显的
`ep_id` 补齐，否则播放器的心跳上报会整条跳过。v1 仅在"v2 正常返回但取不到 durl"时作为兜底。

**写（上报）：** 心跳 `x/click-interface/web/heartbeat`（`type=4`，带 `epid` / `sid` / `played_time`，
播完发 `played_time=-1`）。周期上报 5 秒一次，外加退出 / 切后台 / 播完各一次并去重。
上报前重建 Cookie 头、csrf 与 mid 一律从实时 Cookie 派生 —— 心跳接口对未登录请求同样返回 `code:0`，
只看返回码无法判断是否真的落库，因此诊断打开时会在播放 25 秒后回读一次服务端做端到端确认。

**详情页不再写观看记录：** 服务端对本季只维护一条记录，没播放过就写，会把"上次看到第 N 话"
指向一集没看过的内容（官方客户端的续播入口随之错位）。记录一律由播放器心跳写入。

**本地不保存任何观看进度。**

### 四、诊断怎么开（默认关闭）

`1.2.0fix` 起番剧进度诊断**默认关闭**（不写诊断文件、不发额外回读请求）。
需要排查时：**设置 → 实验室 → 调试 → 番剧进度诊断** 打开，复现一次后取文件：

- `Download/ReBiliDiag/progress-diag.txt`（有存储权限时）
- 否则 `Android/media/com.RobinNotBad.BiliClient.re/progress-diag.txt`

文件里的 `[服务端进度]` / `[续播结果]` / `[回读自检]` 三行分别对应"服务端给了什么"、
"最终采用了哪个来源"、"上报是否真的落库"。

### 五、同一版本里的其它技术问题

- **评论卡片语言**：子评论（楼中楼）与"UP 主觉得很赞"原先用 `?attr/biliCardBackground`
  （主卡片的渐变描边语言），在评论区看起来像"模糊的灰盒子"；改用与搜索页同 token 的
  `background_card_soft`（10dp 圆角 + 0.5dp `#363636` 描边）。
- **搜索页遮挡**：历史记录 / 建议面板与结果列表在布局里同位叠放且底色不透明，
  关键词非空时一旦显示就会整块盖住结果；现在关键词非空且无建议时不再弹出面板。
- **切后台丢结果**：搜索结果只存在内存里，页面重建必然为空；新增"最后一次搜索词"记忆
  （进程内重建走 `savedInstanceState`，冷启动恢复链走 `SharedPreferences` + `EXTRA_RESUME_RESTORE`
  标记），只在恢复场景重放。
- **圆屏播放页**：右侧按钮列原先被上下横条用 `layout_below/above` 夹取，高度吃紧时最后一个按钮被裁掉；
  改为 `WRAP_CONTENT` + 垂直居中并给可横向滚动的菜单行加宽度上限。弹幕按钮的可见性统一由
  `player_ui_showDanmakuBtn` 决定（此前 onPrepared / 退出听视频模式两处口径不一致）。
- **登录态口径统一**：新增 `NetWorkUtil.getLoginMid()` / `getLoginCsrf()` / `isLoggedIn()`，
  一律从实时 Cookie 派生。旧实现读本地快照，Cookie 轮换或换设备后错位，
  表现为"明明登录了却读不到记录 / 上报被静默跳过"。经验与硬币记录的本地累积（`UserLogStore`）
  同样改用该口径做账号隔离。
- **版本名比较**：`VersionNameUtil` 原先要求修复版后缀带连字符（`-fix`），
  现在 `1.2.0fix` 这类写法也能解析（`1.2.0 < 1.2.0fix < 1.2.1`），不再退化到 versionCode 兜底。

- 登录响应、POST 参数、私信内容、直播弹幕认证包不再写入系统日志。
- Cookie 回写全程加锁，并引入账号代际号：切换账号瞬间在途的旧账号响应不再污染新会话。

**修复**

- 登录二维码过期后可在当前页直接刷新（此前只能退出页面重进）。
- 修复评论、弹幕、私信内容含 `&`、`+`、`%` 等符号时发送出错的问题；搜索关键词同步修复。
- 修复发弹幕颜色错误的问题。
- 修复「不进相册」设置被反复撤销导致下载视频出现在相册的问题。
- 下载更可靠：失败任务不再永久卡死队列、指定条目被删后队列继续、音频改用刚获取的
  链接、退出时有总结通知；旧版下载器的解压死循环同步修复。
- 修复快速进出直播间后弹幕连接不关闭导致的耗电与内存泄漏。
- 修复快速切换分P / 清晰度时界面与实际播放内容不一致的问题。
- 修复本地缓存列表偶发崩溃；搜索、热门、动态等列表页加入请求代际守卫，快速刷新

#### 1.1.0-fix1 修复了什么

**搜索建议（三连修）**

- **建议永远为空**：B站 suggest 接口的词表从 `data` 移到了 `result` 字段，旧解析取 `data.tag` 恒为空。
  现改为 `result`/`data` 双字段兼容解析，接口再挪字段也不会悄悄失效。
- **建议卡片回弹**：点击联想词后卡片重新弹出、盖住搜索结果——点击会经 `setText` 触发一次新的建议
  请求，旧代码没有在搜索执行时作废它。现搜索执行期间整条建议链路被屏蔽（含输入法延迟 commit），
  并作废在途请求、主动收起卡片。
- **建议结果被整包丢弃**：结果回调以"输入框此刻是否持有焦点"为显示条件，而部分 ROM 输入法
  （一加13 / ColorOS16 实测）在组词/候选期间会让输入框短暂失焦，导致建议永远不出现。
  现改为代际令牌校验——只显示最新一次输入的响应，同时防乱序竞态覆盖。

**搜索后输入法无法拉起（一加13 / ColorOS16）**

- 搜索执行时 `clearFocus()`、完成后 `requestFragmentFocus()` 把焦点交给结果列表；第一次点击输入框
  只恢复焦点不拉起键盘，第二次才正常；而键盘弹出引发的列表滚动回调又会触发焦点抢占，把刚弹出的
  键盘顶掉。现改为：输入框点击时主动补一次 `showSoftInput`；输入框持有焦点期间
  `requestFragmentFocus` 不再抢占焦点（手表滚轮导航不受影响）。

**低性能设备（W527 手表）转场动画丢失**

- 诊断：关于页新增动画缩放显示（无开发者选项的设备无法查看系统设置）。实测 W527 ROM 将
  `TRANSITION_ANIMATION_SCALE` 设为 0——系统级页面转场被整体禁用，该设置从应用侧无法恢复
  （需 adb / 系统权限）。
- 缓解：页面内容就绪后按"帧数"驱动渐入（帧数 + 时间双上限），把占位屏 → 内容的硬切变成过渡。
  按帧数而非时间驱动是关键：单帧绘制耗时会超过动画时长，时间型淡入在首帧画完时就已结束。

#### 1.0.2-fix1 具体修了什么

**观看进度上报（番剧续播进度写不进服务端）**

- 上报凭证不再读本地快照 `csrf` / `mid`，改为从实时 Cookie（`bili_jct` / `DedeUserID`）派生。
  原实现下 Cookie 轮换后两者会错位，导致**所有 POST 返回 `-111`，而 GET 一切正常** ——
  表现为「只有观看记录上报静默失效」，且同一份代码在不同设备/登录时机表现不同。
- 心跳接口的 `start_ts` 夹到 `>= 0`，避免设备时钟偏慢时被服务端判 `-400`。
- 上报前若 `mid` 为 0，用实时 Cookie 补一次解析，避免已登录却被判未登录。
- 番剧续播进度在 `x/player/wbi/v2` 取不到时，兜底走观看记录列表接口。
- WBI 密钥取成功后才落 `last_wbi`，缓存为空强制刷新，避免一次取密钥失败污染当天所有 WBI 请求。

**跳转后弹幕卡死 / 退出播放后整个应用卡死**

- 弹幕绘制线程不再轮询 `ijkPlayer.getCurrentPosition()`。该回调跑在弹幕同步/绘制线程上，
  而它是会取播放器原生锁的 JNI 调用 —— 既是「弹幕时间轴被旧位置拽住」的直接原因，
  也是绘制线程卡住后主线程 `release()` 内 `join()` 无限等待、**整个应用卡死**的共因。
- 退出链路（`finish` / `onPause` / `onStop` / `onDestroy`）与 MediaSession 状态更新
  不再在主线程调用 `getCurrentPosition()`。
- 弹幕未 `prepared` 时的 seek 请求会暂存、prepared 后补做；新增带观察窗与冷却的弹幕时间轴校正。
- DanmakuFlameMaster 的 `Thread.join` 加 2s 超时，避免主线程被无限阻塞。
- 所有 `TimerTask` 加异常兜底（TimerTask 抛未捕获异常会永久终止整个 Timer，
  导致进度条与进度上报一起静默失效）。
