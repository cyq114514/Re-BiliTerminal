# BiliTerminal-RE / Revival 功能移植评估与 Plan

> 调研日期：2026-11-05  
> 目标项目：`Re-BiliTerminal-workspace-20261105`  
> 方式：短任务子代理分仓库取证 + 主代理逐项复核；只读分析，未构建、未运行 APK、未修改项目代码。

## 一、结论

**不建议合并任一仓库，也不建议引入 Kotlin 或替换播放内核。最佳路线是：以 Revival 的 Java 实现为低成本参考，以 RE 的独立策略类和 API 为功能参考，逐项用当前项目的 Java + XML 架构重写。**

首批推荐顺序：

1. **Wi-Fi / 移动数据独立默认画质**（Revival）
2. **跳到指定时间**（RE）
3. **横滑调进度灵敏度**（RE）
4. **AI 视频摘要**（RE）
5. **本地缓存视频断点续播**（RE；涉及本地行为变更，先确认）
6. **只读视频笔记**（RE）
7. **存储占用统计，再评估安全清理**（Revival；删除行为必须先确认）

`SAF 外置存储`、`跨稿件通用连播`、`触摸锁定`有价值，但影响面更大，应在前述功能分别验收后再做。`多线程下载`、`ExoPlayer 替换`、`兼容中继`、`整仓 Kotlin 重构`不进入近期计划。

## 五、串行实施 Plan

每阶段单独交付、单独验收，**不并行铺开**。后一阶段只有在前一阶段验收通过后才启动。每阶段均以最小 diff 实现，不整文件覆盖上游。

### 阶段 0：冻结基线与回归清单

- 保存当前工作区 diff，特别是未发布的番剧、音频队列、弹幕、搜索和 UI 修复。
- 建立播放器基线：在线视频、多 P、番剧、本地缓存、直播、后台恢复、横滑、±N 秒、弹幕同步。
- 建立下载基线：普通 MP4、DASH、多 P、暂停/继续、失败重试、本地删除。
- 当前没有 `testImplementation`，也未检索到 `*Test.java/*Test.kt`；若补 JUnit 属于新依赖，需先经用户确认。否则只能交付构建 + 真机证据，不能声称自动化覆盖。

**出口**：基线构建成功，核心路径有改前记录；若基线已有失败，先登记，不能把它算作移植后回归。

### 阶段 1：分网络默认画质（Revival）

- 用 Java 写纯策略：网络类型 `UNKNOWN/MOBILE/WIFI`，设置值“跟随全局/指定画质”。
- 手动选择清晰度始终覆盖网络默认值；未知网络、VPN 无法识别时回退原 `play_qn`。
- 全仓枚举 `play_qn` 读取点，只改**播放默认画质**；下载默认画质不在本阶段改变。
- 接入视频、番剧、短视频等实际播放入口，设置项同步进入设置搜索。

**验收**：Wi-Fi、移动数据、未知网络、手动覆盖、设置持久化、冷启动、短视频/长视频/番剧；下载画质保持不变。  
**回滚**：移除两个策略类与设置 UI，恢复原 `play_qn` 读取点。

### 阶段 2：播放器精确控制（RE，两个子批次串行）

**2A 跳到指定时间**

- Java 重写解析策略，不引入 Kotlin；支持全角冒号、非法段、溢出、超片长钳制。
- 复用现有统一 seek 入口，确保弹幕使用同一跳转链路；直播不显示入口。

**2B 横滑灵敏度**

- 默认 1.0x；提供有限档位，不开放任意浮点输入。
- 只缩放横滑换算，不改起滑阈值、缩放拖动画布、双击和 ±N 秒。

**验收**：非法输入不跳、暂停态跳转、跳转后弹幕不反复清空、放大画面拖动不冲突、直播无入口、默认手感不变。  
**回滚**：分别独立回滚 2A/2B，互不影响。

### 阶段 3：AI 视频摘要（RE）

- 在当前 `VideoInfoApi` 增加 conclusion 请求，复用现有 WBI 签名、Cookie 与错误处理。
- 详情页增加入口和加载态；使用当前选页对应 cid，不固定取第一 P。
- 明确处理未登录、无摘要、接口失败、视频切换后的迟到响应。

**验收**：有摘要/无摘要/未登录/断网/多 P/快速离开页面；不阻塞详情页打开。  
**回滚**：删除 API 方法和入口，其他详情逻辑不变。

### 阶段 4：本地缓存断点续播（RE，先确认行为）

推荐方案：在每个缓存目录写 `.video_meta.json`，只保存本地播放进度与必要元数据。相比修改下载数据库，它不需要数据库迁移，且目录移动时进度可随文件走。

- 仅作用于 `PlayerData.TYPE_LOCAL`；在线视频和番剧仍走当前服务端进度。
- 只移植进度所需模型与读写，不带入 `FolderManager`。
- 读写使用同一“已看完”判定；损坏 JSON 回退从头播；避免频繁重复写盘。
- 多 P 必须按实际目录/cid 隔离；退出、切后台、进程被杀分别验证。
- 需用户先决定：是否默认开启，以及隐私模式下是否禁止写本地进度。

**验收**：单文件、DASH、多 P、看到结尾、进度超过片长、损坏元数据、进程被杀、目录移动；在线番剧进度对照组完全不变。  
**回滚**：停用本地读写并删除新增调用；已写 `.video_meta.json` 是否清理由用户决定，不自动删用户文件。

### 阶段 5：只读视频笔记（RE）

- 复用其 Java API 解析思路，注意字符串形式的长笔记 ID，避免数字精度丢失。
- 新 Java + XML 页面，先支持文本、样式、图片、时间标签；不做撰写/编辑。
- 时间标签复用统一 seek；未登录、无笔记、79502/79503、网络失败分别提示。

**验收**：无笔记、纯文本、图片、时间标签、长 ID、异常响应、小屏滚动。  
**回滚**：移除笔记页面和详情入口，不影响专栏/动态解析。

### 阶段 6：存储统计与安全清理（Revival）

- 6A 只读统计：图片缓存、临时文件、更新包、可用空间；不删除任何内容。
- 6B 在用户同意删除行为后，才加入白名单清理；明确保留视频、登录账号、记录和用户自定义媒体目录。
- 清理放后台线程，有并发保护、二次确认、实际释放字节和失败数反馈。

**验收**：自定义目录与缓存目录重叠、符号链接/异常路径、并发点击、清理中退出、无权限、更新包路径变化；不得误删用户内容。  
**回滚**：6B 可直接移除清理按钮；6A 只读统计可独立保留。

### 后续独立专项

依次再评估：触摸锁定 → 拉黑/举报 → SAF → 通用连播 → 创作中心。每个专项必须重新做影响面分析，不能沿用本 Plan 直接动代码。

## 六、验证与交付要求

每一阶段交付都必须包含：

1. 变更摘要：文件与增删行数。
2. 验证证据：实际命令与输出、真机步骤与结果；不能只写“验证通过”。
3. 已知限制与未验证项：尤其是 API 19 老设备、低端手表内存、移动网络/VPN、B 站接口变化。
4. 下一步：用户需要安装的产物、复测路径与需提供的日志。
5. 回滚：该阶段最小反向 diff；不得通过整仓覆盖回滚，避免误伤后续已验收功能。

建议真机矩阵：现有 PJZ110 用于最新系统回归；至少再补一台 API 19-23 设备或模拟器。RE 自己也声明 API 19-23 只做静态审计、未真机验证（`RE/readme.md:175-181`），不能把上游声明当成兼容性证据。
