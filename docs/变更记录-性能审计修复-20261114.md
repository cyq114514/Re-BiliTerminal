## 2. 逐条实现

### P1-1　PlaybackService 每秒无条件重建并重发通知

`service/PlaybackService.java:176` `notifyIfChanged()`：先取 `notifySnapshot()`（`playing|title|position|duration` 拼串），与 `lastSnapshot` 相同就直接返回，不再 `new Builder` + 两个 `PendingIntent` + `notify()`。`service/PlaybackService.java:63` `contentIntent` 改为 `onCreate` 建一次（`:103-112`），`refresh()` 直接复用，去掉每秒一次的 `getLaunchIntentForPackage` IPC。

- 并发口径保持原注释要求：每次仍新建 Builder（`refresh()` 未改结构），快照只是字符串比较。
- 播放中位置逐秒前进 → 快照必变 → 观感与改动前一致；暂停/缓冲卡住的 tick 直接短路。

### P1-2　AudioPlayerService 暂停态每 2s 重建 + 重发

`service/AudioPlayerService.java:1372` `refreshNotification()` 加同款快照判断；`notificationText()`（`:1336`）被 `buildNotification()` 与 `notificationSnapshot()` 共用，保证「用来判断的字符串」和「真正发出去的内容」永远同源，不会出现「判定没变、实际变了」的滞后。`initNotificationIntents()`（`:1356`）在 `onCreate` 建好 5 个 PendingIntent（4 个 action + 1 个 Activity），`buildNotification()` 直接引用。

`onCreate` / `onStartCommand` 里 `startForeground()` 成功后立刻回填 `lastNotificationSnapshot`（`:320`、`:351`），避免启动后第一次 tick 白重建一次。

### P2-1　直播列表 bind 内跑 Jsoup

`adapter/LiveCardAdapter.java:42` `titleCache` + `:95` `strippedTitle()`：按 `LiveRoom` 实例缓存去标签结果，同一间房只解析一次。

**与报告方案的偏差（需知悉）**：报告写的是「adapter 构造时对 roomList 一次性预处理」，实施时发现覆盖不全——三个使用方都会分页追加（`SearchLiveFragment:77` `roomList.addAll` + `notifyItemRangeInserted`，推荐/关注两页的 `continueLoading` 同构），构造期遍历拿不到后续页。改为「按房间对象懒缓存」后：首屏绑定不再重复解析、后续页同样生效、且不改写外部 `LiveRoom` 对象。缓存用 `WeakHashMap`（key 弱引用）——列表刷新丢弃旧房间后条目自动回收，不会把旧数据钉在内存里。

顺带修掉一个既有崩溃点：`room.title` 为 null 时原代码把 null 直接交给 `Jsoup.parse`（抛 `IllegalArgumentException`），现在按空串处理。

### P2-2　PlayerActivity 漏摘 hideVolumePanel

`PlayerActivity.java:3968`，与既有三行清理同款：`if (layout_volume != null) layout_volume.removeCallbacks(hideVolumePanel);`。依据是全部挂载点都挂在 `layout_volume` 上（`:3422`、`:4658`、`:4667`、`:4678`），走 View 自己的 handler 链，`mainHandler.removeCallbacksAndMessages(null)` 摘不到。

### P3-1　urlCache 过期条目不清理

`AudioPlayerService.java:542`（playCurrent）、`:1056`（prefetchNext）在 `valid()` 为假时 `remove`。

**同时把 `urlCache` 换成 `ConcurrentHashMap`（`:169`）**：原本 `get` 分布在主线程（起播）与后台线程（预取）而 `put` 全在解析线程，已经是并发读写；再叠加一个读取路径上的 `remove` 就变成并发写-写，HashMap 上不可接受。换容器后 get/put/remove 全部安全，行为等价。

### P3-2 / P3-3 / P3-4

- `NoticeHolder.java:46` 静态 `TIME_FORMAT`，`:111` 直接复用（`onBindViewHolder` 只在主线程，SimpleDateFormat 非线程安全不构成问题）。
- `VideoCardAdapter.java:268` 改局部移除，长按菜单里点「不感兴趣」不再让整屏卡片重新 bind。
- `ViewCache.java` 删除：`grep -rn ViewCache` 在 `*.java/*.kt/*.xml` 中仅命中文件自身，其余命中全在 `app/build/` 产物里。

## 4. 明确没做的事

- 报告 §4「不动的项」一个没碰（音频不吃 Audio Focus、`player_pause_bg_music` 语义、PlayerSentinel commit、DFM 帧循环、PlayerActivity 250ms 空醒、BaseActivity 胶囊轮询、CookieRefresher、SendGuard、BackgroundManager、DashData 双重解析、DownloadService 进度通知）。

- 通知刷新频率未改（视频侧仍 1s，音频侧仍 2s）。

## 6. 真机复测清单

1. 后台播放：设置里开「后台/熄屏继续播放」→ 播视频 → Home 退后台 → 暂停，等 30s，通知不应有任何刷新；继续播放，进度条仍逐秒走；暂停/继续/关闭按钮、点正文回任务均正常。
2. 收藏夹听歌：暂停挂后台 30s 通知不动；切歌后第一次刷新必须立刻出现新标题（不能滞后到下一次 tick）。
3. 直播列表：推荐/关注/搜索三个入口滚动，标题无 `<em>` 残留。
4. 推荐页长按 → 不感兴趣：只该卡消失，无整屏闪动。
5. 播放页：长按音量键调出无极调音面板 → 立刻返回退出 → 反复数次，无异常、无泄漏迹象。
6. 消息页：时间显示格式不变。
