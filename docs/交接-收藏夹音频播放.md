## 三、音频播放架构

```
收藏夹详情页 FavoriteVideoListActivity
  「▶ 听全部（纯音频）」
    → AudioPlayerService.startQueue(items, mediaId, order, folderName)
        → AudioQueue.setQueue()（loadedPage=按条数÷20推算, hasMore=true；aidSet 按 aid 去重）
        → 前台服务：playCurrent()
             ① 预取命中？ ② URL 缓存命中？ ③ playCurrent→后台 getVideoDash
             → AudioTrackPicker.pick()（优先 30280 AAC）
             → prepareAndPlay(urls, item, local=false, index)
                  · ijk 设 vn=1 / user_agent / referer
                  · 失败 → 候选 +1 重试
                  · 全部失败 → downloadAndPlay（OkHttp 缓冲到 cache/audio_cache/<cid>.m4s）
             → onPrepared：通知栏 + MediaSession + ensureMoreItems + prefetchNext
             → onCompletion：下一首 / 全量拉取未完时每页到达即续播
```

- **不请求音频焦点**：按产品要求允许与视频真混音；只在耳机拔出时暂停
- **UI 解耦**：Service 持播放器；全屏页 `AudioPlayerActivity` 只读状态 + 发控制指令
- **状态读取**：`AudioPlayerService.isRunning()/isActive()/isResolving()/isPlaying()/getPositionMs()/getDurationMs()`
- **UI 监听**：`addListener/removeListener`（全屏页、队列页）

## 五、关键决策与理由

1. **独立 Service 而非复用 PlayerActivity**：视频与音频要能同时存在、互不影响，同页面实例做不到。
2. **不请求音频焦点**：用户明确要求真混音同时出声；代价是与其他音乐 App 也会混音（产品选择）。
3. **不做底部迷你条**：用户反馈底部条被压扁且遮挡，改为顶部小胶囊（只作入口，控制走通知栏）。
4. **全量拉取（2026-11-05 用户需求变更，取代原「首播不翻全收藏夹」）**：起播仍用列表页已加载内容立即开始，
   `ensureMoreItems` 改为后台串行翻页直到收藏夹到底，每页到达即追加并通知——队列页实时变长、进度文案（3/57）变准。
   单页失败重试 3 次（1.5s 间隔）后停住，下一首 onPrepared 从断点续拉；`AudioQueue.append` 按 aid 去重
   （列表页翻过的多页与分页接口边界重叠不会重复）；`loadedPage` 按条数÷20 推算（此前固定记 1，会重复拉列表页已加载的页）；
   `AudioQueueApi` 的 hasMore 改用接口原值（某页 20 条全是失效稿件被滤空时后面可能还有页，此前会误判到底）。
   安全上限 100 页/2000 条，仅防接口异常死循环；串行单页请求，与原懒加载同样的 412 限速口径。
5. **多候选 CDN 重试 + URL 缓存 + 下一首预取**：解决"部分音频 403 / 切歌慢"；候选全部失败才下载兜底。
6. **只选 30280 AAC**：flac/dolby 需要会员且 ijk 预编译 so 未必带解码器。

## 六、已知问题 / 待办

| P3 | 队列上限 | 全量拉取上限 100 页/2000 条（防接口异常死循环）；超大收藏夹的内存占用仍待低配机观察 |
