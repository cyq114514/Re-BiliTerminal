# Agent 工作流（workflow）

> 什么时候读：接到一个非平凡任务、需要交接、或要判断"做到哪算完成"时。
> 任务模板：`../templates/task-template.md`；交接规范：`agent-handoff.md`。

## 1. 标准任务生命周期（七步）

1. **理解任务**：目标、影响模块、允许/禁止范围、验收条件。缺信息先问，不要猜。
2. **定向探索**：只读必要代码。先用 `../architecture/module-map.md` 定位模块，再读对应 `../modules/*.md` 的「先读」清单；用符号名/调用链搜索，不要从 6,544 行的播放页第一行开始读。
3. **制定计划**：复杂任务先列预计修改的文件、原因、依赖、风险、验证方式；写进任务模板或提交说明。
4. **实施最小修改**：不夹带格式化、重命名、无关业务改动；一次只做一件事。
5. **自主验证**：按改动范围执行 `commands.md` 里的检查（静态 → 编译 → 产物核验；Release 等价验证只能 CI）。
6. **检查 Diff**：意外删除、无关改动、敏感信息、依赖/构建配置变化、文档一致性。
7. **交付报告**：完成内容、修改文件、验证结果（含未执行项）、风险、下一步。

## 2. 计划与范围（复杂任务）

计划至少写清：

- 目标与验收条件（可检验，不写"优化一下"）；
- 影响模块与预计改动文件；
- 不允许触碰的部分（版本号/签名/包名/第三方模块/用户数据）；
- 验证方式与当前能验证到哪一级（本地/CI/设备）。

超过 3 个文件或跨模块时，先建任务模板（`../templates/task-template.md`）再动手；可以在任务分支或草稿里维护，不必提交。

## 3. 探索策略（省 token）

- 从模块文档和 `path:line` 锚点开始；不要全仓 `grep -r` 不带 include。
- 读大文件用锚点：`PlayerActivity`（6,544 行）、`AudioPlayerService`（1,619 行）、`ShortVideoFeedFragment`（1,572 行）、`DownloadService`（1,149 行）——先读模块文档给出的方法/行号附近，不整文件加载。
- 历史问题查 `../更新日志.md`（按版本），不要读 `docs/audit/**` 当现状。
- 布局/资源改动先看 `DESIGN.md` 的 token 规则，避免自造样式。

## 4. 验证矩阵（与 `commands.md` 一致）

| 改动范围 | 最低验证 | 说明 |
|---|---|---|
| 纯文档 | `git diff --check` + 链接检查（目标文件存在） | 不需要构建 |
| 资源/布局 | Debug 构建 + 视觉检查 | 资源裁剪风险需 CI release 验证 |
| Java 业务 | Debug 构建 + 模块回归清单（能跑则跑） | 无真机时回归标 NOT RUN |
| 构建配置/CI | Debug 构建 + `git diff` 审阅；CI 配置只能真实运行验证 | 未 push 时标 PARTIAL |
| 发布相关 | 全部交给 CI，本地不改 | 版本/签名/update 机制禁改 |

未执行/无法执行必须写 `NOT RUN`/`BLOCKED`/`PARTIAL` 并说明原因；**不得用"配置看起来对"冒充验证通过**。

## 5. Diff 自查清单

- [ ] 没有意外删除（`git diff --stat` + 逐个删除项确认用途）
- [ ] 没有夹带格式化/重命名/无关文件
- [ ] 没有新增凭据、token、keystore、`local.properties` 内容
- [ ] 没有依赖/构建工具版本变化（除非任务明确要求且已评估）
- [ ] 没有改 `applicationId`/versionCode/versionName/签名/ABI
- [ ] 文档与实际一致（新增/修改的路径、命令、链接真实存在）
- [ ] 第三方模块（`ijkplayer-java`/`brotlij`）无改动；DFM 改动有说明

## 6. 交付报告

写清：完成了什么、改了哪些文件、执行了哪些检查及结果、未完成/未验证项、风险与回滚方式。
涉及发布的改动必须写"未创建 tag/未发 Release"。

## 7. 多 Agent 协作

- 每个任务明确**负责人**和**文件边界**；同一文件同一时间只允许一个 Agent 修改。
- 独立任务用独立分支（`feature/*`、`fix/*`、`chore/*`），合并前检查完整 diff。
- 共享结论写进 `docs/architecture/**` 或对应模块文档，不靠聊天记录传递。
- 重大架构/构建决策记 `docs/decisions-*.md`（已有两份先例：主题色、TLS 回移）。
- 交接按 `agent-handoff.md` 执行；关键事实（版本、分支、验证结果）以文件/命令输出为准。

## 8. CI 反馈闭环（现状）

目标流程：改代码 → 提交工作分支 → Actions 自动构建 → 读取结果/日志 → 修复 → 复跑 → 人审合并。

当前现状（如实）：

- 本地可闭环到 **Debug 编译**；
- Actions 的结果读取需要 GitHub 登录或 `gh`，本机**没有**（无 gh、无凭据）→ 只能人工在网页看日志后贴回；
- 因此 CI 闭环验证在补齐凭据前只能标 **PARTIAL/BLOCKED**；
- Release 发布链的最终验证只能在真实发版时完成。

## 9. 文档维护

- 架构/模块边界/构建配置/重要业务行为变化 → 更新 `docs/architecture/**` 或 `docs/modules/**`；
- 普通 Bug 修复不必改架构文档，但**根因值得记录时**补进 `docs/更新日志.md` 对应版本；
- 不生成重复开发日志；不把推测写成事实；不因小改动重写整个项目地图；
- 新增文档要在 `docs/README.md` 登记。
