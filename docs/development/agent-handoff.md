# Agent 交接（agent-handoff）

> 什么时候读：任务中断、换模型/换会话、多人/多 Agent 接力时。
> 模板：`../templates/handoff-template.md`；历史范例：`../交接-收藏夹音频播放.md`（仅结构参考，其中本机路径为历史记录）。

## 1. 交接必须回答的问题

新接手者**只读交接文件 + `AGENTS.md` + 相关模块文档**，应当能知道：

1. 当前任务目标与验收条件是什么；
2. 已经完成了什么、还差什么；
3. 改了哪些文件（含新增/删除），当前分支与提交；
4. 执行过哪些检查、结果如何（PASS/FAIL/PARTIAL/BLOCKED/NOT RUN）；
5. 已知问题、风险与下一步建议；
6. 哪些东西**没有验证**、为什么。

## 2. 事实规则

- 只写事实与证据（文件路径、命令、输出摘要、提交号），**不复制聊天历史**、不写"用户说……"式转述。
- 没执行过的检查不写"已通过"；无法验证写 `BLOCKED`/`PARTIAL` 并给原因。
- 不写推测当成结论；不确定的标"待确认"。
- **不得写入凭据、token、签名口令、`local.properties` 内容**。
- 交接文件里引用代码位置时给 `path:line`（行号以当前分支为准）。

## 3. 存放与命名

- 长期/跨会话交接：放 `docs/handoffs/YYYYMMDD-<主题>.md`（目录按需创建；任务合并后可归档）。
- 短期交接（同一分支内）：可直接写在任务分支的提交说明或 PR 描述里，不必新增文件。
- 交接完成后，若结论已成为长期知识，应把其中可复用部分（架构/模块行为）沉淀到 `docs/architecture/**` 或 `docs/modules/**`，而不是只留在交接文件。

## 4. 写交接的时机

- 任务被中断（会话结束、上下文切换、等待用户决策）；
- 预计需要另一个 Agent/模型接手；
- 一次改动跨越多个阶段，阶段之间需要 review；
- 发现的风险超出当前任务范围，需要移交决策。

## 5. 交接后的动作（接手者）

1. 先 `git status`/`git log` 核对交接里写的分支与提交是否一致；
2. 打开交接列出的文件，确认 diff 与描述一致；
3. 重跑交接里"已验证"的**关键**检查（至少静态检查与编译），不盲信文字；
4. 未完成事项先与用户/负责人确认范围，再继续。
