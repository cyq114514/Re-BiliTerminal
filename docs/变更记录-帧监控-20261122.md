# 变更记录：掉帧监控写进调试日志（2026-11-22）

## 0. 背景

用户反馈搜索页（尤其专栏 tab）快速滑动卡顿，但目标设备是手表与低配手机，没有 adb，
`dumpsys gfxinfo` 取不到数据；应用现有「调试日志落文件」是用户唯一能自己导出的通道
（`Download/ReBiliDiag/app-log.txt`）。本次把主线程掉帧也写进这份日志。

## 1. 实现

新增 `util/FrameMonitor.java`：

- 用 `Choreographer.postFrameCallback` 逐帧比较 vsync 时间差；
- 单帧 ≥ 32ms（60Hz 约 2 帧预算）记为慢帧，连续慢帧合并成一段；
- 段结束（或满 5 秒强制）只写**一条** W 日志：`卡顿 250ms/12 帧，最长 87ms，页面=SearchActivity`；
- 距上一帧 ≥ 1 秒视为息屏/静止后恢复，重置基线，不误报；
- 跟随 `Logu.KEY_FILE_LOG`（设置→实验室→调试日志落文件）启停，靠 SharedPreferences 监听热切换；
  关闭时移除 Choreographer 回调，不做任何采集。

接入 `BiliTerminal`：

- `onCreate`：日志开关初始化之后调用 `FrameMonitor.install()`；
- `onActivityResumed`：`FrameMonitor.notePage(activity)`，让日志能标注卡顿发生在哪一页。

## 2. 验证（PJZ110 / 1.4.1 / versionCode 20261122）

真机覆盖安装后，冷启动与搜索页滑动均产生记录：

```
W 11-22 12:49:25.697 FrameMonitor>flushSegment 卡顿 198ms/2 帧，最长 116ms，页面=RecommendActivity
W 11-22 12:49:26.546 FrameMonitor>flushSegment 卡顿 99ms/1 帧，最长 77ms，页面=RecommendActivity
W 11-22 12:49:51.511 FrameMonitor>flushSegment 卡顿 88ms/1 帧，最长 77ms，页面=SearchActivity
W 11-22 12:50:00.766 FrameMonitor>flushSegment 卡顿 66ms/1 帧，最长 55ms，页面=SearchActivity
```

同一份日志里，66ms 的卡顿紧跟在 `search_type=article&page=2..6` 的请求之后，
说明专栏页滑动卡顿与**连续分页插入**高度相关（`notifyItemRangeInserted` + 新卡片上屏）。

样本：`~/Desktop/bili-jankmonitor-verify-20261122/app-log-sample.txt`（38 行，18 条 FrameMonitor 记录）。

## 3. 已知限制

- **热切换未单独实测**：开关打开后重启一次应用最稳（冷启动路径已实测）。
- 只记 ≥32ms 的明显掉帧；16–32ms 的轻微掉帧不记录（避免日志膨胀）。
- 只测主线程帧间隔，不区分是 layout、图片解码还是 GPU 导致；需要更细的归因仍然要 adb + gfxinfo。
- 日志本身也是文件 I/O（W 级立即 flush），一次卡顿一条，已按段合并限流。
