## 3. 已知限制与未验证项

| 项 | 说明 |
|---|---|
| 首帧颜色 | 系统预览窗口由 manifest 主题在进程启动前绘制，**只能中性化，无法跟随任意配色**。要同色只能枚举预设 + 多 `activity-alias`，不做 |
| 老图补算延迟 | 升级前已导入的背景图没有主色记录，第一次启动解码时后台补算，**下一次启动**才生效（首次仍为粉） |
| 图主色为灰阶 | 有彩像素占非近黑像素 < 20% 时回退默认粉，不强行造色（第二轮改，原为彩度 < 12 判定，见第 5 节修订记录） |
| 未真机验证 | 主题配色页的「来自背景图」文案、预设色块不选中、背景图开关切换后即时换色、「恢复默认」文案分支 |
| 未验证项 | 低配机 / 手表（W527）上量化耗时；暗度 0 的高亮底图取色后的观感 |
| 版本日志 | `UpdateLog.java` / `readme.md` / `site/changelog.html` / `docs/更新日志.md` 四处**未同步**，按约定留到发版时统一写 |

## 5. 修订记录

### 2026-11-14 修复：背景图主色永远不生效（我自己引入的缺陷）

**现象**：用户启用绿色植物背景图后，开屏仍是粉色（截图短线采样 `#FF6097` ≈ 默认粉 `#FE679A`，光晕 `#1D0C12` 也是粉色按呼吸 alpha 衰减后的值）。

**根因**：`BackgroundManager.getSeed()` 用了 `return seed > 0 ? seed : 0;`。主色是不透明 ARGB
（`0xFFRRGGBB`），在 Java 里恒为负数，`seed > 0` 永远 false，图主色被一路当成"没有"。

```
seed = 0xFF37577B → 十进制 -13150341
旧判断 seed > 0   → false
新判断            → #FF37577B
```

**修法**：
1. `getSeed()` 只排除 `0`（以及旧版本哨兵 `-1`），不再做符号判断，返回前统一补 alpha；
2. 状态改用独立布尔键 `bg_image_seed_done` 记录"已经算过"，不再用 `-1` 当哨兵
   （纯白种子就是 `0xFFFFFFFF` = `-1`，哨兵会与真实颜色撞车）；
3. 升级兼容：老安装里已有真实主色的直接认（补上 done 标记），旧 `-1` 当作未计算、重新补算。

**验证**：`./gradlew :app:assembleRelease` BUILD SUCCESSFUL；新包已覆盖安装。
真机取色效果待用户复测（测试期间设备在前台运行其他应用，未再抢占）。

### 2026-11-14 第二轮：取色算法换成色相直方图（用户反馈「色系匹配度不够高」）

**现象**：取色链路已经通了，但取出的颜色和底图的色系对不上（偏橄榄 / 偏青灰）。

**根因**：`QuantizerCelebi` 把整张图聚成 16 个色簇，**簇心是跨色相的加权平均**。图里有两个面积不小的
不同色系时，簇心会落到色相环中间。实测（合成图，主色已知）：

| 用例（主色占比） | 旧：量化簇心 | 新：色相直方图 |
|---|---|---|
| 70% 绿 `#3E7B3E` + 30% 红 | `#7B733E` **偏差 43°** | `#3E7B3E` **偏差 0°** |
| 60% 天蓝 `#7FA8C9` + 40% 草绿 | `#769791` **偏差 57°** | `#7FA8C9` **偏差 0°** |
| 90% 绿 + 10% 红 | `#3E7B3E` 0° | `#3E7B3E` 0° |
| 纯色 / 单色系 | 准确 | 准确 |

另外验证了「把量化色数从 16 提到 64」对上面两个用例完全没有改善（跨色相平均发生在聚类阶段）。

**改法**：
1. `ImageSeeder` 主路径换成色相直方图：112px 采样 → 跳过近灰（S<0.18）/近黑（V<0.12）→ 36 段色相按饱和度
   加权 → 环形平滑取峰值桶 → 只在峰值桶 ±1 内加权平均 RGB。量化器降级为兜底。
2. 灰阶图判定改为「有彩像素占非近黑像素 < 20% → 回退默认粉」，不再从灰底里抠彩色小点。
3. 新增算法版本键 `bg_image_seed_ver`（当前 2）：版本对不上时旧主色作废，解码图片时后台重算，
   **下一次启动**生效（不需要用户重新选图）。
4. `KEY_SEED_DONE` 与版本键共同决定是否重算；`clear()` 三个键一起清。

**验证**（同一套合成用例，直调 `ImageSeeder.seedFromPixels`）：

**已知限制**：
- 算法升级后第一次冷启动仍显示旧色/粉（旧值被判失效），进一次首页触发重算，**第二次冷启动**才是新色；

### 2026-11-14 第三轮：色相/彩度/明度统一到 HCT（用户提供三张真实图片后）

**输入**：`0967544…jpg`（开屏截图）、`98abc97…jpg`（首页截图）、`da20dd5…jpg`（背景原图，1280x1379 暖调插画）。

**取证**：从开屏截图里定位到那条 2dp 短线（y=1025~1029，命中 67 像素/行），实际颜色
`#A37F77`（H28 C13 T55）——即当时的种子 `#A47D72`。用户感知的"不匹配"确实存在。

**根因（不是色相取错，是"暗 + 灰"）**：

| 统计口径 | 色相 | 彩度 | 明度 |
|---|---|---|---|
| RGB 直接平均（旧） | 35° | 17 | 56 |
| 亮部（V>0.65）加权 | 35° | 21 | 62 |
| 主色系内 p90 彩度 / p75 明度 | 35° | 24 | 62 |

也就是说：色相本来就对（暖桃/米），但**彩度被拉低 1/3、明度被大片阴影压低 6 档**，
结果就是棕褐色。画面里的"粉"属于次峰（约 20°）的低彩度小面积，不是主导色系。

**改法**（`ImageSeeder`）：
1. 色相：HCT 圆平均（sin/cos，按饱和度加权），不再用 RGB 平均；
2. 彩度：加权平均后取 `max(C, 26)`、上限 60（去脏，但不放大成刺眼）；
3. 明度：主色系内的**第 75 百分位**（`toneHistogram` 加权分位），不再用平均；
4. 算法版本 `bg_image_seed_ver` → 3，已存主色下一次解码时自动重算。

**我引入的回归与修正**：第一版把 HSV 的圆平均色相直接喂给 `Hct.from(hue,...)`，两套色相刻度不同，
导致合成用例里绿色 146°→120°、天蓝 242°→207°。已改为全程 HCT，并把这两条加进回归用例。

**已知限制**：
